# 自动下载（原「自动沉淀」，已合流到下载中心）设计与实现

> 状态：已实施（2026-09-22 合流重构）；**2026-09-23 修正筛选口径**：「当天」由 `update_date` 改为 `posts.date`（发布日），详见 §3。
> 对应需求：依据当天发布的帖子，按规则自动筛选并提交为下载中心任务（kind=auto），与手动下载共用同一队列、同一落盘目录与全部能力。

## 1. 目标

把「当天发布」的帖子中满足筛选条件的，作为 `kind=auto` 任务提交到下载中心队列，由下载中心统一调度落盘到 `downloads/<sanitize_title(标题)>/`。不再独立落盘、不再写 `post.json`/`post.md` 元数据；因此沉淀结果自动计入资产漏斗与「已沉淀」标记（同一棵树 + 同一份履历，无需另写逻辑）。

## 2. 触发方式

页面可配置的应用内定时任务（与定时抓取同源调度）：参数设置页「自动下载」组配置开关与时刻；建议自动下载时刻排在抓取时刻之后，确保当天数据已入库。

- 调度状态：`web/scheduler.py` 的 `PrecipitateJob`，与 `ScrapeJob` 共用 `JobScheduler` 的单线程 60s tick、状态文件、幂等防重（第 24 条约束）。
- 手动触发：`POST /api/precipitate/run`（不受定时时刻限制），用于即时验证。

## 3. 筛选口径（多条件取交集）

`query_candidates()` 按以下全部条件取交集：

| 条件 | 配置项 | 取值 |
|---|---|---|
| 当天发布 | `date = 当天运行日`（帖子真实发布日） | 固定前提（与「当天新内容」口径一致） |

**口径修正（2026-09-23）**：原用 `update_date = 当天`，实测双向偏差——① `update_date` 语义是「最近一次**覆盖**写入日」（`scraper.py` 首次插入硬编码为空串），抓取为全站重抓（单批写库 12 万+ 条），存量历史帖天天被 upsert 刷成当天，按它筛选等于把几个月前的旧帖当成当天新帖（实测候选 816 条仅 1 条为当天发布，其余跨 2-9 月）；② 当天首次入库的新帖该列为空，被整个漏掉（实测 123 帖，版块白名单内 57 帖）。改为 `date = 当天` 后同条件候选 398 条**全部为当天发布**（旧口径同条件 47967 条，其中当天发布仅 341 条）。
| 版块白名单 | `precipitate_fids`（逗号分隔 fid，可空） | `fid IN (...)`，空则不限版块 |
| 标题关键词 | `precipitate_keywords`（逗号分隔，可空） | `title LIKE %kw%`，多个取 OR |
| 互动量阈值 | `precipitate_min_likes` / `precipitate_min_replies`（默认 0） | `(likes≥阈值 OR replies≥阈值)`，任一达标即可（OR 语义已与用户确认） |

SQL 占位符一律 `?` 绑定（不拼字面量，规避第 10 条 SQL 注入/残留风险）。

## 4. 落盘与复用（合流到下载中心）

- 落盘完全交给下载中心：`run_precipitate()` 调用 `download_tasks.manager.submit(urls, kind="auto")`，由下载中心按其既有逻辑落盘到 `downloads/<sanitize_title(标题)>/`，媒体与清单结构与手动下载一致。
- 媒体下载与清单导出复用 `download_files.process_one_detail`（图片/视频/种子实下 + 磁力/云盘写清单），不另写下载逻辑（见 CODEBUDDY.md 第 37 条）。
- 不再区分「自动归档管线」与「手动队列」——两者是同一队列、同一棵树，避免污染也避免重复实现。

## 5. 去重（提交前过滤，避免空跑）

提交前用下载中心履历的并集（已落盘 `alive` + 正在下载 `active`，`active` 含 pending/running）换算成磁盘路径集合，剔除候选中已存在同帖的 URL，避免重复提交、并发写同一文件与空跑。

**前提（2026-09-23 修复）**：`asset_snapshot()` 带 5s TTL memo，而 `submit()` 原先**不失效**它 —— 于是「刚提交的 pending 链接」在 TTL 内对去重不可见，紧接着的第二次触发（手动连点、定时与手动重叠）会把同一批 URL 再提交一遍。失效已内聚进 `manager.submit()`（自动下载直连 submit，不走 api 层那套失效）。实测同一用例由「第 2 次仍提交 2 帖」变为「提交 0 帖、跳过 3」。

## 6. 磁盘水位守卫（提交前必须判，避免写满磁盘）

本机存媒体，**盘满是头号风险**。自动下载是批量向 `downloads/` 连续写入的功能，必须有水位守卫。

- **判据**：`shutil.disk_usage(downloads/).free`（零依赖，复用健康条同一原语）。阈值 `precipitate_min_free_gb`（页内白名单，默认 20GB，与资产条 `diskLow` 红色判据「不足 10% 或不足 20GB」对齐；白名单含上限钳制，防误填天文数字）。
- **触发**：低于阈值即停止提交（已提交的任务仍会跑完），汇总返回 `disk_low`(bool) / `disk_free_gb` / `threshold_gb`，调度器据此生成「磁盘可用空间不足…已停止自动下载」文案。
- **提示复用既有载体（不新建站内信）**：① 写进调度状态 `last.reason`（设置页「上次结果」常驻可见，磁盘不足时文字标红 + `el-alert` 告警）；② 全局「磁盘剩余」由已有的健康条/资产条负责标红。

## 7. 并发

提交动作本身很轻（仅组装 URL + 过滤 + 一次 `submit` 调用）；真正并发由下载中心按 `download_task_concurrency` 控制，不再单独开 `ThreadPoolExecutor`（避免与下载中心抢源站、避免两套并发口径）。

## 8. 配置项

- 环境变量（部署配置，不进白名单）：`TXXY_PRECIPITATE_ENABLED` / `TXXY_PRECIPITATE_TIMES`（默认值，页内可覆盖）、`TXXY_PRECIPITATE_SCHEDULE_STATE_FILE`（调度状态落盘位置）。
- 页内白名单（`web/settings.py`）：`precipitate_enabled`(bool)、`precipitate_times`(times)、`precipitate_keywords`(text)、`precipitate_min_likes`(int,0..100000)、`precipitate_min_replies`(int)、`precipitate_fids`(text)、`precipitate_min_free_gb`(int,0..1000,默认20,提交前磁盘水位阈值)。关键词/版块白名单用 `text` 存逗号分隔串（前端 `array` 类型只支持固定选项，自由文本用 text 更合适）。

## 9. 验证情况

- 已实测：筛选交集、阈值 OR 语义、提交前去重（alive/active 路径并集）、磁盘守卫返回 `disk_low`、调度 `status()` 返回 `{scrape, precipitate}` 结构；接口层 `GET /api/schedule`、`POST /api/precipitate/run` 直接调用 handler 验证不报错。
- **2026-09-23 口径修正实测**（隔离实例 `TXXY_WEB_PORT=8089` + 临时调度/任务/履历文件，真实链路）：
  - 接口级：`GET /api/schedule` 的 `precipitate` 段正常（enabled / times / next_run_at / last）；`POST /api/precipitate/run` 返回 `{"total":0,"submitted":0,"disk_low":false,"disk_free_gb":57.2,...}` 无 500；手动触发后 `last` 立即回写（与定时同源）；设置白名单已含 `precipitate_min_free_gb`（页面可见）。
  - 口径级（同一 `query_candidates` 函数）：仅按版块白名单取 `2026-09-22`，候选 **398 条全部 `date=2026-09-22`**；旧口径同条件 47967 条、其中当天发布仅 341 条（差额 47626 条全为历史帖）。
  - 顺带清理：设置里误填关键词 `V]`（全库命中 1042，匹配标题尾缀 `[2V]` 等）已移除，保留 `人间光影录,乳控之家`。
  - **未实测**：修改后真实媒体落盘（当天命中帖需等下一次抓取产生当天发布数据），待 09-23 抓取后观察 22:30 自动下载的实际提交量。
- **2026-09-23 结果文案分档**（用户质疑「提交 0 帖…（共 0，下载中心已下跳过 0）」不合理）：0 结果必须能区分根因，汇总新增 `today_posts`（当天发布入库总数，作分母）与 `reason`，由 `precipitate.summary_reason()` 唯一生成，定时「上次结果」/ 手动 toast / 前端提示四处同源：

  | 场景 | 文案 |
  |---|---|
  | 当天无发布数据入库 | `当天（2026-09-23）尚无发布数据入库（抓取未完成或未运行），未提交任何下载` |
  | 有数据但没命中 | `当天发布 3 帖，无一命中筛选条件（版块 / 关键词 / 互动阈值），未提交` |
  | 命中但已下过 | `命中 3 帖，但下载中心已全部下载过（跳过 3），未重复提交` |
  | 磁盘不足 | `磁盘可用空间不足（56.9 GB < 阈值 1000 GB），已停止自动下载：命中 3 帖未提交` |
  | 未启用 | `自动下载未启用，未执行本次筛选` |

  7 个真实用例（上表五档 + 命中提交 + 定时与手动同源）全通过。
- **未实测**：真实媒体下载（图片/视频/种子/磁力/云盘清单）需要访问外网或本地镜像，本沙箱无法联网，需在可联网环境跑一次确认 `downloads/` 下真实产出。底层落盘由下载中心长期验证，本次仅新增「筛选 + 提交 kind=auto」，回归风险低。
