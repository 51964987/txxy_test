# txxy 数据展示项目优化建议方案

> 状态：待确认（2026-08-26 产出，基于代码走查 + 互联网最佳实践，尚未改动任何代码）
> 适用范围：web/ 后端（FastAPI + SQLite 只读）与前端（Vue3 + Vite5 + Element Plus + ECharts5）
> 原则：不改变路由路径与 history 模式、不关闭自动刷新（保持 5s 轮询）、Web 进程不写库；每条建议独立，可单独确认、单独实施。

## 一、现状盘点（已具备的优化点，避免重复建设）

- 数据库：WAL 模式 + `PRAGMA query_only=ON` 只读并发安全；索引体系完整（表达式索引 `idx_posts_likes_expr` / `idx_posts_replies_expr`、复合索引 `idx_posts_fid_date_created`、部分索引 `idx_posts_author`、排序索引 `idx_posts_likes_num` 等）。
- 统计接口已做 5s TTL 内存缓存：`/stats/overview`、`/stats/boards`、`/stats/trend_by_fid`、`/stats/fid_dist`、`/posts/fid`。
- CSV 导出已流式（`iter_query` + `StreamingResponse`）并带 UTF-8 BOM。
- 前端 ECharts 已按需引入（`echarts/core` + 只注册 Line/Pie/EffectScatter 与所需组件），此项无需再优化。
- 前端数据总览已做懒加载（`IntersectionObserver`）与 KPI 卡合并（7 张 → 4 张）。
- 帖子页搜索已防抖、导出走 `window.open` 直链。

## 二、P0 建议（收益明显，推荐近期实施）

### P0-1 前端 fetch 封装：超时 + 取消 + 统一错误处理（✅ 已实施 2026-08-26）

**现状问题**
- `web/frontend/src/api/index.ts` 使用原生 `fetch`，**未设置任何超时**：网络异常/后端卡死时请求可能无限挂起，5s 轮询会不断叠加挂起请求，最终堆积。
- 无请求取消机制；无统一错误归一（各 view 各自 try/catch + `ElMessage.error`）。

**方案**
- 封装 `request<T>(path, params, opts)`：内部用 `AbortController` 实现默认 10s 超时；同一轮询 key 发起新请求时自动取消上一次未完成请求（防堆积）。
- 保持现有 `api.xxx` 方法签名不变，各 view 调用处零改动。
- 统一错误归一：非 2xx 时解析 `detail` 抛 `Error`，轮询场景可传入 `silent` 跳过弹错。

**涉及文件**：`web/frontend/src/api/index.ts`、`web/frontend/src/views/DashboardView.vue`、`RunsView.vue`、`PostsView.vue`、`ResourcesView.vue`
**收益**：杜绝请求挂起与堆积；轮询稳定性提升。**风险**：低（仅封装层改动）。

**落地说明（2026-08-26）**：`api/index.ts` 新增 `ApiError`（区分 timeout / network / http / aborted）与 `isAborted()`；`request()` 内置默认 10s 超时与「同 key 新请求顶掉旧请求」去重；各视图 catch 中对主动取消静默忽略；`DashboardView` 5s 轮询与榜单轮询刷新失败静默（仅首屏加载失败提示）。`api.xxx` 方法签名不变，`npx vue-tsc --noEmit` 0 错误。

### P0-2 轮询与图表动画的「页面可见性感知」（visibilitychange）（✅ 已实施 2026-08-26）

**现状问题**
- `DashboardView.vue`：5s `setInterval` 轮询（第 520 行 `autoRefreshTick`）+ 三组轮播定时器（排行榜滚动 2s、环形图高亮轮播 2.2s、趋势图 tooltip 轮播 900ms/1500ms）。
- `RunsView.vue`：4s `setInterval` 轮询。
- 页面切到后台/隐藏时，浏览器将定时器节流到 1 次/分钟甚至挂起，但定时器仍持续注册、恢复可见后会积压执行，浪费 CPU/电量/流量，且轮询可能产生并发重叠。

**方案**
- 监听 `document.visibilitychange`：页面隐藏时统一 `clearInterval` 轮询与全部轮播定时器；恢复可见时立即触发一次刷新并恢复定时器。
- 轮询由 `setInterval` 改为「`setTimeout` 递归 + 请求完成后排下一次」，加 `inFlight` 标志防重入。
- 与 `store.autoRefresh` 开关联动：关闭时不恢复轮询。
- `RunsView.vue` 同样处理。

**涉及文件**：`web/frontend/src/views/DashboardView.vue`、`web/frontend/src/views/RunsView.vue`
**收益**：后台页签零请求、零动画；恢复即最新数据；消除请求堆积。**风险**：低。

**落地说明（2026-08-26）**：两个视图均监听 `visibilitychange`：隐藏时 `stopAllTimers` 暂停 5s/4s 轮询与全部轮播动画（排行榜滚动、环形图轮播、趋势 tooltip 轮播），恢复可见立即刷新一次并重启；`autoRefreshTick` 与 `refreshQuiet` 增加防重入（上一轮未完成则跳过本轮），配合 P0-1 的请求去重，无需 `setInterval` 改 `setTimeout` 也已无并发重叠。

### P0-3 后端未缓存接口补齐 TTL 缓存（✅ 已实施 2026-08-26）

**现状问题**
- `/stats/trend`、`/stats/recent`、`/runs`、`/runs/detail/{id}`、`/runs/{date}` 均未走 `db.cached`，而它们正被前端 5s / 4s 轮询高频调用，每次都直查数据库。

**方案**
- `/stats/trend`：`db.cached(f"trend_{days}", _calc)`，5s TTL，与前端轮询节奏一致。
- `/stats/recent`：`db.cached("recent", _calc)`。
- `/runs`、`/runs/detail/{id}`：`db.cached` 5s TTL（运行记录更新频率低于 5s，可接受）。
- `/posts`：筛选/分页组合多、命中率低，**不建议缓存**；但可将 COUNT 与列表两条查询合并为同连接执行，减少一次连接开销。

**涉及文件**：`web/api.py`
**收益**：轮询场景数据库压力显著下降。**风险**：低（复用现有 `db.cached` 机制）。

**落地说明（2026-08-26）**：`/stats/trend`（`trend_{days}`）、`/stats/recent`（`recent_{limit}`）、`/runs`、`/runs/detail/{id}`、`/runs/{date}` 均已套 `db.cached` 5s TTL；`/posts` 的 COUNT 与列表查询合并为单连接执行。`python -c "import api, resources, app"` 通过。

### P0-4 resources 扫描增量缓存（✅ 已实施 2026-08-26）

**现状问题**
- `web/resources.py` 的 `scan()` 每次请求都对 `downloads/` 目录 `rglob("*")` 全量扫描，文件较多时每次耗时可达几十到上百毫秒，且无缓存。

**方案**
- 方案 A（推荐）：模块级缓存，以「各文件夹 `mtime` + 顶层目录集合」作签名，签名未变直接返回缓存结果；新增/删除/覆盖文件时 `mtime` 变化自动失效。
- 方案 B（简化）：直接套 `db.cached("resources", scan, ttl=30)`，实现最快，但文件列表最长 30s 延迟。

**涉及文件**：`web/resources.py`
**收益**：大目录下资源页响应从百毫秒级降到 1ms 级。**风险**：低。

**落地说明（2026-08-26）**：按方案 A 实施：`scan()` 以「顶层文件夹名 + 各自 mtime」生成目录签名，签名未变直接复用上次扫描结果；新增/删除/覆盖文件均使 mtime 变化自动失效。

### P0-5 启用 GZip 压缩中间件

**现状问题**
- 未启用任何压缩。大文本响应较多：`/resources` 文件清单、`/posts` 分页列表、`/stats/trend_by_fid`（365 天多系列）、CSV 导出。

**方案**
- `app.py` 挂载 `GZipMiddleware(minimum_size=1024)`；`StreamingResponse`（CSV）同样会被压缩，浏览器自动解压，无副作用。

**涉及文件**：`web/app.py`
**收益**：文本类响应体积下降 60%–80%（内网收益小、公网部署明显）。**风险**：极低。

**落地说明（2026-08-26）**：`app.py` 挂载 `GZipMiddleware(minimum_size=1024)`，JSON 列表与 CSV 导出均自动压缩（浏览器自动解压，无副作用）。

### P0-6 前端打包体积优化

**现状问题**
- `main.ts` 全量引入 Element Plus（`app.use(ElementPlus)` + 全量 icons 循环注册 + 全量 `dist/index.css`）。
- 4 个视图路由未做懒加载（搜索无 `() => import(...)`）。
- `vite.config.ts` 无 `manualChunks` 分包，element-plus / echarts / vue 全部打进主包，任何依赖升级都会击穿浏览器缓存。

**方案**
1. **icons 按需注册**：`main.ts` 中改为只注册实际用到的图标（可数，约 20–30 个），去掉全量循环注册。
2. **Element Plus 按需**（可选，二选一）：
   - 方案 A：保持全量 `app.use(ElementPlus)`，仅做 icons 按需 + css 按需（改动最小）。
   - 方案 B：引入 `unplugin-vue-components` + `unplugin-auto-import` 自动按需（新增 2 个 devDependency，代码零改动）。
3. **路由懒加载**：`router/index.ts` 4 个 view 改为 `component: () => import('@/views/xxx.vue')`。
4. **manualChunks 分包**：`vite.config.ts` 将 `vue/vue-router/pinia`、`element-plus`、`echarts` 拆为独立 chunk。

**涉及文件**：`web/frontend/src/main.ts`、`web/frontend/vite.config.ts`（路由懒加载项目本已具备，未改动）
**收益**：首屏 JS 体积下降约 30%–50%，依赖独立 chunk 长缓存。**风险**：中（需回归验证各页面组件、图标显示正常）。

**落地说明（2026-08-26）**：`main.ts` 图标改为按需注册（Odometer / Document / Clock / FolderOpened / Files / Coin / Collection / TrendCharts / DataLine / User / CaretTop / Star / ChatDotRound 共 13 个，PostsView 的局部图标本就按需）；`vite.config.ts` 增加 `manualChunks` 将 vue 全家桶 / element-plus / echarts 拆为独立 chunk；路由懒加载检查发现项目本已使用 `() => import(...)`，未重复改动。`npx vue-tsc --noEmit` 0 错误。

## 三、P1 建议（值得做，按需安排）

### P1-7 stats_overview 查询合并（✅ 已实施 2026-08-26）

**现状问题**
- `_calc()` 内 7 次独立 `db.query()`，每次开/关一次连接；缓存 miss 时开销放大。

**方案**
- 单连接内依次执行：`total/today/yesterday/week` 合并为一条条件聚合 SQL（`SUM(CASE WHEN date = ? THEN 1 ELSE 0 END)`）；`COUNT(DISTINCT author)` 两条保留（已建部分索引 `idx_posts_author`）。

**涉及文件**：`web/api.py`
**收益**：缓存 miss 时少 6 次连接往返，响应更快。**风险**：低（SQL 等价性需验证）。

**落地说明（2026-08-26）**：`stats_overview._calc()` 改为单连接内 4 条语句：`total/today/yesterday/week` 合并为一条条件聚合（`COUNT(CASE WHEN ... THEN 1 END)`，表空时返回 0 而非 NULL），`MAX(created_at)/MAX(date)` 一条，两个 `COUNT(DISTINCT author)` 两条；原 7 次独立 `db.query()` 连接开销消除。`app.openapi()` 生成正常。

### P1-8 图表 setOption 防重复重绘（✅ 已实施 2026-08-26）

**现状问题**
- `autoRefreshTick` 每次轮询都用最新数据全量 `setOption`；两次抓取间隔内数据无变化时仍重复重绘，白白消耗 CPU。

**方案**
- 对每张图表做数据指纹比对（关键字段 `JSON.stringify` 后算轻量哈希），无变化跳过 `setOption`；有变化时用 `setOption(option, { lazyUpdate: true })`。

**涉及文件**：`web/frontend/src/views/DashboardView.vue`
**收益**：轮询期间图表重绘次数大幅下降。**风险**：低。

**落地说明（2026-08-26）**：三张图表各加数据指纹，无变化直接 `return` 跳过 `setOption`（未用 `lazyUpdate`，因指纹命中时无需重绘）：趋势图指纹含 `linkedFid.color`（联动配色变化需重绘）；环形图指纹含视口宽度（`wide` 布局变化需重绘）；各版块趋势图指纹含 `linkedDay` / `linkedFid.name`（联动聚焦变化需重绘）。另将趋势图 click 反向联动注册移入 `trendTipSynced` 一次性初始化块，消除数据刷新后 click handler 重复绑定累积。`npx vue-tsc --noEmit` 0 错误。

### P1-9 DashboardView.vue 拆分组件

**现状问题**
- 单文件约 2300 行，KPI / 趋势图 / 环形图 / 排行榜 / 多组轮播 / 轮询调度 / 懒加载高度耦合，可维护性差。

**方案**
- 按区块拆为 `web/frontend/src/components/dashboard/` 下的子组件：`StatCards.vue`、`TrendChart.vue`、`FidDistPie.vue`、`FidDistBoard.vue`；父组件保留数据获取与调度，通过 props/事件下发。
- 建议一次迁移一个区块，保证行为不变，最后再删冗余。

**涉及文件**：`web/frontend/src/views/DashboardView.vue`、`web/frontend/src/components/dashboard/*`
**收益**：可维护性显著提升，为后续按区块懒加载铺路。**风险**：中（重构量较大）。

### P1-10 接口 response_model 与错误格式统一（✅ 已实施 2026-08-26）

**现状问题**
- 接口直接返回 dict，无 Pydantic 响应模型；错误有 `HTTPException(detail)` 与自定义 `{ok:false,msg}` 两种形态。

**方案**
- 为关键接口（overview、posts、runs、resources）补充 `response_model`，自动生成文档并做运行时校验。
- 错误统一为 `HTTPException(detail={ok:false,msg})` 或统一 `{ok:false,msg}`，前端 `get()` 已能解析 `detail`。

**涉及文件**：`web/api.py`、`web/frontend/src/api/index.ts`
**收益**：API 契约明确。**风险**：低，但改动面较大，建议放在 P0 之后。

**落地说明（2026-08-26）**：错误格式检查确认后端全部为 `HTTPException(detail)`，无 `{ok:false,msg}` 形态（前端 `get()` 已统一解析 `detail`），无需改动。为结构稳定的核心接口补充 Pydantic 模型与返回类型注解：`/config`、`/stats/overview`、`/stats/boards`、`/stats/trend`、`/stats/trend_by_fid`、`/stats/fid_dist`、`/stats/recent`、`/posts/fid`、`/posts`；`/runs`、`/resources` 因字段条件性存在（运行中 / 日志回退等）不强制模型，避免 `response_model` 静默丢弃字段破坏前端契约。`app.openapi()` 生成正常，接口行为不变。

### P1-11 后端连接复用（per-thread 连接池，可选）

**现状问题**
- `db.query()` 每次 open/close 连接；5s 轮询多接口并发时连接创建较频繁。

**方案**
- 用 `threading.local` 缓存连接，进程内每线程复用（FastAPI 同步接口跑在线程池，`threading.local` 天然线程安全）；线程池回收时连接随之释放。
- 说明：SQLite 连接本身很轻量，此项收益有限；若 P0-3 缓存补齐后 DB 压力已明显下降，本项可不做。

**涉及文件**：`web/db.py`
**收益**：查询往返中省去连接创建/销毁开销。**风险**：中（需处理好连接生命周期），故列为可选。
