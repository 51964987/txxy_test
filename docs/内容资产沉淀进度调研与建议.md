# 内容资产沉淀进度 — 调研与建议（2026-09-13）

> 主题：数据总览「内容资产」卡的副标题——**收录内容沉淀为本地媒体资产的进度**。围绕这一个指标域，回答三件事：① 业界怎么做「沉淀进度」；② 本项目现状差在哪（含实测证据）；③ 建议怎么改、按什么优先级。
> 状态：**C1-C11 已实施（2026-09-13）**，C12（冷热分层/归档）按本文结论暂不做；另有 2 个实施中发现并一并修复的既有缺陷（见第八节）。落地说明见《数据总览大屏设计与优化总览.md》第二十节，实施记录与偏离说明见本文第八节。
> 关联文档：《数据总览大屏设计与优化总览.md》§17.4（R4 资产漏斗落地）、§17.8（按类型占比与下钻）、§18.1（下载履历）、§19.2（资产卡空态）；《数据总览大屏业务优化建议.md》R4；《参数设置页调研与建议.md》（若采纳「沉淀目标」需新增设置项）。

## 零、结论先行

1. **缺的不是数字，是目标。** 卡片的分母是全库长尾（146,824）。实测分层后差异极大：全库沉淀率 0.089%，但全站互动 Top500 是 3.40%（38 倍）、「技術討論區」单版块是 1.11%。业界表达「进度」一律用**分层 / 分群**，不用全库平均值——被长尾稀释的百分比既不好看也不可行动。
2. **五态只呈现了一态。** 业界把「库存（已落盘）/ 在途（队列中）/ 缺口（监控中未获取）/ 失败」并列同屏；本项目卡片只展示了「库存」+ 一个累计转化率，看不出「沉淀这件事是否在推进」。
3. **混了量纲。** 第 4 级「占用体积」是字节，不是漏斗的一级（BI 漏斗各级必须是同一分析单元，否则百分比与"逐级递减"都不成立）。而且体积已被视频主导（体积 95.7% / 文件 37.9%），单看体积会严重误判资产结构。
4. **「进度」必然含时间，但当前算不出速率。** 下载履历是 `url → 目录` 的映射，**没有时间戳**；目录 mtime 不能当代理（实测 130 个目录里 123 个 mtime 集中在同一天，明显是批量搬移产生）。要做增长曲线 / 停滞告警，前置是给履历加时间戳。
5. **实测发现一处口径缺陷（真 bug）。** `extract_torrents.sanitize_title` 把目录名截断到 80 字符，长标题帖的目录名 ≠ 库内标题，履历「目录名 = 帖子标题」的精确恢复失配 → 「已下载帖」少计 2 条（132 个目录只有 130 条被认领），且这类帖会被「待下载推荐」重复推荐。
6. **下钻不对称。** 帖子页有「未下载」过滤、没有「已下载」过滤；卡片上「已下载帖 130」点下去无处可去——与既有的「所有数字必须可下钻到明细」约定不一致。

### 1.1 卡片形态（现状）

- 位置：数据总览 KPI 行下方，全宽紧凑横条卡；卡名「内容资产」，副标题「收录内容沉淀为本地媒体资产的进度」。

## 二、业界做法对照

### 2.1 对照表

| 产品 / 系统 | 与「沉淀进度」相关的关键概念 | 对本项目的启示 |
|---|---|---|
| **Sonarr / Radarr / Lidarr（\*arr 系列）** | 库（Library）= 已知条目；**Wanted → Missing**（监控中但未获取）+ **Cutoff Unmet**（已获取但未达质量档）；队列页显示在途与失败；库级「X / Y 已获取」；System → Status 有独立 **Disk Space** 页 | 本项目最贴切的对照：收录 ≈ 库、已下载 ≈ Have、待下载 ≈ Missing。**缺失清单是一等公民**，不是一个转化率百分比 |
| **rclone check / rsync --dry-run** | 源 → 目标**双边对账**：`matches / differs / missing on dst / extra on dst` | 「132 目录 vs 130 帖」的差就是 `extra on dst`，业界会明确报出来而不是静默吞掉 |
| **ArchiveBox** | 每个 URL 一个 snapshot，状态机 `pending / succeeded / failed`；首页汇总快照数与总体积；失败项可重试 | 失败要能被看见与重试；「沉淀」是**每帖状态机**，不是一次性布尔量 |
| **qBittorrent / aria2 / AriaNg / Motrix** | 队列分「下载中 / 等待 / 已完成 / 失败」，显示速度、ETA、`stalled`（停滞） | 「在途」与「停滞」是独立信号；没有它们就看不出"进没在动" |
| **Jellyfin / Plex / Emby** | 媒体库统计（条目数 / 总时长 / 占用空间）、扫描进度、最近添加 | 「库存统计」与「容量占用」是两个视图，不塞进一条漏斗 |
| **Immich / PhotoPrism / Nextcloud** | 备份进度（待备份 N / 已备份 / 失败可重试）、按类型占用、重复资源提示 | 「待处理队列 + 按类型占用」是用户真正会看的两个数 |
| **DAMS（Bynder / AEM Assets 等）** | 资产生命周期 `ingest → enrich → store → preserve`，KPI 用 **ingestion completeness / metadata completeness** | 「完成度」要相对**目标**定义（多少算收完），而非相对"全宇宙" |
| **GA4 / Amplitude / Mixpanel 漏斗** | 同级分析单元逐级递减 + drop-off；**必须按 segment / cohort 对比** | 混量纲（个数 → 字节）不是漏斗；全库平均被长尾稀释，必须分层 |
| **Grafana / Datadog（SLO）** | stat（当前值）/ gauge（对目标）/ time series（增长曲线）/ no-data 标注；SLO = 目标 + 已用额度 + 剩余额度 | 「进度」= 已完成 / **目标**，且需要时间序列来回答"在涨还是在停" |

### 2.2 提炼出的五条口径原则

- **P1 进度必须相对目标。** 没有目标（"收完哪些、收完多少"），百分比就只是一个没有分母语义的比值。
- **P2 分母必须分层。** 库存类覆盖率一律被长尾稀释；业界做法是同时给出整体值与分段值（segments/cohorts）。
- **P3 库存 / 在途 / 缺口 / 失败 四态同屏。** 只看库存等于只看结果不看过程，"进度感"全在另外三态。
- **P4 计数与字节分列两个视图。** 漏斗管"收了多少条"，存储管"占了多少空间 + 还剩多少"。
- **P5 每个数字都能下钻到明细。** 否则用户看到反直觉的数字（如 0.089%）只能怀疑数据。

## 三、现状差距诊断

| 编号 | 差距 | 实测证据 | 影响 |
|---|---|---|---|
| **D1** | 分母不可解释：`posts_total` = 全库长尾 | 全库 0.089% vs Top500 3.40% vs「技術討論區」1.11% | 卡片天天显示 0.1%，用户无法判断"这是没在收，还是本来就不该全收" |
| **D2** | 五态只呈现一态（库存） | 卡片只展示已下载帖 130 / 文件 3,313；在途、缺口、失败、可重下、空壳均不在卡上 | 无法回答"沉淀是否在推进"，「进度」名不副实 |
| **D3** | 混量纲 + 体积被视频主导 | 第 4 级是字节；视频占体积 95.7% 但只占文件 37.9% | 漏斗"逐级递减"在最后一级失效；体积数字会被误读为"收得很多视频" |
| **D4** | 无时间维度，且履历无时间戳 | 履历是 `url → 目录` 纯映射；目录 mtime 分布：09-08 有 123 个、09-09 有 2 个、09-12 有 5 个（批量搬移痕迹） | 无法出增长曲线、沉淀速率、停滞告警；"进度"缺了时间轴 |
| **D5** | 长标题帖失配（真 bug） | `sanitize_title` = `cleaned[:80]`；2 个未认领目录名 80 字、库内标题 99 / 90 字（前缀匹配命中 1 条，全等失败） | 「已下载帖」少计 ~1.5%；这类帖会被「待下载推荐」重复推荐；资源管理页来源回溯走模糊 LIKE 才能显示原帖 |
| **D6** | 无双边对账 | 磁盘 132 目录 vs 履历认领 130；空目录 0（当前） | 数字对不上时无解释入口（rclone check 的 extra/missing 概念缺失） |
| **D7** | 下钻不对称 | 帖子页有 `undownloaded=1`、无 `downloaded=1`；卡片「已下载帖」不可点 | 违反既有"数字自洽 + 可下钻"约定，用户无法核对这 130 条是什么 |
| **D8** | 无存储余量视角 | 可用 39.0 GB / 已用 22.2 GB；卡片无剩余空间与"还能收多少" | 容量规划靠手工看资源管理器；无法回答"照这个速度还能撑多久" |
| **D9** | 失败无持久来源 | 任务面板仅剩 8 条（历史被清理），明细全 ok；履历只记成功 | 失败率、失败清单在任务清理后永久丢失，与 §18.1「履历独立持久化」的思路不一致（履历只做了一半） |

## 四、建议清单

### 4.1 P0：口径修正（低成本、直接消除错误与误导）

**C1 分母分层：首级改为「可沉淀范围」，并给出分层值**

- 做法：卡片首级保留「收录帖子」（全库，作为上下文），在漏斗下方补一行**分层沉淀率**：`全库 0.09% · 互动≥10 0.34% · Top500 3.40%`（三档固定口径，后端一次算完返回）；另在卡头把转化率标签从裸 `0.1%` 改为带范围说明（如 `已下载 130 / 收录 146,824`，鼠标悬浮解释分母）。
- 目标档位建议固定为三档（避免页内可调导致的"数字随设置变"）：**全库 / 互动≥10 / 全站互动 Top500**。理由：覆盖"全部在想什么"到"值得收的高价值部分"，且三档分母都可由一次 SQL 得出。
- 落点：`web/api.py` 的 `stats_assets` 增 `coverage: {all, engaged, top500}`（复用同一次已下载集合，禁止新写第二份判重）；前端 `DashboardView.vue` 漏斗下方一行小字。
- 工作量：小。风险：低（只增字段）。

**C2 修正长标题失配（D5，真 bug，建议最先做）**

- 根因：目录名 = `sanitize_title(title)`（截断 80 字符），而履历恢复判据是「目录名 = posts.title」全等 —— 两条规则不一致，长标题必失配。
- 修法：履历的磁盘恢复改为「目录名 = `sanitize_title(库内标题)`」比对（**复用同一个函数**，禁止再写一份截断逻辑）；`resources.source_lookup(exact_only=True)` 的匹配同样以 `sanitize_title` 归一后再比。
- 预期效果：`downloaded_posts` 130 → 132（本次实测的 2 条被认领）；待下载推荐不再重复推荐这 2 条。
- 落点：`web/download_tasks.py`（启动恢复）、`web/resources.py`（`source_lookup`）。注意：`sanitize_title` 在 `extract_torrents.py`（抓取侧），Web 复用它是既有的跨端复用模式（与 `txxy_env` 同类），不引入新依赖。
- 工作量：小。验证：重启后 `/api/stats/assets` 的 `downloaded_posts` 应等于磁盘目录数（当前应为 132）。

**C3 缺口与在途上卡（D2）**

- 做法：漏斗下方增加一行**状态摘要**（不占大面积，单行 + 悬浮明细）：
  `已落盘 130 · 在途 N · 失败 N · 可重下 N · 空壳 N · 近30日未沉淀高互动 M`
- 数据来源（全部已有，零新增扫描）：在途/失败取 `download_tasks` 任务明细状态；可重下取 `manager.gone_urls()`；空壳取 `resources.scan()` 中 `file_count == 0` 的目录数；未沉淀高互动取 `_download_path_sets()` 与 `posts_filtered` 的差集（待下载推荐已在做同一件事，抽为公用函数，避免两份）。
- 工作量：小-中（后端 1 个聚合 + 前端一行）。风险：任务面板被清理后失败数会归零（见 C6/D9），需在文案上说明口径是"现存任务内"。

**C4 下钻对称补齐（D7）**

- 做法：后端 `/posts` 增加 `downloaded=1` 参数（与 `_apply_undownloaded` 完全对称——同一套 `_download_path_sets()` 归一化 + `IN (...)` 分块，反向取交集），前端帖子页摘要条增加「已下载」筛选项；卡片「已下载帖」点击下钻 `/posts?downloaded=1`。
- SQL 注意：动态占位符一律显式构造（`+ ",".join("?" * n) +`），禁止依赖隐式字符串合并 + `.format()`（既有踩坑记录）。
- 工作量：小-中。验证：`downloaded=1` 的 total 应等于卡片的 `downloaded_posts`（当前 130 / 修 C2 后 132）——这是"数字自洽"的硬校验。

**C5 计数与字节分列（D3）**

- 做法：漏斗保留三级 `收录帖子 → 已下载帖 → 本地文件`；把「占用体积」从漏斗里摘出来，与「按类型占比」合并为独立的**存储条**：`占用 20.7 GB · 可用 39.0 GB · 视频占 95.7%`。
- 理由：符合 P4；同时解决"体积主导观感"问题（体积与文件数分列后，用户一眼看出"视频少而大"）。
- 工作量：小（纯前端布局调整 + 文案）。

### 4.2 P1：进度语义（需要一点后端改造）

**C6 履历加时间戳（D4 的前置，其他 P1 项的基础）**

- 做法：`outputs/download_history.json` 由 `url → "目录名"` 升维为 `url → {"dir": 目录名, "first_at": 首次落盘时间, "checked_at": 最近校验时间}`；启动时把历史字符串值一次性归一为新结构（`first_at` 置空表示"时间不可考"，**不做长期兼容分支**——归一之后代码只认新结构，符合项目"不写兼容层"约定）。
- 顺带落地 D9：在履历里记录每帖最近一次下载的**结果**（成功/失败各记一条计数或最近失败原因），让"失败清单"不再随任务清理而丢失。
- 风险：履历是纯状态文件，结构变更需与 `write_json_atomic` 原子写、`.bak` 轮转保持一致；启动归一属一次性数据修复，需实测（改前备份、改后核对条数不变：164 条）。
- 工作量：中。

**C7 资产增长曲线 + 停滞告警**

- 做法：C6 落地后，`/api/stats/assets` 增加 `growth`（近 N 日每日新增已沉淀帖数 / 新增字节）；前端在存储条旁放一条**迷你折线**（复用 `DashboardView` 既有 ECharts option 结构与网格线规范，不新建图表组件）。停滞判定并入既有采集健康条（`_health_verdict` 一处判定，禁止前端另定阈值）：如「近 14 日无新增资产」升 warn。
- 工作量：中。风险：`first_at` 为空的历史条目无法回填时间（如实标注"时间不可考"，不伪造）。

**C8 沉淀目标（SLO 式进度）**

- 做法：参数设置页新增「沉淀目标」项（落 `web/settings.py` 白名单）：目标范围档位（全库 / 互动≥N / TopN）+ 目标数量或比例。卡片改为 `进度条 + 当前/目标 + 剩余缺口`（Grafana stat-vs-target 形态）。
- 工作量：中。风险：设置项会改变卡片数字语义，需在卡头固定展示"当前目标口径"，避免"数字随设置变、却看不出变在哪"。

**C9 缺口清单（Wanted/Missing 视角）**

- 做法：把「待下载推荐」从"取 8 条"扩展为**可翻页的沉淀缺口清单**：按「未沉淀 + 互动量」排序，支持按版块分组看缺口 Top。与 R3 的建议**共用同一接口与同一判重口径**（不新开第二个推荐列表，避免重复造轮子）。
- 工作量：中。风险：与 R3 功能边界重叠，需明确"R3 是入口、C9 是全量清单"，同一接口不同形态。

## 六、落地约束（对齐项目既有约定）

1. **单一实现**：判重/归一化复用 `_download_path_sets()`；扫描复用 `resources.scan()`；类型占比复用 `buildTypeSegments()`；不得新增第二套目录遍历或第二套「已下载」判定。
2. **Web 不写库**：新增指标全部基于只读 SQL + 文件系统状态；履历结构变更走 `web/atomicfile.write_json_atomic()`（含 `.bak` 轮转）。
3. **接口规范**：新字段加在 `web/api.py` 并包 `db.cached()`（5s TTL）；前端同名方法加在 `src/api/index.ts`；错误统一 `HTTPException(detail)` + `ElMessage.error`。
4. **下钻继承口径**：卡片每个数字的下钻必须携带当前口径（分层档位、时间窗），落到明细页后条数与卡片数字严格一致（帖子页摘要条集中展示并支持逐项清除）。
5. **图表规范**：如需曲线，遵守 Y 轴横向网格线 `rgba(0,0,0,0.08)`、X 轴竖线隐藏、`axisPointer` 深色、`tooltip.appendToBody: true`、色板复用既有 `fidColor.ts` / `utils/category.ts`。
6. **不改语义即不改名**：`/api/stats/assets` 的既有字段（`posts_total` / `downloaded_posts` / `files` / `folders` / `size` / `type_breakdown`）保持含义不变，新语义一律新增字段（避免前端多处误用）。
7. **交付自检**：`python -m py_compile` + 服务重启 + 受影响接口真实请求无 500 + `npx vue-tsc --noEmit` 与 `read_lints` 双通道 0 错误 + 桌面 1440×900 与移动 390×844 双视口实测（窄屏漏斗换行、占比条不溢出）。
8. **文档同步**：落地后在《数据总览大屏设计与优化总览.md》追加章节，更新 `README.md` 对应页面描述与接口清单，本文标注「已实施 / 部分实施 / 作废」。

### 8.1 与原建议的偏离

1. **目标缺口不做下钻**（原建议未提）：目标档位按互动量取前 N 名，帖子页没有对应筛选条件，强行下钻必然口径不一致；故改为悬浮说明「该数字为何不可下钻」，可下钻的缺口统一走状态行的「近 N 日缺口」（口径可表达、与帖子页筛选严格一致）。与既有「行不可下钻」取舍同源。
2. **`by_fid` 不做独立图表**：按「不增加卡片面积」处理为一行摘要 + 悬浮，信息不丢、卡片不膨胀。
3. **空壳与未认领互斥计数**：未认领 = `磁盘目录 − 空壳 − 已认领`，避免空目录被两边重复计入。

### 8.2 顺手修掉的两处既有缺陷（不在原建议清单内）

| # | 缺陷 | 影响 | 修复 |
|---|---|---|---|
| 1 | 导出接口未声明 `author` / `adv` 入参，而前端一直在传 | FastAPI 静默忽略未声明的查询参数 → 「列表按作者筛过、导出的 CSV 却是全库」，无报错无提示 | `/posts/export` 与列表页逐项对齐（含新增 `downloaded`）；实测按作者导出 1,005 行 = 列表 total |
| 2 | `db.iter_query` 在生成器的 `finally` 里关闭连接，而 `StreamingResponse` 在线程池里迭代同一个生成器 | `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread` → 响应中途断流、CSV 被**静默截断**（客户端仍收到 200；实测全库导出只落 4 万余行） | `db.open_conn(cross_thread=True)` 专供流式场景（sqlite3 默认 serialized 模式，同一连接顺序跨线程使用安全），普通查询路径保持默认校验；实测全库导出 146,840 行 = 表行数 |

以上两条均为「按真实链路端到端实测」才暴露（只测接口是否存在、只测返回码 200 都会漏掉）。
