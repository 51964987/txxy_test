### 1.5 热门榜（4 栏，P1 懒加载）

数据来自 `/stats/boards`（点赞/回复最高帖）+ `/stats/today_top`（最新最热：最新数据日期内点赞+回复综合 Top）+ `/stats/month_top`（本月最热：最新数据月份内综合 Top）。原「今日新增版块 / 今日热议帖」两栏已于 2026-08-28 替换为「最新最热 / 本月最热」。

交互规则（2026-08-26 调整，2026-08-28 增补）：
- **点赞最高帖 / 回复最高帖**：标题点击 → `window.open` 原帖 URL（新标签）；卡片空白区点击 → 下钻该版块（`/posts?fid=&sort=likes_desc|replies_desc`）；「查看更多」→ 带排序下钻帖子浏览（`/posts?sort=likes_desc` / `/posts?sort=replies_desc`）。
- **最新最热 / 本月最热**（2026-09-01 补下钻与口径展示，同日追加 P1/P2）：标题点击打开原帖 URL；**卡片空白区点击 → 下钻「该版块 + 该时间窗」**；「查看更多」→ 下钻整个时间窗（最新最热=最新数据日当天，本月最热=最新数据月份的月初~月末），排序随卡头切换联动（`engagement/likes/replies/hot` → `engagement_desc/likes_desc/replies_desc/hot_desc`）。卡头新增**排序维度切换**：综合 / 点赞 / 回复 / 热度（时间衰减，HN 式 `(score-1)/(age+2)^1.8`，解决老帖靠累计量霸榜），切换只重拉对应榜单。每行主指标显示**互动量**（点赞+回复，排序依据显性化），tooltip 附**互动率**（回复/点赞）与类型（围观型 / 均衡型 / 热议型），回复数≥点赞数时行内显示「热议」小标。本月最热额外显示发布日、卡头 sparkline（本月每日互动量）、**NEW 新入榜标记**（对比快照，仅首次进入 Top10 的当天标 NEW、跨天自动消失，口径修正见第十六节）；最新最热不显示发布日（各行同一天、无信息量），也不做 NEW（每日窗口整体更替，会全量刷成 NEW 而失去意义）。四栏版块 tag 统一为中性色，避免颜色竞争。
- **每行悬浮「下载」按钮**：直接 `POST /api/downloads` 创建下载任务（`@click.stop.prevent` 阻断卡片跳转），进度在下载中心查看。

### 1.6 活跃作者 Top10 / 活跃版块 Top10（2026-08-28 上线，2026-09-01 加口径与环比）

- 左右 1:1 横向条形图，P0 随首屏加载（`/stats/top_authors`、`/stats/top_fids`）。
- 作者条点击 → 帖子浏览按作者精确过滤（`/posts?author=`）；版块条点击 → 跳该版块列表；颜色：作者多色区分，版块按 `FID_PALETTE` 确定性色板。
- **下钻继承统计口径**（2026-09-01）：下钻时按当前口径附带 `date_from` / `date_to`（`all` 口径不传，即看全部），使榜单数字与帖子页结果自洽——在「近 7 日」榜上看到 431 条，点进去就是这 431 条，而不是该作者全部的 4314 条。帖子页顶部「当前条件」摘要条展示全部生效条件，可逐项清除或清空全部。
- **统计口径可切换**（2026-09-01）：卡片右上角 `累计 / 近 7 日 / 近 30 日` 分段控件，两卡独立记忆，切换只重新拉取对应榜单，不整页刷新。

| 口径 | 排序与主值 | 候选范围 |
|---|---|---|
| 累计（默认） | `total` | 全部 |
| 近 7 日 | `week` | 仅近 7 日有发帖（`HAVING week_c > 0`） |
| 近 30 日 | `month` | 仅近 30 日有发帖（`HAVING month_c > 0`） |

> 非累计口径必须加 `HAVING` 过滤，否则榜单会被大量 0 值占满，切换后看起来毫无变化。
> 口径切换确实会改变排名：实测累计第 2 名的作者近 7 日只有 234 条，被 431 条的作者反超。

- **环比展示**（2026-09-01）：近 7 日 vs 前 7 日（第 8~14 天）的涨跌百分比，`delta` 字段：
  - 条尾随主值一并展示，涨绿 `↑x%` / 跌红 `↓x%` / 持平灰 `持平`；
  - 前 7 日为 0 时无计算基准，`delta=null`，按橙色「新增」展示。
- **文案统一**：两卡副标题同构 —— `按<口径>发帖量 · 点击查看该<作者|版块>帖子`。
- **空态**：某口径下无数据时显示「该时间段暂无数据」，不再是空白区。
- **实现要点**：图表复用「数据指纹跳过重绘」机制，指纹已纳入口径（`name:value:valueLabel`），否则切换口径后数值未变时图表不会刷新。

## 二、API 接口与后端支持

| 接口 | 路径 | 优先级 | 说明 |
|---|---|---|---|
| 应用配置 | `GET /api/config` | - | 自动刷新开关 |
| 数据总览 | `GET /api/stats/overview` | P0 | 累计/今日/昨日/近7日 + 用户五值（`total_users` 累计去重 / `active_users` 今日活跃 / `yesterday_users` 昨日活跃 / `new_authors_7d` 近 7 个完整日新增 / `new_authors_30d` 近 30 个完整日新增）+ `latest_run_at`（入库活动时间，新鲜度依据） |
| 趋势 | `GET /api/stats/trend?days=N` | P0 | 每日发布趋势（7/14/21/28 天，联动各版块 `trend_by_fid`） |
| 版块分布 | `GET /api/stats/fid_dist` | P0 | KPI 副指标「覆盖 N 个版块」（版块分布图已移除，接口保留） |
| 活跃作者榜 | `GET /api/stats/top_authors?limit=10&range=all` | P0 | `range=all\|7d\|30d` 切换统计口径（非法值 422）；返回 `total/today/week/month/prev_week/delta/value`，`value` 为当前口径主值 |
| 活跃版块榜 | `GET /api/stats/top_fids?limit=10&range=all` | P0 | 与作者榜同构（`range` 语义相同） |
| 热门榜 | `GET /api/stats/boards` | P1 | 各版块点赞/回复最高帖 |
| 最新最热 | `GET /api/stats/today_top?limit=10&sort=engagement` | P1 | `sort=engagement\|likes\|replies\|hot`；返回 `total`（当日帖数）/ `days`（=1）供卡头说明样本规模 |
| 本月最热 | `GET /api/stats/month_top?limit=10&sort=engagement` | P1 | `sort` 同上；额外返回 `daily`（每日互动量，sparkline）与 `is_new`（新入榜，对比快照） |
| 运行记录 | `GET /api/runs` | - | 「抓取中」徽标实时进度（B1） |
| 最近帖子 | `GET /api/stats/recent?limit=N` | - | 最新帖子列表（前端当前未使用，接口保留） |

> 历史更名：`today_top_fids` → `today_fids`、`rising` → `today_top`（旧文档中的接口名，现均已按右列名称提供）；`today_fids` 与 `recent` 前端当前未使用，接口保留。

- **数据库**：SQLite（WAL），`db/posts.db`；统计接口统一 `db.cached()` 5s TTL。
- **性能优化**：`_board_top` 改 per-fid `ORDER BY ... LIMIT 1` 命中表达式索引；新增 `idx_posts_likes_expr` / `idx_posts_replies_expr` / `idx_posts_author` / `idx_posts_created_at`；P1 懒加载减少首屏压力。

## 三、加载与刷新

- **P0**：`Promise.all([overview, trend, fidDist, topAuthors, topFids])` 并行；渲染后启动趋势 Tooltip 轮播；「分版块发布对比」滚动进入视口后懒加载 `trend_by_fid`。
- **P1**：`IntersectionObserver`（rootMargin 200px）进入视口才 `loadBoards()`（`boards` + `today_top` + `month_top` 并行）。
- **自动刷新**：默认 5s（`REFRESH_INTERVAL=5000`），由 `useDashboardStore` 管理；仅静默刷新已加载区块，不显示遮罩。
- **骨架屏**：P0 时 KPI/图表骨架占位；P1 时热门榜骨架。

## 十一、2026-09-01 活跃榜口径与环比（已落地）

## 十四、全屏时是否「自动播放」大屏 — 调研（待确认）

> 调研日期：2026-09-09。结论先放：**不建议在「点击全屏」时自动开启轮播/播放**，但需厘清「自动播放」的两种含义，避免讨论错位。

### 14.1 问题界定

「点击全屏按钮自动播放」在业界有歧义，通常分两层：

- **A. 数据自动刷新（实时性）**：全屏后数据持续/定时拉取，反映最新状态。这是「自动播放」的基础层，几乎所有大屏产品的默认行为。
- **B. 视图自动轮播（演示性）**：全屏后自动在多个视图/页面/维度间切换播放（kiosk 投屏场景），如定时翻页、轮播区块、多 Dashboard 轮换。

两层要分开判断，结论不同。

### 14.2 业界做法汇总

| 产品 / 来源 | 全屏 / kiosk | 自动播放形态 | 退出方式 |
|---|---|---|---|
| **Grafana**（官方文档 `grafana.com/docs`：kiosk mode / TV mode / Playlists） | kiosk/TV mode 隐藏导航栏、工具栏，进入纯净大屏 | **Playlists**：多个 Dashboard 按设定时间间隔自动轮播；数据本身有 auto-refresh | 按 `Esc` 退出；可手动停止轮播 |
| **阿里 DataV** | 大屏全屏展示 | 时间轴组件实现**大屏多页面自动轮播**，轮播联动更新图表数据 | 交互/脚本控制 |
| **帆软 FineReport** | 大屏展示 | 「轮播自动联动播放的大屏实例」、自动翻页、自动播放 | 交互控制 |
| **通用（Chrome 插件 / URL 轮播）** | 浏览器 F11 全屏 | 多个可视化页面 URL 动态轮播（解决多页面连续播放） | 插件控制 |
| **简书 / 可视化博客** | 大屏分屏 | 多分屏（两分/四分/六分/九分）并排展示 + 自动播放 | — |

**共性结论**：
1. 数据自动刷新（A 层）是默认必做项，与是否全屏无关。
2. 视图轮播（B 层）**几乎只服务于「大屏投屏 / 展厅 / 监控墙」这类无人值守、需要持续吸引注意力的场景**。

### 14.3 本项目现状（已核对代码）

- **全屏按钮**：`AppLayout.vue` 的「进入大屏」按钮 → `app.toggleFullscreen(bodyEl())`，全屏目标是右侧内容区（Header + Main），侧栏自动隐藏，但 **Header 的实时时钟与自动刷新开关保留**（`useAppStore` 的 `fullscreen` 状态管理，含真全屏 + iOS 降级伪全屏）。
- **全屏按钮本身不含任何轮播/播放触发逻辑**，仅切换显示态。
- **A 层（数据刷新）已有**：自动刷新默认开启（`config.ENABLE_AUTO_REFRESH=1`，`REFRESH_INTERVAL=5000`），由 `useDashboardStore` 管理，全屏后数据持续刷新——即「自动播放」的基础层本就满足。
- **页面内已有轮播**：趋势图维度轮播 `TREND_DAYS_SEQ=[7,14,21,28]`，悬停暂停（见 1.2 节），属于单图内部维度切换，非整屏轮播。

### 14.4 分析与建议

1. **A 层（数据自动刷新）—— 无需改动**
   业界的「自动播放」基础层在本项目已默认满足。不应把「刷新」与「全屏」重新绑定成新逻辑（刷新本来就开着，绑定反而制造隐含耦合）。结论：**全屏按钮对数据刷新层保持现状即可**。

2. **B 层（多视图/多页轮播）—— 不建议绑定全屏**
   - 业界 B 层专为「无人值守投屏」设计；本项目定位是**单人自用、本机运行**（见项目指引），用户点全屏多是为了「看清大屏 / 专注查看」，不是把屏幕丢给展厅轮播。
   - 自动轮播会**打断阅读与交互**：悬停看 tooltip、下钻明细、点排序维度等都与「自动翻动」天然冲突。
   - 当前大屏是**单页**（无第二个 Dashboard / 第二屏可轮播），强行做「区块轮播」收益低、且会打乱用户正在看的模块。
   - 结论：**不建议在点击全屏时自动开启轮播。**

3. **若确有「投屏演示」需求 —— 做成独立开关，而非绑定全屏**
   遵循项目「不隐藏行为、不盲目折中」原则：「全屏」语义应保持纯粹（仅放大显示）。可另设一个**「演示 / 轮播模式」独立开关**（可配置轮播区块序列与时长，悬停或 `Esc` 暂停/退出），与全屏解耦。这样「全屏 = 放大查看」「轮播 = 演示播放」各司其职，互不污染。
   - 备选轮播序列可复用现有模块：KPI 卡 → 趋势双图 → 活跃作者/版块榜 → 热门四栏，定时焦点切换或整屏滚动。
   - 轮播必须始终**可暂停**（悬停或按键），否则与下钻/tooltip 冲突。

4. **页面内轮播可增强，但需克制**
   现有趋势维度轮播全屏时可考虑加大视觉权重（放大节奏、强调当前焦点），但不应抢占注意力，且**悬停暂停必须保留**。

### 14.5 决策待确认

| 决策点 | 倾向建议 | 理由 |
|---|---|---|
| 全屏时自动开启数据刷新 | 保持现状（已默认开） | A 层已满足，无需新增逻辑 |
| 全屏时自动开启视图轮播 | **不做** | 单人自用，轮播打断查看，单页无可轮播内容 |
| 新增独立「演示/轮播模式」开关 | 待你确认是否要做 | 仅当确有投屏演示需求才值得做，且与全屏解耦 |

**一句话结论**：点击全屏按钮时，**不要自动播放（轮播）**；数据刷新本就自动进行，全屏只做「放大显示」。若需要投屏轮播，应作为独立功能单独评估，而非挂到全屏按钮上。

## 十五、投屏轮播（演示模式）独立功能 — 方案评估

> 评估日期：2026-09-09。依据第十四节结论，把「投屏轮播」从全屏按钮解耦，作为**独立「演示模式」开关**单独设计。

### 15.1 功能定位

- **独立开关，不与「全屏」耦合**：可单独开演示轮播，也可「演示模式 + 全屏」叠加（投屏场景先开轮播再放大屏幕）。
- **只控制「视图焦点/滚动」，不控制数据**：数据刷新仍由各区块自身的自动刷新（5s）负责，轮播不重拉数据、不重绘图表。
- **纯展示增强，单人自用下的「投屏/展厅」场景**：把大屏自动在若干视图间轮换，无需人值守盯屏。

### 15.2 触发入口

- Header 新增一个「演示轮播」按钮（图标复用已注册的 `VideoPlay`），与现有「全屏」按钮并列（`AppLayout.vue` 的 Header 右侧）。
- 点击 → 进入演示模式；再次点击 / `Esc` / 顶部控制条「退出」→ 退出。
- 进入演示模式**不**自动全屏；若用户想投屏，再点全屏即可（两者叠加）。

### 15.3 轮播内容（复用现有区块，不新增页面）

按视觉顺序把大屏切成若干「视图锚点」，轮播在这几个锚点间平滑滚动：

| 序号 | 锚点 | 对应区块（现有） |
|---|---|---|
| ① | 总览首屏 | KPI 卡 + 每日趋势双图 + 活跃作者/版块榜（P0） |
| ② | 点赞/回复最高帖 | 热门榜前两栏（`/stats/boards`） |
| ③ | 最新最热 | 热门榜第三栏（`/stats/today_top`） |
| ④ | 本月最热 | 热门榜第四栏（`/stats/month_top`） |

> 锚点粒度可粗可细：默认按「① 首屏 + ②~④ 热门四栏」4 个；若需要也可把 ① 拆成「KPI+趋势」「活跃榜」两块。序列顺序可后续做配置，初版用固定顺序循环（④ 之后回到 ①）。
>
> **实现说明（2026-09-09 已落地）**：实际锚点落地为 **4 个**——`section-overview`（总览首屏/KPI）、`section-trend`（每日发布趋势 + 分版块趋势）、`section-ranks`（活跃作者 / 活跃 fid 榜）、`section-boards`（热门榜整体）。轮播间隔与板块序列已下沉为「参数设置」页可配置项（`carousel_interval` 秒 / `carousel_sections` 数组），默认 8 秒、四板块按序全选；前端进入轮播时从 `/api/config` 读取一次，运行中不变。原 `CAROUSEL_SECTIONS` 常量改为运行时数组，配置缺失/全空时回落默认，不会空转或崩溃。

### 15.4 轮播节奏与暂停/退出

- **默认间隔**：`CAROUSEL_INTERVAL = 8000ms` 切下一块（待确认，建议 6~10s 可调）。
- **进入时**：先主动 `loadBoards()` 预加载 P1（否则轮播到 ②③④ 时仍是骨架，见 15.7 边界 ④）；首屏停留 1 个间隔后再开始滚动。
- **悬停暂停**（与现有趋势轮播 `trendTipPaused` 同范式）：鼠标进入当前视图区块 → `carouselPaused = true`，停止切下一块、保留当前位置；移出 → 恢复。保证用户想看 tooltip / 下钻时不被强制滚走。
- **顶部极简控制条**（仅演示模式显示，几秒无操作自动隐藏）：播放/暂停、上一块/下一块、退出。
- **`Esc` 优先级**：演示模式激活时 `Esc` 先退出演示模式；若同时处于全屏，再由现有 `fullscreenchange` 同步退出全屏（需确认交互细节，见 15.7 ⑤）。
- **页面隐藏**：复用现有 `pageVisible` 框架——`stopAllTimers()` 一并清 `carouselTimer`，`resumeAllTimers()` 重启（后台标签不空转轮播）。

### 15.5 状态管理落点（不新建分散 store）

- 轮播**激活态**放进 `useDashboardStore`（与 `autoRefresh` / `nowText` 同层，符合「跨页状态归并全局 store、禁新建分散 store」约束），新增：
  - `const carouselActive = ref(false)`、`const carouselPaused = ref(false)`
  - `setCarousel(active: boolean)` / `setCarouselPaused(p: boolean)`
- 轮播**执行逻辑（timer、滚动）**留在 `DashboardView.vue` 本地（与趋势轮播的本地 `trendTipTimer` 同层），`watch(carouselActive)` 启停；通过现有 `rootRef` 与各区块 ref 做 `scrollIntoView`。
  - 不沿用 `registerAutoChange`（那是 autoRefresh 专用回调），DashboardView 直接 `watch` store 的 `carouselActive`/`carouselPaused` 即可，职责更清晰。

### 15.6 技术实现要点（落到代码，初版）

1. **锚点标记**：给 4 个区块容器加 `id`（或 `ref`）：`section-overview` / `section-board-like` / `section-board-today` / `section-board-month`。P0 区块已有 `rootRef`，P1 热门榜各栏在模板中已有对应包裹元素，仅需补 `id`。
2. **滚动**：`document.getElementById(id)?.scrollIntoView({ behavior: 'smooth', block: 'start' })`，滚动容器即 `rootRef` 所在内容区（全屏时仍是该元素，原生滚动正常）。
3. **timer**：`carouselTimer = setInterval(nextSlide, CAROUSEL_INTERVAL)`；`nextSlide` 计算下一锚点并滚动；循环到末尾回 ①。
4. **与自动刷新协同**：刷新只静默更新已加载区块、不重置滚动位置（现有 `loadP0`/`loadTrendOnly` 行为不变），轮播滚动不被刷新打断。
5. **复用清单（不重复造轮子）**：
   - 滚动用原生 `scrollIntoView`，不引第三方库；
   - 暂停框架复用 `pageVisible` + `stopAllTimers`/`resumeAllTimers`；
   - 悬停暂停复用「方法包装规避 ts-plugin 类型收窄」范式（见 1.x 的 `setTrendTipPaused`）；
   - 状态复用 `useDashboardStore`，不新建 store；
   - 区块 ref 复用 `rootRef`、现有 P1 容器，仅补少量 `id`。

### 15.7 风险与边界

| # | 风险 | 应对 |
|---|---|---|
| ① | 轮播滚动与用户下钻/看 tooltip 冲突 | 悬停即暂停（15.4）；暂停时保留当前位置，不强制滚动 |

| ⑤ | `Esc` 与全屏退出冲突 | 明确优先级：演示模式先退轮播，再交全屏退出；统一在 `fullscreenchange`/`keydown` 处理 |

| ⑦ | 退出演示模式后滚动位置残留 | 退出时 `scrollTo({top:0})` 复位到首屏 |

## 十六、新入榜口径修正 + 热门榜窄屏板块 tag 处理（2026-09-10）

### 16.1 新入榜 NEW 标记条件取反（bug 修复，已落地）

**问题（用户反馈）**：「本月最热」卡片中，9/1 首次入榜的帖到 9/10 仍显示「新入榜」NEW，口径不合理。

**根因（代码定位）**：`web/api.py` 的 `_mark_new_and_save` 标记集合取反：

```python
fresh = {u for u in urls if board.get(u) != today}  # 错误：first_seen != 今天 才标 NEW
```

文档与注释口径均为「`first_seen == 今天` → 新入榜、跨天自动消失」，但代码写成「不等于今天才标 NEW」，导致历史帖在入榜后每一天都被重复标 NEW，与「跨天自动消失」相悖——即用户观察到的「9/1 记录截止到现在还是新入榜」。

**修复**：改为基于「写入前的旧值」判定，使口径与文档一致——

- `prev is None` → 首次出现，记 `first_seen = 今天`，标 NEW；
- `prev == 今天` → 当天早些时候已入榜，保持 NEW 一整天（同一天内多次刷新不丢失）；
- `prev` 为更早日期 → 不标 NEW（跨天消失）。

快照仅保留「仍在榜」条目，避免文件无限膨胀；任何异常仍降级为「无新入榜」。

**实测（2026-09-10）**：

- 等价单测：直接调用真实 `_mark_new_and_save`，覆盖「首见 / 同日刷新 / 跨天消失 / 9/1 帖到 9/10 / 全新帖」五组断言，全部通过（`ALL_NEW_LOGIC_TESTS_PASSED`）；
- 真实接口：重启服务后 `GET /api/stats/month_top?limit=10&sort=engagement` 无 500；9/1 帖（技術討論區 2026-09-01）`is_new=False`，不再误标；当前 Top 帖因快照中早已在更早日期首次入榜，全部 `is_new=False`，符合修正后口径（全新帖标 NEW 的行为由单测覆盖证明）。

### 16.2 热门榜窄屏「板块」中文名处理（已落地）

**背景**：四个热门榜卡片（点赞/回复最高帖、最新最热、本月最热）每行含 名次徽章 + 板块 tag + 标题 + NEW/热议 + 发布日 + 下载 + 互动量，窄屏（单列 ≤1100px）下行内元素拥挤，板块 tag 挤压标题可读性。

**方案对比分析**：

- **直接隐藏**：行内最干净，但丢失板块信息；
- **纯 tooltip**：移动端触屏下 tooltip 需长按才触发，不可靠、不直观；
- **业界做法**（微博/知乎热榜、GitHub Trending 移动端）：保留一个紧凑分类小标，而非隐藏或纯 tooltip——分类信息以最小化形式常驻。

**决策**：窄屏（单列 ≤1100px）**隐藏行内板块 tag**，但把板块名并入标题 tooltip（`${name} · ${title}`，长按可看），且卡片空白区点击仍下钻该版块——既释放标题空间，又保证板块信息不丢失。桌面（>1100px，2 列/4 列）保持原中性色板块 tag 不变（项目既有「四栏版块 tag 统一中性色」设计）。这是「隐藏 + tooltip 兜底」的折中，最贴合本卡片行内元素多的现实与移动端可达性。

**改动**：`DashboardView.vue`——四个标题链接 `:title` 由 `item.title` 改为 `` `${item.name} · ${item.title}` ``；`.board-tag` 增加 `@media (max-width: 1100px) { display: none; }`。

**实测（2026-09-10）**：`npx vue-tsc --noEmit` 0 错误、`read_lints` 0 错误、`npm run build` 成功 dist 已更新；移动端设备模拟（≤1100px 单列）标题不再被板块 tag 挤压，长按标题可见「板块名 · 标题」，桌面端板块 tag 保持原样。

**边界说明**：若后续发现 4 列桌面（>1400px）下卡片同样因板块 tag 拥挤，可把隐藏断点扩展到该布局；本次按用户明确的「窄屏」范围处理，未过度扩散。

## 十八、四项口径修正：下载履历 / NEW 快照 / 分板块环比（2026-09-11 已落地）

### 18.1 下载履历（修复「清空任务后已下载帖归零 / 待下载推荐重复推荐」）

**根因**：`downloaded_urls()` 只从**任务列表**（download_tasks.json）取「历史成功且目录仍在」的 URL，而任务列表是易失的——手动「清空已完成」与自动轮转（保留 200 条）都会删记录；「已下载」却是持久事实（文件在磁盘）。实测：用户清空任务后 `downloaded_posts=0`（磁盘 3882 个文件仍在），待下载推荐全量重复。

**业界做法**：下载管理器普遍把「任务列表」（用户可清理）与「下载履历」（append-only 独立持久化）分开——浏览器下载历史、qBittorrent resume data 均如此；判「是否已下载」看履历而非任务面板。

**修复**（`web/config.py` + `web/download_tasks.py` + `web/resources.py`）：
1. 新增**下载履历** `outputs/download_history.json`（url → saved_dir，可用 `TXXY_DOWNLOAD_HISTORY_FILE` 覆盖；随 outputs/ 卷持久化，Docker 各端一致）：任务项完成 ok/skip 时立即记入，随每次任务保存一并原子落盘；
2. `_classify_urls_locked` 的 alive 集合改为「任务项 ∪ 履历」中目录仍在磁盘者（dup_check / downloaded_urls / active_urls 三处口径自动一致）——清空任务、自动轮转都不再丢失「已下载」事实；
3. **启动三步恢复**：读履历文件 → 从现存任务 ok/skip 条目播种（一次性迁移）→ 按「目录名 = 帖子标题」从 downloads/ 增量恢复（复用 `resources.source_lookup` 新增的 `exact_only` 参数，只接受标题全等的精确命中——模糊命中可能张冠李戴，误配会把未下载的帖子错误排除出推荐，宁可漏记不误记；同时覆盖不经任务队列的 CLI 直接下载，每次启动增量自愈）。

**实测**：恢复 156 条履历（磁盘 159 个非空目录中 156 个精确命中来源帖），`downloaded_posts` 从 0 恢复为 156，待下载推荐 8 条与履历零重叠。

### 18.2 NEW 快照口径（修复「9/1 的帖子到现在还是 NEW」第二处根因）

**根因**（与 16.1 修的取反 bug 不同源）：四种排序（综合/点赞/回复/热度）共用**同一个快照 key** `month_top`，而快照「仅保留当前榜条目」的清理逻辑在每次请求后把其它排序的记录整体抹掉——**切换排序维度时，当前排序的 Top10 全部按「首见」重记，切回来再重记一遍**，表现为老帖反复全量标 NEW。快照文件还残留历史实验的整数脏值 key。

**修复**（`web/api.py`）：
1. 快照 key 按排序维度分开：`month_top:{sort}`，切换排序互不覆盖；
2. **去掉「仅保留当前榜条目」的裁剪**：首见记录永久保留，掉榜再回榜不重复标 NEW（「首次进入该榜 Top10」语义严格成立）；文件增长量级为「历次进榜的 url 数」，极小；
3. 读取时**逐值净化**：非法日期值（整数残留等）迁移为「早已入榜」哨兵 `2000-01-01`（永不等于真实今天，不产生 NEW），合法日期值保留不误伤；旧单 key 的日期本身已被排序切换污染（不可考），整组归零并入默认排序 key，避免迁移当天全量刷 NEW。
4. 快照写盘补 **`.bak` 轮转**（与 `download_tasks.json` 对齐）：`write_json_atomic(_SNAP_FILE, snap, backup=True)`。整文件重写场景下，万一写盘中断 / 重启竞态，可回退上一版快照而非丢失——此前该文件缺轮转，是 `download_tasks.json` 之外唯一一处无 `.bak` 保护的 Web 状态文件。

**等价单测**（直接调用真实 `_mark_new_and_save`，隔离快照文件）：首见 / 同日刷新 / 跨天消失 / 排序隔离（三组） / 回榜不重标（回榜者排除、当日首见者保留） / 迁移（旧 key 清除、整数归零、合法日期不误伤）共 **12 项全过**。

### 18.3 链接黑名单（大屏各卡片口径统一过滤）

需求：能否加一个链接黑名单，针对大屏各个卡片口径过滤。结论：**可行，且天然保证口径一致**——黑名单作用在「数据底座」（`posts_filtered` 视图），各卡片口径（累计 / 近7日 / 近30日 / 滚动窗口）都建在其上，结构上不可能出现 A 卡算进、B 卡漏算。

- 支持三类：`url`（链接）/ `author`（作者）/ `fid`（版块），用 `type` 列区分；
- **仅作用于大屏看板**：`/api/stats/*` 全部改读 `posts_filtered` 视图；`/posts` 帖子浏览页、导出、下载中心仍读原 `posts` 表，不受影响（作用范围按需求限定为「仅大屏卡片」）；
- **浏览页「标记不剔除」（2026-09-18）**：`/posts` 列表在每条记录上额外返回 `blacklisted` 标记（沿用 `posts_filtered` 的 url/author/fid 三类判定，逻辑完全一致），前端「标题」列对有标记的行显示橙色「黑名单」标签，**仅标记、不改变返回集合**。这样从「今日发布」等 KPI 下钻进浏览页时，列表条数略多于看板数字的差异（被屏蔽帖仍列出但不计入）即可一眼解释，且保持「浏览页默认读原表、不受影响」的设计不变；
- **浏览页「仅看黑名单」勾选筛选（2026-09-18）**：筛选栏提供「仅看黑名单」复选框（业界常见做法，如 Gmail「has:」「筛选器」、Notion 数据库视图的 filter toggle），勾选后 `/posts` 在 WHERE 中并入与标记**完全相同**的 `_BLACKLISTED_EXPR`（`api.py` 内统一为单一常量，标记列与过滤条件共用，杜绝两套判定漂移），只返回命中三类黑名单任一的帖——**服务端过滤**，分页与总数随之正确（下钻「今日发布」共 544，勾选后仅剩被屏蔽的 2 条）。同一参数也作用于 `/posts/export`，保证导出与列表逐项同口径。复选框状态可经 `?blacklisted=1` 链接带入（与「未下载 / 已下载」下钻同构），并在「当前条件」条中以可清除标签呈现；
- `blacklist` 表与 `posts_filtered` 视图落在 `posts.db`，但仅 blacklist 模块持有**可写连接**，其余查询仍走只读连接（不破坏「web 只读」整体约束）；
- **配置入口统一在设置页「链接黑名单」区**（按类型增 / 删 / 备注）。看板卡片**不放置行内屏蔽按钮**——用户确认按钮不美观、且黑名单属低频配置，集中在设置页管理更清晰；
- **前端刷新机制**：点赞最高帖 / 回复最高帖 / 各版块最高等卡片（`boards`）设计上首次加载后不参与轮询刷新。`boards` 是 **Pinia 跨页面导航持久缓存**，原 `loadBoards` 以「`boards.value` 非空」早退，会导致「设置页改完黑名单、再切回看板」时仍显示旧榜单（含已屏蔽帖）。改为按 `blacklistVersion` 版本号判断：版本不变且不强制则早退（保留「不参与轮询刷新」），版本变化则**强制重拉全部卡片口径**（`loadBoards` 内部 + 今日/本月/待下载/总览），同时覆盖「看板正打开时改」（`watch` 监听 `bumpBlacklist`）与「切回看板时」两种场景，保证即时同步；
- **前端改动需重建**：`app.py` 托管的是构建产物 `web/frontend/dist`。改了 `.vue` 源文件必须 `npm run build` 重新构建，浏览器硬刷新（绕过本地缓存）才能加载新逻辑；仅改后端无需前端重建；
- **视图健壮性**：`posts.url` 库内存有「相对路径 /htm_data/...」与「带域名全称」两种形态，视图用 `substr(p.url, instr(p.url,'/htm_data/'))` 归一后再比较，规避「用户粘贴链接格式与库内不一致」导致黑名单静默失效；
- **入库去域名（与「域名不得写入数据库」铁律一致）**：`blacklist.add` 对 `url` 类型经 `config.to_storage_path` 归一为相对路径 `/htm_data/...` 再落库，避免把 `127.0.0.1:1024` 等环境相关镜像地址写进 DB（数据换环境后该黑名单会因域名对不上而静默失效）。`ensure_schema` 启动时还会把历史残留的「带域名完整链接」url 黑名单归一为相对路径。视图两侧均按 `substr(...,'/htm_data/')` 归一，故无论存相对还是带域名都能正确过滤，但入库统一相对路径更干净、可移植；
- **踩坑**：本机 SQLite 不支持 `CREATE OR REPLACE VIEW`（报 `near "OR": syntax error`），若用该语法建视图会静默失败、视图停留在旧定义（表现为「加了黑名单某卡片仍不过滤」）。改为「`DROP VIEW IF EXISTS` + `CREATE VIEW`」确保每次启动加载最新定义。

**业界参照**：社交平台 mute/block（X/Twitter Block、Reddit Block、YouTube「不感兴趣」）的「单点屏蔽 → 全局各处同步隐藏」范式；与 uBlock/AdBlock「单一过滤列表作用于所有页面」同一思路。

**全链路实测**：重启后连续切换 4 种排序再切回，engagement 榜 0 误标；hot 榜仅 1 条 NEW——经核实为 `[人间光影录]0909爱看看` 今天**首次进入 hot 榜**（不在迁移哨兵的历史条目中），属口径内合法 NEW。

## 十九、三项 UI 口径修复：环比统一 7 日 / 资产空态 / 单一滚动条（2026-09-11 已落地）

### 19.1 全站趋势环比统一为近 7 日

**问题**：全站趋势卡头显示「近 30 日环比」，而分板块对比卡 tooltip 每行、最活板块卡头的环比都是**近 7 日**——两张并排图一张看 30 天、一张看 7 天，并排阅读会困惑（用户原话「一个是近30日，一个是近7日」）。

### 19.2 内容资产卡空态

**问题**：任务 + 文件 + 履历全部清空后，资产漏斗显示「144,057 → 0 (0%) → 0 → 0 B」，技术正确但 UX 生硬。

**业界做法**：Chrome 下载页清空后显示「没有下载内容」空态；GitHub 空仓库给引导性空态。本项目已有独立「下载履历」（`download_history.json`），只清任务不影响（履历仍在，`downloaded_posts` 仍 >0）；仅当三者全清才触发真空间态。

**修复**（`DashboardView.vue`）：`downloaded_posts === 0 && files === 0 && folders === 0` 时渲染引导空态——图标 +「尚未下载任何内容」+ 说明 +「去资源管理 ›」入口，替代生硬「0 漏斗」；其余情况保持四级漏斗不变（已下载帖 >0 即正常展示，含「只清任务」这类履历仍在的场景）。

### 19.3 去除嵌套滚动条（仅保留 .main 一个滚动容器）

**问题**：页面出现两个纵向滚动条——`html/body` 默认可滚动 + `.main`（el-main）`overflow-y:auto`，形成嵌套滚动（用户标注「里面那个滚动条」需去除）。

### 20.1 修掉两个真实缺陷（本次最先动的地方）

**（1）长标题帖的目录失配（口径少计）**：目录名 = `extract_torrents.sanitize_title(标题)`（非法字符替换 + 截断 80 字符），而履历的磁盘恢复判据是「目录名 == 库内标题」全等 —— 长标题必失配。实测 2 个目录（库内标题 99 / 90 字，目录名被截到 80 字）长期未被认领。
修复：新增 `resources.match_dirs_to_posts()` 收敛「目录名 ↔ 帖子」判定口径（按 `sanitize_title(标题) == 目录名` 比对，流式全表扫描 + 命中即停，仅在确有未认领目录时调用），`download_tasks._load` 的磁盘恢复改为调用它；`source_lookup` 去掉已无调用方的 `exact_only` 参数并补充「展示用 vs 判定用」的口径说明。
**实测**：`downloaded_posts` 130 → **132**，`reconcile` 未认领 2 → **0**（132 目录 = 132 认领）。

**（2）CSV 导出被截断（举一反三发现的既有缺陷）**：从「资产卡已沉淀帖 → 帖子页 → 导出」链路实测时发现：导出 CSV 行数与列表 total 对不上（全库导出只落 4 万余行、按作者导出只有 161 行）。
根因：`db.iter_query` 在生成器 `finally` 里 `conn.close()`，而 FastAPI 的 `StreamingResponse` 会把同步生成器交给线程池迭代（`anyio.to_thread`），每次 `next()` 可能落在不同 worker 线程 → `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread`，响应中途断流、CSV 被静默截断（客户端仍收到 200）。
修复：`db.open_conn(cross_thread=True)` 供流式场景使用（`check_same_thread=False`，sqlite3 默认 serialized 模式，同一连接顺序跨线程使用安全），普通查询路径保持默认的线程亲和校验。
同时补齐导出接口缺失的入参：前端本来就在传 `author` / `adv`，但接口未声明这两个参数，**FastAPI 会静默忽略未声明的查询参数**——表现为「列表按作者筛过、导出的却是全库」，无报错无提示；现与列表页逐项对齐（含新增 `downloaded`）。
**实测**：全库导出 146,840 行 = `posts` 表行数；按作者 1,005 行 = 列表 total；`downloaded=1` 132 行 = 卡片数字；`undownloaded=1` 146,708 行；非法 `adv` 正确返回 400；服务日志无 ERROR / Traceback。

## 二十一、「本月最热」互动量图抽离 + 「今日未完整」口径（2026-09-13 已落地）

> 起因：用户提出「本月最热」卡内的互动量 sparkline 应抽成独立图表、卡片只做列表，并要求参考业界做法。
> 结论：**同意抽出**，落点为**趋势区第三张图**（全宽一行），窗口用**近 N 日滚动**（跟随「全站发布趋势」的天数）。

### 21.1 抽出的理由（实测量化，不是审美偏好）

| 项 | 实测 |
|---|---|
| 数据口径 | `month_top.daily` = `SUM(点赞+回复) GROUP BY date`，即**当月全站 14,717 帖**的每日互动量合计——与列表那 10 条帖子无关 |
| 渲染尺寸 | 卡宽 286 / 406px → 图区 **244×26px**（1920 下 364×26）、13 根柱、柱宽 16.6px、**无坐标轴无刻度** |
| 逐日数值 | 09-01 24983 · 09-04 25696 · … · 09-11 17897 · 09-12 12207 · **09-13 1215** |

三个硬伤：

1. **末日塌陷（会误导）**：9-13 是今天，帖子刚发、点赞未累积，1215 = 前一日 12207 的 **10%** → 柱高只剩 **1.2px**，视觉上近乎消失，会被读成「热度断崖」；
2. **不可读数**：26px 高承载 13 个点，相邻日差异（21.8 vs 22.6px）肉眼不可辨，只能逐柱 hover；
3. **同卡混装两个口径**：列表 = 当月 **Top10 帖**（单位：帖，值 1,391/1,306…），图 = 当月**全站所有帖**的每日互动量合计（单位：互动量，值 12k~26k）—— 卡片标题只声明了前者。

补充：全站**没有任何独立图表**承载互动量（趋势双图都是发帖量 = 供给侧），把最有决策价值的「需求侧」指标困在 26px 装饰高度里，等于降级。

### 21.2 业界做法（简）

| 产品 / 规范 | 做法 |
|---|---|
| GA4「Reports snapshot」 | 卡片 = **单指标**（数字 + 该指标自身迷你趋势）；主趋势是独立图 + 指标选择器；明细表独立 |
| YouTube Studio | 「概览」= 指标卡 + 独立「随时间变化」图（可切观看次数/时长）；「内容」页 Top 视频 = **纯列表不带图** |
| Grafana / Datadog | one panel, one question；sparkline 只承载该 stat 自身的时序 |
| Ant Design / Material | sparkline 定位为「紧凑、无坐标轴的单一指标走势」，需读数/对照时用完整图表 |
| 微博热搜 / B站热门 / 知乎热榜 / Steam·App Store 榜单 | 榜 = 纯列表（排名 + 热度值 + 变动）；趋势在独立图表 |

共性：**榜单 = 列表，趋势 = 图表**；卡内迷你图只能承载「卡自身那个指标」。本卡的迷你图是另一个口径（全站每日互动量）→ 不满足前提。

### 21.3 落点决策

| 方案 | 结论 |
|---|---|
| **B. 趋势区新增独立图（采用）** | 供给侧（发帖量）与需求侧（互动量）**同屏可对照**；**投屏/演示轮播下无需交互即可见**（切换器在无人操作的大屏上形同虚设——决定性理由）；可用完整坐标轴、DataZoom、规范标注 |
| A. 现有趋势卡加指标切换 | 像素零新增，但必须切换才能看，投屏场景无意义；备选 |

### 21.5 顺带修掉的两处既有缺陷

| # | 缺陷 | 影响 | 修复 |
|---|---|---|---|
| 1 | **`markLine` 组件从未注册**（`use([...])` 里没有 MarkLineComponent） | 分版块图「点总趋势某天 → 同天高亮」的垂直标线**自上线起从未渲染**（徽标会显示、图内无标线）；ECharts 按需引入模式下未注册组件被静默忽略 | 注册 `MarkLineComponent`；标线坐标与分版块横轴（完整日期）本就一致，注册后即可渲染 |

### 21.10 缩放选区联动补齐：全站发布趋势 ⟷ 每日互动量趋势（2026-09-13 同日追加）

**用户报告**：趋势天数输入 365 后出现横向滑动条；拖动全站趋势的滑动条，「分版块发布对比」有联动，但「每日互动量趋势」纹丝不动。

**诊断结论：不是 bug，而是这条联动边从未接线。**

- `buildDayLineOption()` 对 `points.length > 31` 的两张单指标图都注入 `dataZoom: [inside, slider]` —— 所以 **365 天下「全站」与「互动量」两张图都有滑动条**（用户只看到全站那条，因为互动量在下排右半宽卡里）。
- `trendChart.on('datazoom', () => applyTrendZoom())` 的监听**只挂在全站图上**；`applyTrendZoom()` 只做「写 `trendZoomRange` + `renderFidTrendChart()`」，而 `renderFidTrendChart()` 是**唯一**消费 `trendZoomRange` 的地方。
- `renderTrendEngChart()` 只读 `trendEng.value` 全量数据，既无 datazoom 监听、也不读 `trendZoomRange`；其函数头注释只声明「刻意不参与 **Tooltip 双向联动与自动轮播**」，**未提缩放** —— 即新图接入时漏接了这条边，而非有意排除。
- 实测（1920×1080，输入 365 天）：三条请求齐发（`trend?days=365&metric=posts` / `metric=engagement` / `trend_by_fid?days=365`）；在全站图上滚轮缩放后，分版块卡头出现「跟随趋势区间：09-30 ~ 08-27」，而互动量图 x 轴（09-14…09-06）与滑动条宽度前后**逐像素一致**；反向在互动量图上缩放则三图毫无变化 —— 该图是完全孤立的视窗。

**顺带发现并修复的第二个问题**：跨年徽标读起来像「起止倒序」。徽标只取 `trendZoomRange.start.slice(5)`（MM-DD），而 365 天窗口必然跨年（2025-09-30 ~ 2026-08-27），显示为「09-30 ~ 08-27」。

**改动（`web/frontend/src/views/DashboardView.vue`）**

1. `applyTrendZoom(source: 'trend' | 'eng' = 'trend')` 参数化：新增 `dayChart(key)` 统一取「图表实例 + 日期序列」，读哪张图的 `dataZoom[0]` 由参数决定；算出日期区间后，把选区 **`dispatchAction('dataZoom', {startValue, endValue})` 同步给另一张单指标图**（不带 `dataZoomIndex` = 同时作用于它的 inside 与 slider），**只移动视窗、不改数据** —— 比照分版块那样裁剪数据更干净：滑动条语义完整，用户可在任一张图上继续调。
2. 新增 `zoomSyncing` 防回声标志（与既有 `tipSyncing` 同思路）：`dispatchAction` 会**同步**触发目标图自己的 `datazoom` 事件，不挡住两张图会互相触发；`trendEngChart` 的监听由新标志 `trendEngZoomBound` 保证只注册一次，并在 `rebuildCharts()`（大屏/卡片全屏切换会 dispose 重建实例）里复位。
3. `clearTrendZoom()` 复位**两张**单指标图（原先只复位全站，会留下「徽标已清、互动量仍在旧区间」的不一致）；`onTrendDaysChange()` 改为直接复用 `clearTrendZoom()`。
4. 徽标文案抽成 `zoomRangeLabel` computed：同年 `MM-DD`，**跨年显示完整 `YYYY-MM-DD`**。
5. 显式记录**单向边界**：分版块图的缩放不回传（其选区语义是「在已裁剪数据里再看一段」，后端 `trend_by_fid` 只支持「最近 N 天」，回传会引入循环裁剪语义）——写进 `applyTrendZoom` 注释。

**改动一：缩放联动从「两张单指标图双向」扩到「三图双向」**

- 新增 `fidRenderedDates`（分版块**本次实际渲染**的日期，可能已被共享区间裁剪）+ `linkedChart(key)` 统一取三图的「实例 + 日期序列」。
- 分版块注册 `datazoom` 监听（与另两张同款），其选区索引经 `fidRenderedDates` 映射回真实日期后回传为共享区间，再分发给两张单指标图。
- **分版块作为来源时的「满区间」特判**：它的数据本身已被裁剪，滑动条只表示「在裁剪区间内再看一段」，故「选区覆盖其全部数据」不视为区间变更（否则每次裁剪后复位滑动条都会自我触发）。
- 每次裁剪重绘后把分版块自身滑动条复位为「裁剪区间的满宽」（索引区间在重绘后已失效），该 `dispatchAction` 同样被 `zoomSyncing` 挡回声。

**改动二：聚焦日联动补齐为三图双向（并修掉「接线了但点不中」）**

- 单指标图的标线由 `buildDayLineOption` 新增 `markDate` 支撑：`markLine.data` 变为数组（① 今日未完整橙虚线 ② 聚焦日蓝实线，逐项 `lineStyle`/`label` 覆盖；与末端同日时不重复画），互动量图据此次获得「参与联动」的能力。
- **修掉两个「接线了却点不中」的隐患**（这才是本次真正的坑）：
  1. 折线 markLine/series 的点击命中区只有 `lineStyle.width`（2px）——固定列上扫 14 次点击**仅命中 1 次**；
  2. 即便命中，`triggerLineEvent` 给出的 series 事件 **`dataIndex` 为 undefined**（`dataIndex` 是「点中符号」的语义，而本图 `showSymbol: false` 不渲染符号）→ 旧代码 `trend.value[undefined]` 必然落空（实测 15/15 全落空），**该功能自上线起从未可用**。

### 21.12 下载后列表更新：写操作 → 定向失效（2026-09-13 同日追加，源于用户上报）

**现象**：在「待下载推荐」点行内「下载」，列表不更新——刚提交的帖子仍停在推荐位上。

**业界做法（用户问「是否合理」）**：合理，且是通行做法，但要成对做两件事——**写成功后失效** + **只失效受这次写影响的查询**：

- React Query `invalidateQueries` / Apollo `refetchQueries` / SWR `mutate`：写成功后把「数据依赖本次写」的查询标记失效并重取，不依赖的不动（定向失效，不做全量重拉）。
- 队列 / 收件箱类列表（Gmail 归档、待办、推荐队列）另有「乐观更新」变体：本地先移除、后台再对账。本项目提交只是「入队」，该帖是否真离开推荐由后端状态决定，故取「写成功后重取」而非乐观移除（避免提交失败时列表与后端不一致）。
- 只在**写成功**后失效：被判重剔除、用户取消确认、请求失败时数据没有变化，刷新属无效请求 + 视觉抖动。

**排查后确认的两个真实缺口（两条都修，只修一条都没效果）**：

1. **后端**：`/stats/pending_downloads`、`/stats/assets`、`/stats/health` 都走 `db.cached` 的 5s TTL，但**所有改变下载 / 本地文件状态的写接口都没有失效统计缓存**——`resources.invalidate_cache()` 清的是 `resources.scan()` 自己的签名缓存，与 `db` 的统计缓存是两套。于是前端即使立刻重拉，拿到的仍是 5s 内的旧快照 → 表现即「点了下载，那条还在」。本环境 `enable_auto_refresh=false`（Header 无开关、无轮询），列表在修复前**永远不会**更新。
2. **前端**：`useDownloadSubmit.submitDownload` 创建成功后没有任何刷新动作。

**落地**：新增 `web/api.py:_invalidate_download_stats()`（失效 `pending_downloads_*` / `assets_*` / `health_*`），在 10 个写接口后调用——下载侧 `POST /downloads`、`/downloads/{tid}/cancel`、`/retry`、`/retry-url`、`/downloads/clear`、`DELETE /downloads/{tid}`；文件侧 `POST /resources/delete`、`/batch-delete`、`/restore`、`/purge`（与既有 runs 写操作的 `db.invalidate("runs")` 同一套「写后即失效」约定）。

**举一反三（用户追问「其它卡片是否也应当这样处理」）**：判据是「该卡的数据是不是这次写的函数」——

| 卡 / 列表 | 数据依赖下载状态？ | 处置 |
|---|---|---|
| 待下载推荐 | 是（提交 → 变「在途」即退出推荐；文件被清理 → 变「可重下」） | 提交成功后立即重拉 |
| 内容资产 | 是（在途 / 已沉淀 / 缺口 / 覆盖率随之变） | 同上（抽出 `loadAssets()`，不为一次点击重跑整个首屏十余个接口） |
| 榜单四卡（点赞最高帖 / 回复最高帖 / 最新最热 / 本月最热） | 否（按点赞 / 回复 / 互动排序，本就包含已下载帖） | **不刷新**：重拉只会得到相同数据，还会打断列表滚动位置与 NEW 标 |
| 帖子浏览页「未下载」筛选（由本卡下钻而来） | 是 | 提交成功后重刷当前页；本页被刷空时自动回退一页 |
| 下载中心页 | 自身即任务源 | 已有 SSE / 轮询，不动 |

**改动文件**：`web/api.py`；`web/frontend/src/composables/useDownloadSubmit.ts`（`submitDownload` 改为返回「是否真的创建了任务」）；`web/frontend/src/views/DashboardView.vue`（抽出 `loadAssets()` + 新增 `refreshDownloadDependent()`，`downloadUrl` 成功后调用）；`web/frontend/src/views/PostsView.vue`（新增 `downloadOne` / `reloadAfterDownload`）。

**实测（2026-09-13，重启后的运行服务）**：

- **接口级（真实 HTTP）**：提交推荐首位帖 → 立刻重取（距上次取数约 2s，**远早于 5s TTL，无失效必返回旧快照**），目标帖已从列表消失、资产卡「在途」0 → 1；随后取消任务 + 彻底删除该目录，再次重取：目标帖立即回归、在途回落 0（同时验证了 cancel 与 `/resources/batch-delete` 的失效）。
- **浏览器级（Playwright 真实点击）**：本环境 `enable_auto_refresh=false`（无轮询兜底，天然排除 5s 轮询干扰），点行内「下载」→ 确认框「仍要提交」→ 成功提示 t+0.53s → **列表在 t+0.76s 换榜**（榜首由「南方小土豆重返战场！…」变为「[原创]安排骚妻…」），浏览器控制台 0 错误。
- 测试残留已清理：测试任务取消并删除、验证期间下载产生的目录彻底删除、伪造 URL 的履历条目删除；复核后 177 条履历 / 19 个任务 / 已沉淀帖 142 / 失败 1 / 在途 0 / 对账未认领 0 / 空壳 0，推荐首位与状态均与验证前一致（本地目录 142 → 141、文件 3536 → 3531，即被清理的那条推荐帖的 5 个文件；该帖回到 `re_download`，随时可从推荐位重新下载）。
- 方法备注：`txxy_env.to_storage_path` 对**非本站域名**原样返回（不裁剪），故接口级测试必须用本站域名构造 URL 才能命中「在途」判重——用 `127.0.0.1:9` 之类的假 host 无法匹配，会误判成「修复无效」。

## 二十三、「发帖作者」卡沉淀「新作者」人数（2026-09-19 已实施）

> 来源：用户提问「参考下互联网，数据总览中的『发帖作者』KPI 卡片，是否可以沉淀出类似『新作者』的人数」。经三轮实测探针确认口径后落地，用户选定：**近 7 个完整日** / **不加产量门槛** / **方案 C 卡面承载**。

### 23.1 业界口径与本项目映射

- 业界（GitHub Insights 的 `new contributors`、Discourse 的 `new users`、GA 的 `new users`）统一定义为「**首次出现**」，差异只在时间基准（注册时间 vs 首次发帖时间）。本项目 `posts` 表无注册时间，唯一可用基准是 `MIN(date)`（帖子真实发布日），即「新作者 = 该作者在本库中最早的发帖日落在窗口内」。
- 与既有 R8（新晋作者榜：`MIN(date) >= 近30日` 且窗口内发帖 ≥ 3）同源；本次先落地**人数**（轻量形态），榜单仍待确认。

### 23.2 实测数据（本库 153,750 帖 / 3,691 作者）

### 23.3 三处口径边界（均已实测，决定数字怎么读）

1. **是「库内首次出现」，不是「站点新用户」**，失真方向为**高估**：`scraper.py` 的 `END_PAGE = 100` / `AUTO_DETECT_END_PAGE = False` 决定抓取有页数上限，老作者若早期帖落在范围外会被算成新面孔（本库历史已覆盖到 2006 年，故对近月窗口影响很小）。
2. **窗口取「近 N 个完整日」，不含今天**（约束 18）：今天抓取未覆盖全天，实测含今天的 7 日 = 65 人 vs 前 7 个完整日 = 72 人（被今天稀释约 10%）。SQL 条件为 `mn_d >= date(?, '-7 days') AND mn_d < ?`。
3. **不加产量门槛**（与业界 new contributors 一致）：本库 39.5% 的作者只发过 1 帖，近 30 日首现者中 53% 只有 1 帖——所以这个数字更接近「第一次出现的作者名」，不代表持续产出者；若要「新且高产」需加门槛（≥2 帖 99 人 / ≥3 帖 81 人）。此说明已写入 tooltip，避免用户误读。

## 二十五、内容资产「下载失败」下钻落点 + 两量纲区分（2026-09-19 已实施）

### 25.1 用户上报的问题

内容资产 KPI 卡片显示「下载失败 3」，点进去下钻到下载中心后：① 下载中心没有按「失败」状态筛选承接；② 下载中心「失败」的数字与卡上的 3 对不上。用户质疑口径不一致。

### 25.2 根因：两个「失败」是不同量纲，天然不等

| 量纲 | 来源 | 含义 | 是否随任务清空 / 轮转消失 |
|---|---|---|---|
| **失败缺口（帖 / 链接级）** | 下载履历 `_history` 中「最近一次失败、此后未成功」的条目（持久记录，见 §18.1） | 真正的、本地还缺的帖子数 | **不消失**——履历独立于任务列表，任务被 `clear` 或按 `TASK_MAX_KEEP` 轮转移除后依然存在 |
| **失败任务（任务级）** | 任务列表 `status == 'failed'` | 一个曾经失败的任务 | 会消失（清空 / 轮转） |

一个失败任务可含**多条**失败链接（如某任务 3 个链接全失败），于是「失败任务数」必然 ≤「失败链接数」，两者数字**永远不可能相同**，混在一处只会让用户以为其中一个算错了。此前下载中心统计卡叫「失败」、资产卡也叫「失败」，两个「失败」撞名是这次对不上的直接原因。

### 25.3 业界做法（参考）

- **Sonarr / Radarr（*arr 系列）**：`Wanted → Missing` 与 `Activity`（任务历史）**分栏承载**，Missing 是「缺失清单」、可逐条触发搜索，Activity 是「最近发生的事」；两者口径分离，清单数字不会去和任务历史数字对齐。
- **qBittorrent / Transmission**：`Errored` 是独立的条目集合（按种子），与「完成 / 做种 / 下载中」任务状态并列，可单独筛选与重试；不是把「错误」塞进任务总数里再让用户去减。
- **Grafana / Datadog 的 drill-down**：下钻落点必须与卡片**同口径**（点「错误率 3%」进去看到的就是 3 条错误，而不是另一套聚合），否则下钻失去意义。

结论：本项目的正确做法是「**分栏 + 同口径下钻**」——资产卡下钻到与卡上 N **同源同口径**的「失败缺口」清单（N 条对 N 个），而任务列表的「失败任务」保留但明确标注「按任务计数」，二者不再互相冒充。

### 25.4 方案落地

- **后端**：新增 `GET /api/downloads/failures`（缓存键 `download_failures_v1`，5s TTL；写操作经 `_invalidate_download_stats` → `db.invalidate("download_failures_")` 立即失效，键用 `startswith` 匹配 `download_failures_v1`，写后即失效成立）。其 `count` 直接来自 `_asset_snapshot()["failures"]`——**与资产卡 `state.failed` 同一份数据派生**，保证「卡上 N = 清单 N 条」；逐条输出（不去重），否则条数凭空少于卡面。

### 25.10 清单表格「版块并入标题列」+ 表头排序（2026-09-19，已实施）

用户要求：① 版块与标题合并为一列，表头命名「标题」；② 表头兼容排序，参考「帖子浏览」做法。

- **合并列**：两清单去掉独立「版块」列，改为与帖子浏览同款的 `.title-cell`（`.fid-chip` 标签前置 + `.title-link` 标题省略号）；窄屏卡片同步把版块标签并入「标题」行。当前列集合为「标题（含版块标签）/ 失败时间（或 首次下载时间）/ 操作」。
- **表头排序（参考帖子浏览做法）**：两 `<el-table>` 加 `@sort-change`，标题列与时间列用 `sortable="custom"`（原生三态箭头：升序 → 降序 → 取消）。区别在于**数据已在内存**（接口全量返回、前端分页），故排序在 `pagedXxx` computed 里对**全量过滤结果**排序后再切片——等价于帖子浏览「服务端排序」的效果，而非 el-table 本地排序（本地排序只作用于当前页，等于没排，与帖子浏览注释同一结论）。实现见 `sortItems()`：空值恒沉底（与「-」占位一致）、文本按 `localeCompare` 比较；排序变化回第 1 页（与筛选同口径）。
- **实测（真实服务 8088，Playwright 真实点击表头）**：失败缺口表头 `标题 / 失败时间 / 操作`、可重下表头 `标题 / 首次下载时间 / 操作`；首行标题单元格内含 `.fid-chip`（合并生效）；点标题表头 → 页面标题单调升序、再点 → 单调降序；可重下 656 条时**升序首行 = 全量最小标题、降序首行 = 全量最大标题**（证明排序作用于全量而非仅当前页）；console 错误 0；`vue-tsc --noEmit` 与生产构建均通过。
- 改动文件：`web/frontend/src/views/DownloadsView.vue`（新增 `failSort` / `reSort` / `sortItems` / `onFailSortChange` / `onReSortChange`，两表格列与两窄屏卡片结构相应调整）。
