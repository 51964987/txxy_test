# txxy 资源管理页面优化方案

> 状态：P0-1~P0-4 已实施（2026-08-26），P0-5 评估后不实施；P1/P2 待确认
> 适用范围：`web/frontend/src/views/ResourcesView.vue`（仅前端），后端 `/api/resources` 已具备增量缓存与限流，不在本次范围。
> 原则：不改变路由路径与 history 模式、Web 进程不写库、页面保持「只读展示」定位；每条建议独立，可单独确认、单独实施。
> 注：本页为独立功能模块文档，不与「数据总览大屏」文档合并；大屏相关汇总见 `数据总览大屏设计与优化总览.md`。

## 一、现状盘点（当前页面已具备的能力，避免重复建设）

- 统计卡片：资源目录数、文件总数、总大小三张卡，实时反映整体概览。
- 目录折叠列表：按文件夹分组展示，展开后显示文件清单；单次仅展开一个文件夹（`active` 互斥）。
- 大列表虚拟滚动：文件多的文件夹已改用 `el-table-v2`（P2-14 已落地），高度自适应（上限 420px）、宽度跟随容器（`ResizeObserver` 监听）。
- 文件元信息：类型 Tag（图片/视频/种子/文本/其他）、大小格式化、相对路径展示、修改时间（目录级）。
- 便捷操作：`复制目录名` / `复制路径`（`navigator.clipboard`）。
- 后端配套：`/api/resources` 有增量缓存（目录签名）与 60 次/分限流；前端已走统一 `request()`（10s 超时 + 去重 + 统一错误）。
- 空态：`downloads/` 无资源时展示 `el-empty`。

**当前交互能力相对薄弱**：纯「展开看 + 复制路径」只读浏览，无搜索、无筛选、无排序、无分页懒加载、无层级导航、无文件数/大数据的加载策略。

## 二、P0 建议（收益明显，推荐近期实施）

### P0-1 目录/文件搜索过滤（前端即时过滤）

**现状问题**
- 文件夹与文件数量较多时，只能逐个展开目视查找，无法按文件名快速定位。

**方案**
- 在统计卡与资源列表之间加一个 `el-input` 搜索框（`prefix-icon` 放大镜 + `clearable`），对当前展开文件夹的文件列表做**前端即时过滤**（大小写不敏感、`includes` 匹配 `name` / `rel_path`）。
- 搜索词非空时高亮命中的匹配片段（`name` 片段高亮，参考文件管理器通用交互）。
- 因单文件夹文件量已受虚拟滚动约束，前端过滤足以覆盖，**无需后端搜索接口**。

**涉及文件**：`web/frontend/src/views/ResourcesView.vue`、`web/frontend/src/main.ts`（如需新增 `Search` 图标，须在按需注册列表中加入）
**收益**：大文件夹内秒级定位文件；实现成本低（纯前端 `computed` 过滤）。**风险**：低。

**落地说明（2026-08-26）**：新增 `keyword` 搜索词，`filteredFiles` 对当前展开文件夹做类型筛选 + 关键词过滤（匹配 `name` / `rel_path`，大小写不敏感）；文件名命中片段用 `<mark>` 高亮（文本先 HTML 转义再替换，避免特殊字符破坏渲染）。`main.ts` 已注册 `Search` 图标。

### P0-2 文件类型筛选（分类 Tab / Tag 过滤）

**现状问题**
- 文件类型仅在行内以 Tag 展示，无法按「只看视频 / 只看种子」等维度快速聚焦。

**方案**
- 在列表表头上方加 `el-segmented` 或 `el-radio-group`（全部 / 图片 / 视频 / 种子 / 文本 / 其他），与搜索框并列；筛选对当前展开文件夹的文件列表生效，实时重算。
- 选中类型后，将虚拟滚动数据源替换为过滤结果；空结果展示轻量 `el-empty`（小尺寸）。

**涉及文件**：`web/frontend/src/views/ResourcesView.vue`
**收益**：按类型聚焦大文件夹，浏览效率显著提升。**风险**：低（复用现有列定义与虚拟滚动）。

**落地说明（2026-08-26）**：新增 `typeFilter`（`el-segmented`：全部/图片/视频/种子/文本/其他），与搜索共用 `filteredFiles` 过滤链路；过滤后无匹配时展示小尺寸 `el-empty`。

### P0-3 文件列表排序能力（名称 / 大小 / 类型）

**现状问题**
- 文件顺序固定为后端返回的路径字典序，无法按大小、类型等重排。

**方案**
- 给 `el-table-v2` 列头（文件名 / 大小 / 类型）加 `sortable` 排序（前端 `computed` 对过滤后的数据排序）；排序状态用 `ref` 保存。
- 注意 `el-table-v2` 的 `sortable` 需通过列配置与事件实现，若与虚拟滚动耦合较麻烦，可用表头外的 `el-dropdown` 排序切换作为降级方案。

**涉及文件**：`web/frontend/src/views/ResourcesView.vue`
**收益**：大文件夹按大小/类型排序，便于清理大文件。**风险**：中（需验证 `el-table-v2` 排序事件，可退化为下拉切换）。

**落地说明（2026-08-26）**：文件名/类型/大小三列配置 `sortable: true`，绑定 `:sort-state` 与 `@column-sort`，`filteredFiles` 内按排序键做前端排序（大小按数值，其余按 `localeCompare`）；采用 `el-table-v2` 原生表头排序，未退化为下拉。

### P0-4 加载失败重试与刷新按钮

**现状问题**
- `load()` 失败仅 `ElMessage.error`，页面停留空态，用户需手动刷新整个浏览器页面才能重试；无手动刷新入口。

**方案**
- 在统计卡右侧加「刷新」`el-button`（`icon="Refresh"`，`loading` 状态复用 `loading`），点击重走 `load()`。
- 失败时在统计卡下方保留一个 `el-result` / 内联错误块 + 「重试」按钮，替代仅弹一条 error 后空白的体验。

**涉及文件**：`web/frontend/src/views/ResourcesView.vue`、`web/frontend/src/main.ts`（如需新增 `Refresh` 图标，须在按需注册列表中加入）
**收益**：弱网/瞬时失败可自助恢复，不依赖整页刷新。**风险**：低。

**落地说明（2026-08-26）**：统计卡第 4 格加入「刷新」按钮（`Refresh` 图标，`loading` 复用加载态）；`load()` 失败时设置 `loadError`，展示 `el-result`（错误信息 + 「重试」按钮）；`main.ts` 已注册 `Refresh` 图标。

### P0-5 大数据文件夹渐进加载（可选，视文件量）

**现状问题**
- `/api/resources` 一次返回全部文件清单；若某文件夹文件数达数万，JSON 体积大、首屏解析耗时，且列表 420px 高度内需先拿到全量数据。

**方案**
- 若实测某文件夹文件数超阈值（如 > 5000），改为「展开时按需加载」：后端新增 `/api/resources/{folder}?offset&limit` 分页接口，前端展开时按需拉取并配合虚拟滚动滚动加载。
- 若文件量在可接受范围（当前场景），本项可不做，仅作为容量水位预案。

**涉及文件**：`web/frontend/src/views/ResourcesView.vue`、`web/api.py`、`web/resources.py`、`web/frontend/src/api/index.ts`
**收益**：超大文件夹首屏响应与内存占用下降。**风险**：中（需新增后端接口，属可选）。

**评估结论（2026-08-26）**：实测当前 `downloads/` 仅 2 个文件夹、96 个文件，最大文件夹 88 个文件，远低于本项预设的 5000 阈值，`/api/resources` 全量返回压力可忽略。引入后端分页接口属于「为不存在的容量问题预支复杂度」，**当前不实施**；若未来单文件夹文件数超阈值再按此方案落地。

## 三、P1 建议（值得做，按需安排）

### P1-6 目录面包屑 / 层级导航

**现状问题**
- 文件以「相对路径」文本展示，但用户无法点击进入子目录；扁平 `downloads/<folder>/<file>` 结构下层级不深，但路径可读性一般。

**方案**
- 保持现有「文件夹 → 文件」两层结构（符合当前数据组织），但在文件行把相对路径改成可点击的浅色链路（复制用途保留）。
- 若未来出现子目录嵌套，再引入面包屑导航；当前两层结构下**不建议**为导航过度设计。

**涉及文件**：`web/frontend/src/views/ResourcesView.vue`
**收益**：路径更可读、便于按目录心智定位。**风险**：低。

### P1-7 排序稳定性与记忆

**现状问题**
- 无任何筛选/排序状态持久化，切换页面或刷新后回到默认排序。

**方案**
- 将「搜索词 / 类型筛选 / 排序键」用 `sessionStorage` 或 `useAppStore` 保存，返回页面时恢复。
- 与项目「跨页状态归并 useAppStore」约束一致：若做持久化优先归入 `useAppStore`，避免新建散 store。

**涉及文件**：`web/frontend/src/views/ResourcesView.vue`、`web/frontend/src/stores/*`
**收益**：高频使用者的操作习惯不丢失。**风险**：低。

### P1-8 文件行操作扩展（下载 / 打开）

**现状问题**
- 当前文件行仅「复制路径」一个操作，对「只读展示」足够，但缺少直达动作。

**方案**
- 增加「下载」：因文件在服务端本地目录，可新增后端 `/api/resources/download?path=`（鉴权后 `FileResponse`）下载文件；考虑到 Web 进程只读定位与安全（路径穿越校验），**建议保守**，仅当确有此需求时再做。
- 增加「打开目录」：复制目录名已覆盖此诉求，可暂不重复。

**涉及文件**：`web/frontend/src/views/ResourcesView.vue`、`web/api.py`
**收益**：便捷下载/查看。**风险**：中（引入文件 IO 与路径安全校验，需谨慎）。

### P1-9 复制成功的可视反馈增强

**现状问题**
- 复制成功仅 `ElMessage.success`，无「已复制」的状态标记；复制失败时仅 `ElMessage.error`，无法区分是权限拒绝还是其他原因。

**方案**
- 复制成功后，行内「复制路径」按钮短暂切换为「已复制 ✓」（2s 后复原，可用 `ElMessage` 外的行内状态）。
- 失败分支区分 `navigator.clipboard` 在非 HTTPS / 非 localhost 下的不可用场景，降级用 `document.execCommand('copy')` 兜底（仅复制场景，非业务兼容）。

**涉及文件**：`web/frontend/src/views/ResourcesView.vue`
**收益**：操作反馈更明确。**风险**：低。

## 六、变更范围与风险

1. 本次优化**仅涉及前端** `web/frontend/src/views/ResourcesView.vue`（及按需的 `stores`、`api/index.ts`）；除 P0-5 / P1-8 外**不新增后端接口**，不改动路由与 `createWebHistory` 模式，不触碰 Web 写库禁令。
2. 每条建议相互独立，可单独确认、单独实施；建议实施顺序：P0-1 → P0-2 → P0-3 → P0-4 → P1-6/7/9 → P1-8 → P0-5。
3. 实施自检：前端改动后 `cd web/frontend && npx vue-tsc --noEmit` 0 错误，且 `read_lints`（ts-plugin IDE 诊断）0 错误；后端若新增接口需 `python web/app.py` 可启动并对受影响接口真实请求验证无 500。
4. 若确认实施，请在对应条目上回复（如「P0-1、P0-2 确认」），未确认的条目保持不动。
