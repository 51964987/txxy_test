# txxy 资源管理页面优化方案

> 状态：P0-1~P0-4 已实施（2026-08-26），P0-5 评估后不实施；**B 系列业务优化 P0（B1-B4）与 P1（B5-B11）已实施（2026-08-28，见第七节）**；旧条目 P1-7 由 B10 承接、P2-12 由 B11 承接，其余 P1/P2 仍待确认
> 适用范围：`web/frontend/src/views/ResourcesView.vue`（仅前端），后端 `/api/resources` 已具备增量缓存与限流，不在本次范围。
> 原则：不改变路由路径与 history 模式、Web 进程不写库、页面保持「只读展示」定位；每条建议独立，可单独确认、单独实施。
> 注：本页为独立功能模块文档，不与「数据总览大屏」文档合并；大屏相关汇总见 `数据总览大屏设计与优化总览.md`。

## 一、现状盘点（当前页面已具备的能力，避免重复建设）

- 统计卡片：资源目录数、文件总数、总大小三张卡，实时反映整体概览。
- 目录折叠列表：按文件夹分组展示，展开后显示文件清单；单次仅展开一个文件夹（`active` 互斥）。
- 大列表虚拟滚动：文件多的文件夹已改用 `el-table-v2`（P2-14 已落地），高度自适应（上限 420px）、宽度跟随容器（`ResizeObserver` 监听）。
- 文件元信息：类型 Tag（图片/视频/种子/文本/其他）、大小格式化、相对路径展示、修改时间（目录级）。
- 便捷操作：`复制目录名` / `复制路径`（`navigator.clipboard`）。
- 后端配套：`/api/resources` 有增量缓存（目录签名）与 60 次/分限流；前端已走统一 `request()`（10s 超时 + 去重 + 统一错误）。
- 空态：`downloads/` 无资源时展示 `el-empty`。

**当前交互能力相对薄弱**：纯「展开看 + 复制路径」只读浏览，无搜索、无筛选、无排序、无分页懒加载、无层级导航、无文件数/大数据的加载策略。

## 二、P0 建议（收益明显，推荐近期实施）

### P0-1 目录/文件搜索过滤（前端即时过滤）

**现状问题**
- 文件夹与文件数量较多时，只能逐个展开目视查找，无法按文件名快速定位。

**方案**
- 在统计卡与资源列表之间加一个 `el-input` 搜索框（`prefix-icon` 放大镜 + `clearable`），对当前展开文件夹的文件列表做**前端即时过滤**（大小写不敏感、`includes` 匹配 `name` / `rel_path`）。
- 搜索词非空时高亮命中的匹配片段（`name` 片段高亮，参考文件管理器通用交互）。
- 因单文件夹文件量已受虚拟滚动约束，前端过滤足以覆盖，**无需后端搜索接口**。

**涉及文件**：`web/frontend/src/views/ResourcesView.vue`、`web/frontend/src/main.ts`（如需新增 `Search` 图标，须在按需注册列表中加入）
**收益**：大文件夹内秒级定位文件；实现成本低（纯前端 `computed` 过滤）。**风险**：低。

**落地说明（2026-08-26）**：新增 `keyword` 搜索词，`filteredFiles` 对当前展开文件夹做类型筛选 + 关键词过滤（匹配 `name` / `rel_path`，大小写不敏感）；文件名命中片段用 `<mark>` 高亮（文本先 HTML 转义再替换，避免特殊字符破坏渲染）。`main.ts` 已注册 `Search` 图标。

### P0-2 文件类型筛选（分类 Tab / Tag 过滤）

**现状问题**
- 文件类型仅在行内以 Tag 展示，无法按「只看视频 / 只看种子」等维度快速聚焦。

**方案**
- 在列表表头上方加 `el-segmented` 或 `el-radio-group`（全部 / 图片 / 视频 / 种子 / 文本 / 其他），与搜索框并列；筛选对当前展开文件夹的文件列表生效，实时重算。
- 选中类型后，将虚拟滚动数据源替换为过滤结果；空结果展示轻量 `el-empty`（小尺寸）。

**涉及文件**：`web/frontend/src/views/ResourcesView.vue`
**收益**：按类型聚焦大文件夹，浏览效率显著提升。**风险**：低（复用现有列定义与虚拟滚动）。

**落地说明（2026-08-26）**：新增 `typeFilter`（`el-segmented`：全部/图片/视频/种子/文本/其他），与搜索共用 `filteredFiles` 过滤链路；过滤后无匹配时展示小尺寸 `el-empty`。

### P0-3 文件列表排序能力（名称 / 大小 / 类型）

**现状问题**
- 文件顺序固定为后端返回的路径字典序，无法按大小、类型等重排。

**方案**
- 给 `el-table-v2` 列头（文件名 / 大小 / 类型）加 `sortable` 排序（前端 `computed` 对过滤后的数据排序）；排序状态用 `ref` 保存。
- 注意 `el-table-v2` 的 `sortable` 需通过列配置与事件实现，若与虚拟滚动耦合较麻烦，可用表头外的 `el-dropdown` 排序切换作为降级方案。

**涉及文件**：`web/frontend/src/views/ResourcesView.vue`
**收益**：大文件夹按大小/类型排序，便于清理大文件。**风险**：中（需验证 `el-table-v2` 排序事件，可退化为下拉切换）。

**落地说明（2026-08-26）**：文件名/类型/大小三列配置 `sortable: true`，绑定 `:sort-state` 与 `@column-sort`，`filteredFiles` 内按排序键做前端排序（大小按数值，其余按 `localeCompare`）；采用 `el-table-v2` 原生表头排序，未退化为下拉。

### P0-4 加载失败重试与刷新按钮

**现状问题**
- `load()` 失败仅 `ElMessage.error`，页面停留空态，用户需手动刷新整个浏览器页面才能重试；无手动刷新入口。

**方案**
- 在统计卡右侧加「刷新」`el-button`（`icon="Refresh"`，`loading` 状态复用 `loading`），点击重走 `load()`。
- 失败时在统计卡下方保留一个 `el-result` / 内联错误块 + 「重试」按钮，替代仅弹一条 error 后空白的体验。

**涉及文件**：`web/frontend/src/views/ResourcesView.vue`、`web/frontend/src/main.ts`（如需新增 `Refresh` 图标，须在按需注册列表中加入）
**收益**：弱网/瞬时失败可自助恢复，不依赖整页刷新。**风险**：低。

**落地说明（2026-08-26）**：统计卡第 4 格加入「刷新」按钮（`Refresh` 图标，`loading` 复用加载态）；`load()` 失败时设置 `loadError`，展示 `el-result`（错误信息 + 「重试」按钮）；`main.ts` 已注册 `Refresh` 图标。

### P0-5 大数据文件夹渐进加载（可选，视文件量）

**现状问题**
- `/api/resources` 一次返回全部文件清单；若某文件夹文件数达数万，JSON 体积大、首屏解析耗时，且列表 420px 高度内需先拿到全量数据。

**方案**
- 若实测某文件夹文件数超阈值（如 > 5000），改为「展开时按需加载」：后端新增 `/api/resources/{folder}?offset&limit` 分页接口，前端展开时按需拉取并配合虚拟滚动滚动加载。
- 若文件量在可接受范围（当前场景），本项可不做，仅作为容量水位预案。

**涉及文件**：`web/frontend/src/views/ResourcesView.vue`、`web/api.py`、`web/resources.py`、`web/frontend/src/api/index.ts`
**收益**：超大文件夹首屏响应与内存占用下降。**风险**：中（需新增后端接口，属可选）。

**评估结论（2026-08-26）**：实测当前 `downloads/` 仅 2 个文件夹、96 个文件，最大文件夹 88 个文件，远低于本项预设的 5000 阈值，`/api/resources` 全量返回压力可忽略。引入后端分页接口属于「为不存在的容量问题预支复杂度」，**当前不实施**；若未来单文件夹文件数超阈值再按此方案落地。

## 三、P1 建议（值得做，按需安排）

### P1-6 目录面包屑 / 层级导航

**现状问题**
- 文件以「相对路径」文本展示，但用户无法点击进入子目录；扁平 `downloads/<folder>/<file>` 结构下层级不深，但路径可读性一般。

**方案**
- 保持现有「文件夹 → 文件」两层结构（符合当前数据组织），但在文件行把相对路径改成可点击的浅色链路（复制用途保留）。
- 若未来出现子目录嵌套，再引入面包屑导航；当前两层结构下**不建议**为导航过度设计。

**涉及文件**：`web/frontend/src/views/ResourcesView.vue`
**收益**：路径更可读、便于按目录心智定位。**风险**：低。

### P1-7 排序稳定性与记忆（已由 B10 承接实施，见第七节）

**现状问题**
- 无任何筛选/排序状态持久化，切换页面或刷新后回到默认排序。

**方案**
- 将「搜索词 / 类型筛选 / 排序键」用 `sessionStorage` 或 `useAppStore` 保存，返回页面时恢复。
- 与项目「跨页状态归并 useAppStore」约束一致：若做持久化优先归入 `useAppStore`，避免新建散 store。

**涉及文件**：`web/frontend/src/views/ResourcesView.vue`、`web/frontend/src/stores/*`
**收益**：高频使用者的操作习惯不丢失。**风险**：低。

### P1-8 文件行操作扩展（下载 / 打开）

**现状问题**
- 当前文件行仅「复制路径」一个操作，对「只读展示」足够，但缺少直达动作。

**方案**
- 增加「下载」：因文件在服务端本地目录，可新增后端 `/api/resources/download?path=`（鉴权后 `FileResponse`）下载文件；考虑到 Web 进程只读定位与安全（路径穿越校验），**建议保守**，仅当确有此需求时再做。
- 增加「打开目录」：复制目录名已覆盖此诉求，可暂不重复。

**涉及文件**：`web/frontend/src/views/ResourcesView.vue`、`web/api.py`
**收益**：便捷下载/查看。**风险**：中（引入文件 IO 与路径安全校验，需谨慎）。

### P1-9 复制成功的可视反馈增强

**现状问题**
- 复制成功仅 `ElMessage.success`，无「已复制」的状态标记；复制失败时仅 `ElMessage.error`，无法区分是权限拒绝还是其他原因。

**方案**
- 复制成功后，行内「复制路径」按钮短暂切换为「已复制 ✓」（2s 后复原，可用 `ElMessage` 外的行内状态）。
- 失败分支区分 `navigator.clipboard` 在非 HTTPS / 非 localhost 下的不可用场景，降级用 `document.execCommand('copy')` 兜底（仅复制场景，非业务兼容）。

**涉及文件**：`web/frontend/src/views/ResourcesView.vue`
**收益**：操作反馈更明确。**风险**：低。

### 8.1 删除功能

#### 8.1.1 互联网上的常见做法

| 做法 | 代表产品 | 启示 |
|---|---|---|
| **回收站 / 最近删除** | Windows 回收站、macOS「废纸篓」、百度网盘/Google Drive「最近删除」 | 删除先移入隔离区，保留 N 天后才真正清理；用户可自助恢复 |
| **二次确认 + 危险色** | 各类后台管理系统 | 破坏性操作用红色主按钮，弹窗写明「N 个文件 / 释放 X MB / 不可撤销」 |
| **延迟执行 + 撤销** | Gmail「撤销发送」 | 提交后给几秒撤销窗口；实现复杂，通常回收站已足够 |
| **批量多选删除** | 网盘、文件管理器 | 需要先有勾选列，配合全选/反选 |
| **操作审计** | 企业网盘 | 记录谁在何时删了什么，便于追溯 |

#### 8.1.2 方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A 永久删除 | `unlink` / `rmtree` 直接删除 | 实现最简单，立即释放空间 | **误删无法恢复**；目录删除风险极高 | ❌ 不单独采用 |
| **B 软删除到回收站（推荐）** | 移动到 `outputs/trash/<日期>/<原相对路径>`，保留 N 天（默认 7 天）后可清理；提供「恢复」入口 | 误删可恢复；实现难度适中；与网盘体验一致 | 占用额外磁盘空间（同盘移动，实际是改名，开销极小） | ✅ 推荐 |
| C 调用系统回收站 | Windows `SHFileOperation` | 与系统体验一致，可在回收站还原 | 需引入 `pywin32`（**违反项目不引新依赖约束**），且 Linux 无对应实现 | ❌ 不采用 |

#### 8.1.3 推荐设计（B）

后端：

| 文件 | 改动 |
|---|---|
| `web/resources.py` | 新增 `resolve_safe_dir(rel)`（目录版路径校验，禁止 `downloads/` 根自身）、`move_to_trash(rel)`、`restore_from_trash()`、`list_trash()`；删除/恢复后**主动失效目录签名缓存**（见风险 3） |
| `web/api.py` | `POST /api/resources/delete`（body: `{paths: string[], scope?: 'file'\|'dir'}`）、`POST /api/resources/restore`、`GET /api/resources/trash`；删除属重操作，限流建议 10 次/分 |

前端：

- 文件行新增「删除」（红色文字按钮），目录头新增「删除目录」
- 删除前 `ElMessageBox.confirm`：写明**对象名称、文件数（目录）、将释放空间、保留 7 天后可恢复**
- 删除成功后刷新列表并提示「已移入回收站，可在『回收站』中恢复」
- 工具栏新增「回收站」入口：抽屉展示待清理项，支持「恢复」与「立即清理」
- 建议**不做批量多选**：当前列表是 `el-table-v2` 虚拟滚动且无多选列，加勾选列改动面较大；先用单行/单目录删除覆盖主要场景，若确需批量再单独评估

#### 8.1.4 风险与规避

| # | 风险 | 严重度 | 规避 |
|---|---|---|---|
| 1 | 误删下载成果 | 高 | 软删除 + 7 天保留 + 恢复入口；删除弹窗写明后果 |
| 2 | 路径穿越 / 越权删除 | 高 | 复用 `resolve_safe` 的 `resolve()` 校验；**禁止删除 `downloads/` 根**；拒绝绝对路径与 `..` |
| 3 | 扫描缓存未失效，列表仍显示已删文件 | 中 | `resources.py` 用「顶层文件夹名 + mtime」做签名缓存，删除**子文件不一定改变顶层目录 mtime** → 删除后必须主动 invalidate |
| 4 | 删除正在进行下载任务的目录 | 中 | 删除前检查 `download_tasks` 是否有该目录的活动任务，有则拒绝并提示 |
| 5 | 磁盘空间未释放（回收站占用） | 低 | 回收站保留期到期清理；提供「立即清理」；同盘移动不额外占用 |
| 6 | 与抓取/下载进程并发 | 低 | 删除失败（文件被占用）时明确提示，不做静默重试 |

#### 8.1.5 需确认

1. **是否允许 Web 端做删除**（项目此前的能力边界是「下载中心仅做文件系统下载」）；确认后按软删除实现
2. **保留期**：默认 7 天是否合适？是否需要「立即永久删除」入口（需更强的二次确认）
3. **删除范围**：仅文件、仅目录，还是两者都要
4. **是否需要批量多选**

### 8.2 视频播放

#### 8.2.1 互联网上的常见做法

| 做法 | 适用场景 | 本项目 |
|---|---|---|
| **HTML5 `<video>` + HTTP Range** | 自托管影音站、NAS  web 界面、个人媒体库 | ✅ 最契合：后端已有受控文件接口，Starlette `FileResponse` 原生支持 206，前端 `<video>` 直接播、可拖进度 |
| HLS / DASH 分片 | 大型视频站（YouTube、B 站） | ❌ 需要 ffmpeg 转码切片 + 额外存储与依赖，过重 |
| 服务端转码 | 需兼容任意格式 | ❌ 需 ffmpeg，且 CPU 开销大 |
| 缩略图 / 雪碧图预览 | 提升浏览体验 | ⚠️ 可选增强，同样依赖 ffmpeg，建议不做 |

#### 8.2.2 方案对比

| 方案 | 做法 | 结论 |
|---|---|---|
| **A 扩展现有文件接口（推荐）** | `PREVIEW_TYPES` 增加视频 MIME 映射，`/api/resources/file` 放行视频；限流从 60 提高到 300 次/分（Range 拖动请求频繁）；前端视频行「播放」→ `el-dialog` + `<video controls>` | ✅ 复用现有路径校验与限流器，改动最小 |
| B 新增独立 `/api/resources/video` | 独立路由与限流，语义清晰，便于后续扩展 | ⚠️ 与 A 相比需重复挂载限流与返回逻辑（校验可复用 `resolve_safe`），收益有限 |
| C HLS 转码 | ffmpeg 切片 + `.m3u8` | ❌ 引入外部依赖，违反项目约束 |

#### 8.2.3 推荐设计（A）

后端：

| 文件 | 改动 |
|---|---|
| `web/resources.py` | 新增 `PLAYABLE_TYPES`（`.mp4`→`video/mp4`、`.webm`→`video/webm`、`.m4v`→`video/mp4`、`.mov`→`video/quicktime`）；`PREVIEW_TYPES` 保持图片专用，新增播放白名单避免语义混淆 |
| `web/api.py` | `/api/resources/file` 放行白名单改为「图片 + 可播放视频」；视频走独立限流（建议 300 次/分），避免拖动进度条触发 429 |

前端：

- 视频文件行新增「播放」按钮（与图片「预览」并列）
- 播放层：`el-dialog`（全屏或宽屏）+ `<video controls preload="metadata" :src="...">`
- 关闭对话框时暂停并释放 `src`，避免后台继续缓冲
- **格式兼容提示**：`.mkv/.avi/.flv/.ts/.m3u8` 浏览器支持不确定（Chrome 对 mkv 仅部分编码可播），对非白名单格式不显示「播放」，改为提示「可下载后用本地播放器观看」

#### 8.2.4 风险与规避

| # | 风险 | 规避 |
|---|---|---|
| 1 | Range 请求频繁触发限流 | 视频单独限流 300 次/分（拖动一次进度条通常产生 3~10 个请求） |
| 2 | 大视频内存占用 | 依赖 `FileResponse` 流式分块读取，不整文件读入内存；需实测确认 206 生效 |
| 3 | 编码/封装不支持导致黑屏 | 白名单只放行浏览器普遍支持的格式；不支持的格式不显示播放入口 |
| 4 | 对话框关闭后仍在缓冲 | 关闭时 `pause()` 并清空 `src` |
| 5 | 移动端播放体验 | `<video controls>` 走系统播放器；全屏由浏览器原生提供，不额外实现 |

#### 8.2.5 需确认

1. **播放是否需要覆盖全部 `VIDEO_EXTS`**，还是只放行 mp4/webm/m4v/mov（推荐后者，兼容性最稳）
2. **播放入口形态**：弹窗（推荐）还是点击后新标签页直接打开
3. **是否需要播放列表/连续播放**（同目录下多个视频自动连播）——当前图片预览已有翻页能力，视频是否对齐

#### 8.5.2 与原方案的两处差异

1. **视频改用独立路由 `/api/resources/video`（原方案推荐合并进 `/api/resources/file`）**
   原方案未考虑限流差异：视频拖进度条一次会产生 3~10 个 Range 请求，60 次/分不够用，而图片预览维持 60 次/分更合适。**同一路由只能挂一个限流器**，无法按扩展名区分，故拆为独立路由并挂 `VideoRateLimit`（300 次/分）。路径校验仍复用 `resolve_safe()`，安全逻辑没有重复实现。

2. **「立即永久删除」入口放在回收站抽屉，而不是首次删除弹窗**
   原方案设想在删除确认时提供该入口。实施时改为两步：删除默认只做软删除（弹窗只保留「移入回收站 / 取消」），彻底删除仅在回收站内对已删除项提供（并带独立的红色二次确认）。这样用户必须先看到「已移入回收站」的反馈，再决定是否彻底删除，误操作概率更低。

#### 8.5.3 实测结果

**接口层**（curl）：

| 场景 | 结果 |
|---|---|
| 软删除文件 | `{"ok":true,"id":"20260831_145842_cc6b8b","rel":"_webtest/test.txt","size":20}` |
| 回收站列表 | `remain_days: 7`、`expired: false`、`keep_days: 7` |
| 恢复 | `{"ok":true,"rel":"_webtest/test.txt"}`，文件回到原路径 |
| 彻底删除（清空） | `{"ok":true,"count":1}`，文件消失、回收站归零 |
| 越界删除 `../db/posts.db` | **400 拒绝** |
| 删除 `downloads` 根目录 | **400 拒绝** |

- **控制台错误 0**

**校验**：`python -m py_compile` 通过；`npx vue-tsc --noEmit` 与 `read_lints` 双通道 0 错误；`npx vite build` 通过；清理测试数据后 `/api/resources` 回归正常（7 目录 / 156 文件）。

#### 8.5.4 已知限制

- **过保留期的条目不会自动清理**：`list_trash()` 只标记 `expired`，真正释放空间需要用户在回收站点击「清空回收站」或逐项「彻底删除」。
- **恢复时若原路径已存在同名文件会被拒绝**（不覆盖现有文件），需先处理同名文件。
- **视频能否播放取决于编码**：白名单覆盖了全部 `VIDEO_EXTS`，但浏览器只保证普遍支持 H.264/AAC（mp4、m4v）；`.mkv/.avi/.flv/.ts` 等取决于具体编码，无法播放时请用「打开」后在本地播放器观看。
- 批量多选删除按确认结果**暂未实现**，当前为单行/单目录删除。

### 8.6 回收管理页面（2026-08-31 已实施，方案 B）

> 用户确认：采用 B（新增 `/trash` 独立页面，同意变更 5 条路由约定）、暂不做批量多选、需要搜索与排序。
> 落地说明见 8.6.6。

#### 8.6.1 互联网上的做法

| 产品 | 回收站形态 | 共性原因 |
|---|---|---|
| 百度网盘 / Google Drive / OneDrive | **独立页面**（侧边导航有独立入口） | 回收站是独立数据域：需要列表、多选、排序、批量恢复/删除、清空、空间占用统计 |
| Windows 回收站 / macOS 废纸篓 | 独立位置（桌面或侧边栏入口） | 同上，且需要「按删除时间/原位置查看」 |
| Gmail「垃圾桶」 | 独立文件夹视图，与主列表同构 | 复用列表能力，降低学习成本 |
| 各类后台管理系统 | 多数独立页面，轻量场景用抽屉 | 取决于条目规模与操作复杂度 |

**规律**：回收站是否需要独立页面，取决于两件事——**条目规模**和**操作复杂度**。条目少、只做单条恢复时抽屉够用；需要多选、批量、排序、搜索、空间统计时，独立页面（或等价的独立视图）更合适。

#### 8.6.2 方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A 保持抽屉 | 现状（8.5 已落地） | 零改动；不丢失上下文 | 条目多时难浏览；无排序/筛选/批量；「清空」风险高 | 条目少时够用 |
| B 新增独立页面 `/trash` | 新增第 6 条路由 + 菜单项 | 空间充裕，能力最完整 | **变更项目既定的「5 条固定路由」约定**，需你明确同意 | 功能最完整，代价是破坏约定 |
| **C 页内视图切换（推荐）** | 在 `/resources` 顶部加「资源 / 回收站」切换，回收站为同页内的完整列表视图 | **不新增路由**，不破坏既定约定；可获得接近独立页面的能力（表格、多选、批量、统计） | 与资源列表共用页面，切换时需清理筛选/展开状态 | ✅ 推荐 |

> 说明：项目约束为「路由固定为 `/`、`/posts`、`/runs`、`/resources`、`/downloads` 五条」。此前「全屏按钮」与「帖子阅读页」都用「按路由限制 / 用抽屉」的方式规避了新增路由，C 方案沿用同一思路。

#### 8.6.3 C 方案设计要点

**前端（`/resources` 页内）**

- 顶部 `el-segmented` 切换视图：`files`（资源）| `trash`（回收站）
- 回收站视图：
  - 统计条：条目数 / 占用空间 / 已过期数 / 保留期说明
  - 表格：名称、类型（文件/目录）、大小、删除时间、**剩余天数**、原路径
  - 多选列 + 工具栏：恢复选中、彻底删除选中、清空回收站
  - 排序（删除时间 / 大小 / 名称）与名称搜索
- 切回资源视图时自动刷新资源列表（避免在回收站操作后看到过期数据）
- 批量操作确认：写明「恢复 N 项」/「彻底删除 N 项，不可恢复」

**后端配套（仅在需要批量时）**

- `POST /api/resources/restore`：`{ id }` 扩展为 `{ ids: string[] }`，返回 `{ ok, restored, failed: [{id, reason}] }`
- `POST /api/resources/purge`：同样支持 `ids`，`ids` 为空沿用「清空全部」语义
- 逐项处理、部分失败不影响其他项，返回明细供前端提示

#### 8.6.4 风险与规避

> 背景：此前**只有图片（预览）与视频（播放）有操作入口，文本 / 种子 / 其他类型只能复制路径或删除**；排版上目录头把来源、元信息、操作全挤在一行，统计卡第 4 格只放一个「刷新」按钮。

### 9.2 后端新增能力

| 接口 | 说明 |
|---|---|
| `GET /api/resources/text?path=` | 受控文本查看：仅 `.txt/.md/.log`，UTF-8 优先、**GB18030 兜底**（中文 Windows 生成的 txt 多为 GBK 系），超 512KB 截断；限流 60 次/分 |

## 十、移动端适配（2026-09-01 已实施）

> 背景：原先文件列表在手机端只能横向溢出——`el-table-v2` 的列宽固定（名称 300 + 类型 90 + 路径 250 + 操作 260 等，合计 1000+ px），窄屏必然出现横向滚动，虚拟滚动表格在小屏体验很差。

### 10.1 互联网参考

| 产品 / 规范 | 做法 | 启示 |
|---|---|---|
| Google Drive / 百度网盘 移动端 | 文件用**单列列表**（主信息 + 副信息），彻底不用表格 | 窄屏该换形态，而不是把表格塞进去 |
| Ant Design Mobile / Vant | List 组件，行内操作用图标或「更多」菜单 | 操作收进下拉，避免按钮挤成一行 |
| Material Design / iOS HIG | 可点区域 ≥ 48dp / 44pt | 触控目标要够大 |
| Bootstrap `.table-responsive` | 表格外套一层横向滚动 | 成本最低但体验一般，仅适合兜底 |

**结论**：窄屏不要试图压缩表格，直接换成单列卡片列表（网盘移动端的通行做法）。

### 10.2 实现

- 断点复用布局层 `useAppStore.isMobile`（`(max-width: 767px)`），**页面不自建第二套判定**
- 移动端文件列表改为**单列卡片**：类型色点 + 文件名 / 副信息（类型 · 大小 · 路径）/ 主操作（按类型：预览 · 播放 · 查看 · 种子信息）+ 「更多」下拉（打开 / 复制路径 / 删除）
- 卡片最小高度 56px（满足移动端触控目标 ≥44px 的建议）
- **移动端没有表头可点排序** → 工具栏增加「排序字段下拉 + 升降序切换」，与表头排序**共用同一套 `sortState`** 并双向同步，跨视口切换不丢排序
- 目录模式与全局结果模式同样处理（两处卡片结构一致，改一处需同步另一处）

**目录行专项优化**（2026-09-02 追加）：目录名被操作按钮挤压，实测 390px 下只剩约 120px，几乎看不出标题：

1. **移动端把「复制目录名 / 打开 / 删除目录」收进「更多」下拉**。根因是这三个按钮都是 `flex-shrink: 0`（合计约 200px），而 `.folder-main` 带 `min-width: 0` 会主动收缩——因此仅加 `flex-wrap: wrap` **不会**触发换行（文件夹总能缩到最小），标题照样被压。必须先移走按钮，释放出的宽度才回到标题。
2. **目录名改为两行截断**（`-webkit-line-clamp: 2`）。目录名即帖子标题，普遍四十字以上，单行省略只能看到十来个字；两行是 Material / iOS 文件列表的通行做法。
3. 标题旁的「未下载到媒体」等 Tag 允许换行，不与标题争抢横向空间。

**踩到的两个坑（均已修，引以为戒）**：

- **CSS 顺序**：移动端块最初写在样式表**中部**，而 `.folder-name` 基础规则在其后（1840 行）——同特异性下后定义者胜，整块静默失效。现已固定放在**样式表末尾**并在注释中写明原因。
- **`line-clamp` 标准属性冲突**：同时写 `line-clamp: 2` 与 `-webkit-line-clamp: 2` 时，Chrome 的新 `line-clamp` 实现会接管，把 computed `display` 强制为 `flow-root` 并覆盖 `white-space`，导致两行截断完全失效（表现为高度仍是一行）。**只保留 `-webkit-box` + `-webkit-line-clamp` 组合**即可正常工作。
- 统计卡沿用全局 `style.css` 已有的 1100 / 640 两档响应式，未重复定义

### 10.3 验证（iPhone 13 视口 390×844，含 isMobile + 触控）

| 横向溢出 | `scrollWidth == clientWidth`，**展开目录前后均无横向滚动** |

## 十二、点击「最大目录」自动滚动定位（2026-09-02 已实施）

## 十三、容量洞察卡布局（2026-09-02 已实施）

**业界做法**：仪表盘类布局（Grafana / Google Analytics / 各类 BI 看板）的通行分法是**按信息层级分配宽度**——

1. **全局性概览**（整体构成、总览图表）独占整行，视觉权重最高，读者一眼先看它；
2. **同级的明细列表**并排等宽，因为它们信息密度相当，做成一大一小反而会让读者误以为两者重要性不同；
3. 窄屏回落为单列纵向堆叠，不做横向挤压。
