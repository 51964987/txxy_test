## 零、现状快照（调研时实测）

- 数据规模：14.4 万帖 / 3617 位作者 / 13 个版块，`created_at` 全量有效（发布时段类分析可行）。
- 页面分区：KPI 4 卡 → 趋势双图 → 活跃作者/版块榜 → 热门四栏（P1）。
- **重要发现**：后端已实现 4 个「数据源健康与资产管理」类接口，前端 `api/index.ts` 也已定义对应方法，但**大屏尚未接入**（工作区未提交改动）：

  - `/stats/pending_downloads`（待下载推荐 FD1：窗口内互动量最高且未下载的帖子）

## 一、第一批推荐（后端已就绪，只差前端接线）

### R1. 采集健康条（接入 `/stats/health`）【建议优先】

- **业界做法**：Grafana 的 alert banner / 数据源状态灯——大屏顶部一条常驻状态，绿/黄/红三态 + 一句话结论（「成功 6 个版块 / 失败 0 个 / 未执行 0 个（7 个进行中）」「已 3 天无入库活动」「2 个版块失败：xxx」），点击直达运行记录页。
- **业务价值**：大屏是「看数据」的，但单人采集工具最怕的其实是「数据悄悄停更」。健康条把「数据源还正常吗」从 KPI 卡副指标的间接暗示，升级为第一眼可见的明确判定；且后端已把阈值判定收敛在 `_health_verdict` 一处，前端只上色展示，不存在两端口径打架。
- **落点建议**：Header 下方（或 KPI 卡上方）一条窄横幅；`level=ok` 时弱化为小绿点 + 短文案，不抢视觉；warn/danger 时整条高亮。点击下钻 `/runs`。
- **工作量**：小（纯前端一个区块 + 一个接口调用，P0 随首屏）。

### R2. 全站周期对比（接入 `/stats/compare`）

- **业界做法**：GA 的「对比上一时间段」、电商 BI 的环比卡——近 7 日 vs 前 7 日、近 30 日 vs 前 30 日的发布量涨跌。
- **业务价值**：目前只有「今日 vs 昨日」环比（今日发布卡），缺中期趋势感。「近 7 日发布 +12%」能回答「这站最近整体活跃度是在涨还是在跌」，与活跃榜 7d 口径同源（后端 `_window_pair` 刻意与榜单共用滚动窗口与 `_delta`，不会出现「榜单说涨、大屏说跌」）。
- **落点建议**：并入「累计收录」卡副指标（现已有近 7 日绝对值 `week_new`，补一个环比箭头）；30 日对比可放趋势图卡头统计条。不新开卡片，避免 KPI 卡膨胀。
- **工作量**：小。

### R3. 待下载推荐（接入 `/stats/pending_downloads`）

- **业界做法**：YouTube「推荐/稍后再看」、内容平台的策展位——按互动量排序的「值得收藏」清单。
- **业务价值**：这是本工具业务闭环上的关键一环——大屏目前只「看」，下载要去热门榜逐条悬浮找按钮。待下载推荐直接回答「近 30 天互动最高、还没下到本地的帖子是哪些」，把「发现 → 下载」链路缩短为一步（行内下载按钮复用热门榜现有实现）。
- **落点建议**：热门榜区域新增一栏（或与「最新最热」并列的可切换视图）；标题、版块 tag、互动量、下载按钮样式全部复用热门四栏既有组件风格。
- **工作量**：中（一个新区块，样式复用为主）。

### R4. 内容→资产漏斗（接入 `/stats/assets`）

- **业界做法**：BI 经典漏斗图（转化漏斗）：收录总量 → 已下载帖数 → 本地文件数 → 占用体积，逐级呈现「内容沉淀为本地资产」的转化。
- **业务价值**：项目定位是「采集 + 本地媒体资产管理」，但大屏目前完全没有「资产侧」视角。漏斗回答「14 万收录里我到底存下了多少」，四级的口径后端已与提交判重、资源管理页对齐。
- **落点建议**：两种形态二选一——（a）紧凑横条卡（四级数字 + 箭头 + 转化率 %），放 KPI 行下方或「最近入库」卡旁；（b）并入「设置/下载中心」侧。倾向 (a)：资产是本工具第二主角，值得大屏一席。
- **工作量**：小-中。

## 二、第二批推荐（新业务能力，需后端配合）

### R5. KPI 卡下钻（文档九.6 的 B2 候选重提）

- **业界做法**：GA / Amplitude 的「所有指标可点」——点任何数字都能看到构成它的明细列表。
- **业务价值**：大屏已经为榜单做了大量「下钻继承口径」，但 4 张 KPI 卡本身不可点。「今日发布 856」→ 点进 `/posts?date=今天`、「发帖作者」→ 当日活跃作者帖子列表，符合现有交互心智，成本极低。
- **工作量**：小（`goPostsWith` 传参即可；注意「累计收录」无时间语义、「最近入库」跳 `/runs`）。

### R6. 发布时段热力图（周几 × 小时）

- **业界做法**：GA「用户活跃时间」热力图、YouTube Studio 受众报告——7 列（周一~周日）× 24 行（小时）的矩阵，颜色深浅 = 发布量。
- **业务价值**：回答「这个站什么时段最活跃」。对采集有直接指导意义（挑活跃时段跑批、看刚发的新帖），对内容消费也有参考（什么时候去刷最新内容）。`created_at` 全量有效，SQL 按 `strftime` 聚合 + 5s TTL 缓存即可，14 万行无压力。
- **落点建议**：趋势双图区下方或与活跃榜同层；点击某格下钻「该周几+时段」不可行（posts 页无小时筛选），改为点击格子弹 tooltip 显示当日该时段代表帖即可；或按周几下钻（date 无周几筛选，亦不可下钻）——**本图定位纯洞察，不做下钻**。
- **工作量**：中（新接口 1 个 + ECharts heatmap，注意遵守网格线/tooltip 顶层规范）。

### R7. 互动分布直方图（内容质量视角）

- **业界做法**：电商 BI 的 GMV 分层分布、B站创作的「互动量分布」——把帖子按互动量分桶（0 / 1-9 / 10-99 / 100-999 / 1000+），看长尾结构。
- **业务价值**：目前榜单只看头部（Top10），但 14 万帖的整体质量结构（多少帖子零互动、头尾悬殊程度）没有任何视图承载。对「这个站的内容值不值得持续收」是重要信号，也为下载推荐提供直觉校验（桶越靠前越说明待下载推荐池足够肥）。
- **落点建议**：可与 R4 漏斗合并为一张「内容质量/资产」双视图卡；纯 SQL 分桶 + 缓存。
- **工作量**：小-中。

### R8. 新晋作者榜（rising stars）

- **业界做法**：GitHub Trending 的 "Rising stars this period"、B站涨粉榜、微博新星榜——不是看累计资历，而是「最近冒出来的新面孔」。
- **业务价值**：活跃作者榜切到 7d 后仍可能被熟面孔占据；「新晋」回答「最近有哪些第一次出现且高产的新作者」（如 `MIN(date) >= 近30日` 且窗口内发帖 ≥ 3）。对内容发现类工具是高价值信号，也是现有口径体系（累计/7d/30d）的自然补集。
- **工作量**：中（新接口 + 榜单区块，样式复用条形图）。

### R9. 作者榜副指标增强（文档十一「未做候选」落地）

- **业界做法**：榜单行悬浮展示多维画像（跨版块数、篇均互动、最后活跃时间）——榜单主值保持单一可解释，细节进 tooltip。
- **业务价值**：纯发帖量排序对「活跃」的定义较窄；tooltip 补「跨 N 个版块 · 篇均互动 X · 最后活跃 X 天前」后，判断作者质量不需要跳页。SQL 均为一次 GROUP BY 可得。
- **工作量**：小-中。

### R10. 趋势图空窗/断档标注（数据质量视角）

- **业界做法**：Grafana 的 no-data gap——断点/零值日显式标注而非连线糊过去。
- **业务价值**：趋势图目前「无数据的日期」与「零发布」不可区分（采集停了几天的坑会被平滑折线掩盖）。前端把 0 值日画成灰点/断线 + 顶部小字「N 天无数据」，一眼识别采集断档，与 R1 健康条互补（健康条看当下，标注看历史）。
- **工作量**：小（纯前端，趋势接口已含逐日数据）。

## 三、暂不推荐 / 前置条件不满足（如实列出，避免反复讨论）

| 项 | 不推荐理由 |
|---|---|
| 标题词云 | 需 `echarts-wordcloud` 新依赖（违反「不引入新 UI 依赖」）且中文分词需引入 jieba（新后端依赖），成本高收益一般；若确实需要，可先做「热词 TopN 榜」替代方案再评估 |
| 同比去年（B3） | 数据最早有效日期在 2026 年内，**不足一年**，无同比基准；待数据满一年后自动具备，先不做 |
| 沉寂版块榜 | 实测 13 个版块 `MAX(date)` 全部为 2026-09-10（当日全活跃），当前无沉寂版块可展示；版块「活力」已由活跃版块榜 + 7d/30d 口径覆盖 |
| 头部集中度（帕累托） | 「Top20% 作者贡献 X% 帖子」单看有趣但决策价值弱，可先以作者榜卡头一行小字实现（轻量），独立图表暂不做 |
| 发布日历热力图（GitHub contributions 式） | 与现有趋势图信息重叠，仅视角更长（一年）；若要做建议与「同比」一起等数据满一年后作为「年度回顾」一并评估 |

## 五、若确认实施，统一遵守的落地约束

1. 新接口一律进 `web/api.py` + `db.cached()` 5s TTL + 前端 `src/api/index.ts` 同名方法；SQL 过滤 `date >= '2000-01-01'` 脏数据。
2. 所有可下钻入口必须继承当前统计口径（时间窗/版块/排序），沿用 `goPostsInRange` 范式，禁止用不带时间语义的 `goPostsWith` 承接时间窗入口。
3. 图表遵守既有规范：Y 轴横向网格线 `rgba(0,0,0,0.08)`、X 轴竖向线隐藏、`axisPointer` 深色、`tooltip.appendToBody: true`、色板复用 `fidColor.ts`。
4. 桌面 + 移动端双视口实测（含窄屏布局与触摸可达性），`npx vue-tsc --noEmit` 与 `read_lints` 双通道 0 错误，后端接口真实请求验证无 500。
5. 不引入任何新依赖；不新建 store，跨页状态归并 `useDashboardStore`。

## 七、落地后的四项口径修正（2026-09-11 当日已落地）

> R1-R4 落地后用户提出的四个追问，经诊断全部属实，当日修复。详细方案与实测见《数据总览大屏设计与优化总览.md》第十八节。

| # | 用户追问 | 诊断结论 | 修复 |
|---|---|---|---|
| 1 | 清空下载中心任务（资源管理保留）后，「内容资产·已下载帖」是否为 0？ | **是，且不合理**。「已下载」判定只依赖任务列表，而任务列表是易失的（手动清空 + 自动轮转均删记录）；实测清空后 `downloaded_posts=0`（磁盘 3882 文件仍在） | 新增**下载履历** `outputs/download_history.json`（url → 保存目录，独立持久化），「已下载」= 履历 ∪ 任务历史中目录仍在者；启动时从任务播种 + 按「目录名=帖子标题」精确匹配从 downloads/ 增量恢复（实测恢复 156 条，`downloaded_posts` 0→156） |
| 2 | 全站趋势有「近30日环比」，分板块对比没有类似环比，是否合理？ | **不对称属实**。逐版块环比在「活跃版块 Top10」条尾已有，但趋势卡本身缺失 | `/stats/trend_by_fid` 每系列附 `delta`（近 7 日 vs 前 7 日，与活跃榜同源同窗）；分板块卡头新增「最活板块 7 日环比」统计卡，tooltip 每行尾附「· 7日 ↑/↓x%」 |
| 3 | 本月最热 9/1 的帖子到现在还是 NEW，口径是否有问题？ | **确有 bug（与 16.1 取反 bug 不同源）**：四种排序共用同一快照 key，且快照「仅保留当前榜条目」——切换排序会把其它排序的首见记录整体抹掉，切回来全部按「首见」重记，老帖反复全量标 NEW；快照文件还残留整数脏值实验 key | 快照 key 按排序分开（`month_top:{sort}`）；去掉按榜裁剪（掉榜回榜不重标）；历史污染逐值净化为「早已入榜」哨兵（合法日期不误伤）；等价单测 12 项全过，重启后切换排序 0 误标（hot 榜仅 1 条为当日真实首见） |
| 4 | 待下载推荐在清空任务后仍推荐已下载资源，是否合理？ | **不合理，与问题 1 同根因**（`downloaded_urls()` 只看任务列表） | 同问题 1 的下载履历修复，实测待下载 8 条与履历零重叠 |

**业界参照**：浏览器下载历史 / qBittorrent resume data（任务面板可清理，下载履历独立持久化）；Grafana / GA 对比图表的同期环比标注；微博热榜「新上榜」以该榜独立口径判定。
