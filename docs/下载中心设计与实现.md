# 下载中心（URL 批量下载）设计与优化建议

> 项目：txxy 数据展示项目（FastAPI + Vue3）
> 功能：前端任意 URL 链接一键提交下载，后端复用 `download_files.py` 异步批量下载到 `downloads/`，
> 支持单选、多选批量、进度跟踪、任务取消、历史持久化、并发可配。
> 状态：**已实施上线**；优化建议 v2 的 P0（D1-D4）与 P1（D5-D9）已于 2026-08-28 落地（见第十节）；进度实时性优化 R1/R2/R4 已于 2026-08-28 落地（见 11.3 实施记录），P2（D10/D11）与 R3/R5 待确认。
> 注：本文件原名 `docs/download_tasks.md`，2026-08-28 重命名为中文（与 docs/ 其余文档命名统一）。

## 一、功能概述

- 入口一：`帖子浏览`（`/posts`）表格新增多选列与「批量下载」按钮，操作列新增单行「下载」按钮；
- 入口二：`数据总览`（`/`）四个热门榜（点赞最高/回复最高/最新最热/本月最热）每行 hover 新增「下载」按钮；
- 下载中心（`/downloads`）：任务列表 + 实时进度条 + 逐 URL 明细 + 任务日志 + 取消/删除，3 秒轮询自动刷新；
- 下载完成后可在「资源管理」（`/resources`）查看已下载文件（扫描逻辑天然覆盖新目录）。

## 二、架构与数据流

```
前端（PostsView / DashboardView / DownloadsView）
   │  POST /api/downloads { urls: [] }          GET /api/downloads
   ▼                                                ▼
web/download_tasks.py  DownloadTaskManager（模块级单例）
   ├─ queue.Queue：任务排队（任务之间串行，避免网络并发拥塞）
   ├─ ThreadPoolExecutor：单任务内按 DOWNLOAD_CONCURRENCY 并行下载 URL
   ├─ 每个 URL → download_files.process_one(url)
   │     ├─ rmdown/.torrent → download_torrent
   │     ├─ 图片/视频直链   → download_media_direct（独立目录）
   │     └─ HTML 页面       → process_page（提取并下载图片/视频/种子/磁力/云盘）
   └─ JSON 持久化 → outputs/download_tasks.json（每步状态变更落盘，原子替换）
```

关键约束（与项目既有规范一致）：

1. Web 进程**只下载文件，不写库**（posts.db 仍为 scraper 独占写）；下载是文件系统操作，合规；
2. 复用 `download_files.py`：新增 `process_one(url)` 入口，CLI `main()` 行为零变化；
3. **不调用 `file_logger.setup()`**：该函数会重定向全局 stdout，Web 进程禁用（改用 `_ThreadLogCapture` 按线程收集，见 11.6）；
4. 任务日志 = 事件记录（创建/开始/逐 URL 结果/取消/完成）+ **该 URL 的完整下载过程明细**（正在请求/标题/保存目录/共提取到 N 个资源/逐文件 `[完成] xxx.jpg（字节数,链接）`），明细行带 `[序号/总数]` 前缀标注归属；最多保留最近 2000 条防膨胀（原 300 条不足以容纳明细）。

## 三、后端接口契约

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/downloads` | body `{urls: string[]}`；校验非空、≤ `DOWNLOAD_MAX_BATCH`、http/https；任务内去重；返回 `{id, count}` |
| GET | `/api/downloads` | 全部任务，按创建时间倒序 |
| GET | `/api/downloads/{id}` | 任务详情（状态/进度/逐 URL 明细/日志） |
| POST | `/api/downloads/{id}/cancel` | 取消（pending/running → cancelled，记录保留） |
| DELETE | `/api/downloads/{id}` | 删除记录（运行中先请求取消） |

任务字段：`id / status / urls / total / done / items[] / logs[] / created_at / started_at / finished_at / cancel_requested`。
`items[]` 每项：`url / status(ok|skip|fail|cancelled|pending) / stats(图片/视频/种子/磁力/云盘等数量) / error`。
状态机：`pending → running → done | failed | cancelled`。

## 四、前端交互

- `api/index.ts`：`request()` 扩展支持 `method`/`body`（JSON），新增 `post/del` 辅助与 5 个下载方法；POST/DELETE 默认不参与轮询去重（仅用户主动点击，避免同 key 顶掉已提交请求）；
- `DownloadsView.vue`：任务表格（状态 tag / 进度条 / 成功·跳过·失败汇总）+ 详情抽屉（逐 URL 明细 + 日志），`visibilitychange` 可见才轮询；

- `DashboardView.vue`：四个榜单卡片加 `Download` 图标按钮，`@click.stop.prevent` 阻断卡片跳转。

## 五、业务建议（参考业界下载管理器 / 任务队列实践）

1. **任务化 + 异步提交**：提交即返回任务 ID，后台执行；避免同步阻塞 HTTP 与线程池占满（FastAPI `BackgroundTasks` 只适合秒级任务，且无法跟踪进度/取消，故自建队列）；
2. **任务状态机 + 逐项明细**：每个 URL 独立成功/跳过/失败统计，失败项可追溯错误，后续可扩展「失败重试单个 URL」；
3. **去重幂等**：同任务内 URL 去重；重复文件复用 `download_files` 既有「已存在跳过」逻辑，不重复下载；
4. **限流保护**：默认并发 2 + 任务之间串行，配合 `DOWNLOAD_INTERVAL=0.3s` 与重试逻辑，降低源站封禁风险；
5. **取消能力**：处理下一个 URL 前检查取消标志，已提交并发项自然收尾；
6. **历史持久化**：任务列表落 JSON，服务重启不丢；中断的非终态任务恢复为 `failed` 并标注原因；
7. **下载中心独立页**：任务进度、日志、取消/删除集中管理，完成后一键跳转资源管理（业界下载管理器的标准形态）。

## 六、技术优化建议（当前未做，按需演进）

1. **失败重试**：`items` 已含逐 URL 状态，可加 `POST /api/downloads/{id}/retry` 仅重跑 `fail` 项；
2. ~~**日志流式化**：如需原始 stdout，可给 `process_one` 增加回调注入按 URL 采集输出~~ → **已于 2026-09-05 落地**（见 11.6）：采用按线程收集 stdout，未改动 `download_files` 接口；
3. **任务并发上限**：`DOWNLOAD_CONCURRENCY` 按「单任务内并行 URL 数」实现；如需多个任务并行，可加任务级信号量（默认任务串行已足够安全）；
4. **持久化文件轮转**：任务无限增长时 JSON 会变大，可按条数上限裁剪历史（如保留最近 200 个任务）；
5. **跨页多选保留**：帖子页翻页选中清空（el-table 默认行为）；如需跨页保留可加 `row-key` + `reserve-selection`。

## 七、风险与边界

| 风险 | 说明与对策 |
|---|---|
| 源站反爬/限流 | 默认并发 2 + 任务串行；环境变量 `TXXY_DOWNLOAD_CONCURRENCY` 可调低 |
| 进程重启丢运行态 | 运行中任务恢复为 `failed` 并标注「服务重启导致任务中断」，已下载文件保留 |
| 目录一致性 | `download_files.py` 的 `DOWNLOAD_ROOT` 固定为项目根 `downloads/`（基于脚本位置的绝对路径，支持 `DOWNLOADS_DIR` 环境变量覆盖，与 `web/config.py` 同源）；CLI 与 Web 页面下载输出目录恒定一致，且与进程 cwd/启动目录无关；`resources.py` 扫描根同为项目根 `downloads/`，下载完成即可见 |
| SSRF 面 | 接口仅校验 http/https 前缀，内网工具场景可接受；如需收口可加域名白名单 |
| 误提交 | 单次上限 `TXXY_DOWNLOAD_MAX_BATCH`（默认 50），超限 400 |
| 写盘失败 | 持久化 OSError 被捕获，仅跳过本轮落盘，内存任务继续执行，下轮自动重试 |

### 10.6 任务历史是否需要分页展示（评估结论：暂不实施，以「保留策略 + 筛选」替代）

**参考互联网模式**：
- GitHub Actions / Jenkins 构建历史：活跃任务常驻顶部，历史靠懒加载与筛选消化，而非传统分页；
- Motrix / aria2 WebUI：任务量增长主要靠「虚拟滚动 + 状态筛选」，分页仅用于超大规模列表；
- 网盘传输列表：进行中与历史传输分区展示，历史默认收起，同样不做传统分页。

**结合本项目现状的分析**：
1. **实时面板不宜传统分页**：下载中心 3s 轮询全量刷新，分页会导致翻页后数据「错位」（新完成任务挤动当前页、进行中任务滑出当前页），需额外做当前页锚定与增量 diff，复杂度高而收益低；
2. **历史规模已被主动控制**：D9 落地后持久化最多保留 200 条终态任务（`TXXY_DOWNLOAD_TASK_MAX_KEEP`），列表上限明确；任务列表为紧凑表格（每任务一行），200 条内一次性渲染无压力，配合 D3 状态筛选足以快速定位；
3. **明细已惰性加载**：逐 URL 明细与日志仅在「详情」抽屉打开时渲染，长历史的主要渲染与传输成本已被规避；轮询 payload 为任务概要级别，200 条规模可接受。

**演进阈值与路径**（出现任一情况再实施分页）：
- 任务历史确需长期留存（需要放宽或取消 200 条上限）；
- 单页任务数持续超过约 300 条，轮询 payload 与首屏渲染明显变慢；
- 届时方案：后端 `GET /api/downloads?offset=&limit=&status=` 分页且列表只返回概要字段（items 移至详情接口惰性加载），前端无限滚动；进行中/排队任务不受分页影响、始终全量返回；同时把 `download_tasks.json` 迁移为 SQLite（追加型历史数据更合适），避免大 JSON 反复整体重写。

> **决策更新（2026-09-07）**：用户确认实施任务列表分页——采用前端切片分页（每页 20、仅超一页时显示分页条，与链接明细同一模式），状态排序保证活跃任务置顶、不受翻页影响（见 11.8）。任务保留上限 200，无需虚拟滚动；若未来规模达数千条，再按上述演进路径迁移后端分页。

## 十一、进度实时性优化建议（2026-08-28 · 待确认）

> 背景：当前进度数据在后端是**实时**的（worker 每完成一个 URL 即更新内存并落盘），但展示端靠 **3s 轮询全量列表**（`GET /api/downloads`，含 items 明细与日志），进度最多滞后 3s，且轮询 payload 偏重。
> 参考互联网：**aria2 / webui-aria2 / Motrix** 用 WebSocket 实时推送任务进度；**AriaNg** 在连接中断时自动降级为轮询；**Vercel / GitHub Actions 构建日志**用 SSE（Server-Sent Events）流式推送；通用结论——单向服务器推送场景 SSE 优于 WebSocket（更轻、HTTP 原生、自动重连），WebSocket 优势在双向交互（本项目无此需求）。

### 11.1 建议清单（R 系列）

| # | 建议 | 参考来源 | 需后端 | 成本 |
|---|---|---|---|---|
| **R1 列表接口瘦身（概要化）** | `GET /api/downloads` 只返回任务概要：新增 `items_summary`（ok/skip/fail/pending 计数）替代完整 items，logs 不随列表下发；详情抽屉打开时才拉 `GET /api/downloads/{tid}` 全量（接口已有）。轮询/推送 payload 降一个数量级 | GitHub Actions / Jenkins 列表不含日志、详情按需加载 | 是（列表响应结构收窄，前端适配） | 低 |
| **R2 SSE 实时推送（核心建议）** | 新增 `GET /api/downloads/events`（`text/event-stream`）：服务端每 500ms 读取任务内存快照并与上次 diff，有变化才推 `task_update` 事件（id/status/done/total/items_summary）；前端 `EventSource` 订阅替代轮询，`onerror` 自动降级回轮询。实现取「SSE 端点内自 diff」最简形态——不需要 worker 线程到 asyncio 的桥接，SSE 只是传输层 | Vercel/GitHub Actions 流式日志；AriaNg 断线自动降级轮询；MDN EventSource 自动重连 | 是（一个流式端点 + 前端订阅） | 中 |

| **R4 进度条平滑过渡** | `el-progress` 百分比变化增加 CSS transition / 前端插值动画，消除轮询粒度带来的「台阶感」，视觉上接近连续实时 | 进度条平滑渲染通用实践 | 否 | 低 |

### 11.2 推荐组合与风险

- **推荐组合**：**R1 + R2 + R4**——R1 让推送/轮询都变轻，R2 提供亚秒级实时进度（SSE diff 粒度 500ms），R4 补足视觉连续性；R3 在 SSE 稳定后仅留作降级通道；R5 锦上添花。
- **SSE 风险与对策**：
  - 浏览器对同域 HTTP/1.1 连接数限 6 个，SSE 长连接占 1 个——下载中心单页单流，无影响；
  - 反向代理可能缓冲 SSE 流——响应头加 `X-Accel-Buffering: no` 预防（本机直连无代理，属前瞻防护）；
  - SSE 端点自 diff 的 500ms 快照对比开销极小（内存 dict 浅 diff），不落盘不查库；
  - EventSource 断线自动重连（内置），重连期间前端自动切回轮询，体验无断点。
- **实施顺序建议**：R1（先瘦身，列表结构变更前后端同步改）→ R2（SSE 端点 + 订阅/降级）→ R4（纯前端）。

> 确认方式：请回复要实施的条目（如「R1、R2 确认」），未确认前不实施；实施后本节将补充落地记录（沿用 10.5 格式）。

### 11.4 修复：check-dup 前端漏传请求体（2026-09-01）

**现象**：下载中心输入 URL 点「提交下载」必现 `POST /api/downloads/check-dup` → `422 Unprocessable Entity`，任务无法创建。

**根因**：后端 `DownloadCheckReq` 要求请求体 `{ "urls": [...] }`（`web/api.py`），而 `web/frontend/src/api/index.ts` 的 `checkDownloadDup` 只传了路径、没传 body——与紧邻的 `submitDownload`（`post('/downloads', { urls })`）写法不一致。FastAPI 收不到 `urls` 字段即返回 422。

**影响面**：`submitUrls()` 第一步就调用 `checkDownloadDup`，失败即抛出并中断，因此 **R1/R2 改造（2026-08-28）之后新建下载任务全程不可用**；后端接口本身一直是正常的。

**修复**：`checkDownloadDup` 补上 `{ urls }`。经排查，后端仅 `POST /downloads` 与 `POST /downloads/check-dup` 需要请求体，cancel / retry / prioritize / clear / delete 本就无 body，前端写法无需改动。

**验证**：不带 body → 422（复现）；带 body → 200；端到端点击「提交下载」时请求体为 `{"urls":[...]}`、响应 200、控制台无错误（真实创建用 mock 拦截，未产生下载副作用）。

**教训**：本次改造的自检只验证了后端接口（curl 带 body 通过），没有走过前端点击路径，属于测试盲区。新增 POST 端点后，前端调用与后端请求模型应成对自检。

### 11.5 重复提交判重增强（2026-09-01，P0）

**背景**：原 `dup_check` 依据「内存任务历史」（`status in ok/skip`）判重，而实际是否跳过由 `download_files` 依据磁盘决定（文件存在且非空即跳过）——两套依据不一致，导致两个真问题：

1. 用户清理过 `downloads/` 后再提交同一链接，提示仍是「已下载过、将跳过」；用户若信了提示而取消提交，该文件就再也下不回来（实际会重新下载，却被提示劝退）；
2. `pending` / `running` 未纳入判重，同一 URL 可重复提交，存在并发写同一文件的风险。

**原则**：判重依据与实际行为保持一致——是否跳过由磁盘决定，历史记录只用于提示，因此提示必须按「文件是否还在」分情况说明。

**改动**：

- 后端 `dup_check` 改为返回三类：`still_exists`（历史成功且保存目录仍在 → 提交后会被跳过）/ `gone`（历史成功但文件已不在 → 提交后**重新下载**）/ `running`（排队或下载中 → 有并发写风险）。新增 `_saved_dir_exists` 以磁盘为权威判据（保存目录存在且非空）；`saved_dir` 缺失时保守按「不在」处理——宁可提示会重新下载，也不要让用户误以为文件还在。
- API 新增响应模型 `DownloadCheckResp`，端点返回类型由 `dict` 改为该模型（原返回 `{"duplicated": [...]}` 已废弃）。
- 前端：`running` 类链接**自动剔除**并提示「已移除 N 个正在下载中的链接」（若全部被剔除则不提交）；`still_exists` 与 `gone` 在确认框中分别说明后果并列出前 3 个链接，URL 经 HTML 转义后拼入（防 XSS）。

**验证**：构造目录验证分类随磁盘状态切换（无目录 → `gone`；建目录 → `still_exists`；重命名 → `gone`；清理 → `gone`，测试目录用完即删）；提交不可达地址验证 `running=1`（随后删除测试任务）；端到端确认弹窗文案区分「文件仍在 / 文件已不在」。

**已实施（2026-09-07）：单链接「重新下载」**——详情抽屉链接明细每行「重新下载」按钮，调用 `retry_url` 把该链接重置为 pending 并重新调度**原任务**，只重跑这一条（结果停留在原任务详情内，不另开任务），对应原「`skip` 项单条强制重下」「强制重新下载」诉求；`ok`/`skip` 状态禁用以避免重复下载。
**未做（P1 及以后）**：记住选择、秒传式体验。

### 11.6 下载过程日志明细（2026-09-05 落地）

**背景**：任务详情日志只有「任务开始 / 每个 URL 的成功摘要 / 任务完成」，看不到下载过程。而 `download_files` 在 CLI 下会打印完整过程（正在请求 / 标题 / 保存目录 / 共提取到 N 个资源 / `[完成] 001.jpg（194356 字节,链接）`）——这套输出在下载中心里因为跑在线程池中而丢失，任务详情只剩骨架。

**原则**：**收集既有输出，不重写下载日志**。`process_one_detail` 的过程日志已经写好了，在下载中心再实现一遍就是重复造轮子，且两处口径迟早漂移。

**难点**：`sys.stdout` 是进程全局的，而下载是多线程并发执行——直接用 `contextlib.redirect_stdout` 会（a）多线程输出互相串扰，（b）劫持 Web 进程自身的 stdout（正是本文件 32-37 行所禁止的）。

**方案**：新增 `_ThreadLogCapture`（`web/download_tasks.py`），把 `sys.stdout` 包装为**按线程分发**：

- 执行下载的线程调用 `attach(buf)`，其 `print` 写入自己的缓冲区；
- 未 `attach` 的线程（Web 进程的正常输出）**原样转发真实 stdout**，行为与安装前完全一致，不劫持任何输出；
- 任务内每个 URL 结束后 `detach()`——线程池线程会复用，不 detach 会污染该线程后续输出。

`_run_one` 返回 `(stats, saved_dir, error, elapsed, detail_log)`，`_record_result` 把明细逐行追加到 `task["logs"]`，带 `    [i/N] ` 前缀（缩进表示明细从属于上面的结果摘要行）。日志上限由 300 提到 2000（一张图一行，300 会让早期 URL 的日志被挤掉）。

**验证**：

- 并发隔离：3 个线程各打印 4 行，各线程缓冲区只含自己的内容，无串扰；
- 未注册线程的 `print` 正常输出到控制台（未劫持）；
- 格式化：以模拟的下载过程输出验证，明细按 `[1/2]` 前缀、空行被过滤；
- 真实链路：重启服务后提交任务，`GET /api/downloads/{tid}` 的 `logs` 含「正在请求 / 重试 / 错误」全过程（测试任务已删除）。

### 11.7 done 口径修正 + 一致性自愈 + 交互增强（2026-09-07）

**背景**：任务 `9170f6652d` 出现「状态已取消、进度 50/50、明细 49 条已取消」的数据矛盾，排查确认是 `done` 计数口径错误，举一反三审查后一并修复。

- **`done` 口径修正（根因修复）**：`done` 现严格等于明细中 `ok + skip` 数量——`_record_result` 仅在链接成功/跳过时 +1（此前 `fail` 也计入）；`retry_url` 重置任务时 `done` 按 `ok+skip` 重算（此前把 `cancelled` 也计入）。进度条 `done/total` 从此与链接明细严格自洽。
- **`_load` 启动自愈（两层）**：① 终态任务按 `_finalize_status` 重新校准状态与 `done`，历史脏数据加载即修正，无需手动改持久化文件；② 非终态（重启中断）任务，除 `pending` 外 **`running` 项也一并置为 `cancelled`**——进程已崩溃，running 链接不可能继续，此前会永远停留在「正在下载」（任务已 failed 却存在 running 项）。
- **操作列「重试」扩展**：`cancelled`（已取消）任务与 `failed` 任务一致显示「重试」按钮（重跑全部未成功链接，复用既有 `POST /retry`，后端本就支持重跑 `cancelled` 项），此前已取消任务无任何重新下载入口。
- **链接明细分页**：详情抽屉链接明细改为前端切片分页（每页 20、仅超过一页时显示分页条），序号跨页连续；切换任务或筛选条件自动回到第一页。
- **明细行「重新下载」按钮修正**：tooltip 原文案「生成一个新的下载任务」与实际行为（本任务内就地重跑）不符，已更正；`running/pending` 行新增禁用（此前可点、依赖后端拒绝兜底）。

验证：`py_compile` / `vue-tsc --noEmit` / `read_lints` 全 0；磁盘全量 8 个任务按新口径重算自洽；`_load` 自愈以等价最小复现实测通过（构造含 `running` 项的崩溃任务，加载后 `running/pending→cancelled`、`done` 按 `ok+skip` 重算）。

### 11.9 排队中任务「取消」立即生效（2026-09-07）

**问题**：排队中（pending）任务点「取消」后状态仍是「排队中」，看似未取消。根因：`cancel()` 只设 `cancel_requested=True`，不改状态、不使队列元素失效——任务要等 worker 消费到它时才经 `_execute` 收尾为 cancelled；并发=1 且前面有任务在跑时，等待期可能很长（且收尾前还会打一条无意义的「任务开始执行」日志）。

**修复**：`cancel()` 分状态处理——`running` 保持原样（标志位，worker 在下一个链接前收手）；`pending` 立即把未跑链接置为 `cancelled`、任务进入 `cancelled` 终态，并复用 `prioritize` 的同一令牌失效机制（`_seq` 递增 + `_ticket` 换新 + `_queued=False`），worker 消费旧队列元素时校验不通过直接跳过，不会再次执行。立即终态的任务不再挂 `cancel_requested` 标志（语义干净，`_finalize_status` 按明细「有已取消项 → cancelled」判定一致，`_load` 自愈亦兼容）。

验证：等价最小复现实测通过——排队任务取消后 `status=cancelled`、全部链接 `cancelled`、`_queued=False`、旧令牌失效（worker 消费条件判定为跳过）、`_finalize_status` 一致；`running` 场景行为不变（仅设标志）。

### 11.10 「重试」改为原任务内重跑（2026-09-07）

**变更**：`POST /retry` 不再收集未成功项生成新任务，改为与单链接重下 `retry_url` 同一机制的多链接版——把 fail/cancelled/遗留 running 项重置为 pending（清空旧 stats/error/saved_dir/elapsed）、任务重置为可调度状态（`done` 按 ok+skip 重算）、重新入队由 worker 只跑 pending 项。进度、日志、明细全部留在原任务上，列表不再出现成对的「原任务 + 重试任务」。

**新增保护**：进行中（pending/running）任务调用 retry 直接拒绝（返回 0 → 400）——reset 一个正在执行的任务会导致两个线程并发跑同一任务，这是原「生成新任务」实现不存在的新风险，改为原地重跑后必须显式拦截。

验证（等价最小复现，monkey-patch 禁用 worker 零网络）：failed 任务（1 ok + 1 fail + 1 cancelled）retry 后任务数不变、fail/cancelled 重置为 pending 且旧结果清空、ok 保留、`done=1`、重新入队；done 任务返回 0 状态不变；running 任务拒绝；不存在任务返回 None。`py_compile` / `vue-tsc` / `read_lints` 全 0。

### 11.11 「清空已完成」口径变更：只清 done，保留失败/已取消（2026-09-07）

**变更**：`POST /downloads/clear`（`clear_finished` → `clear_done`）从「删除全部终态任务」改为**只删 done**——failed / cancelled / running 一律保留。按钮文案、预检提示、确认弹窗同步对齐（弹窗明示「失败 / 已取消任务会保留」）。

**口径分裂说明（有意为之，用途不同）**：手动清空只删已完成（用户不想误删失败/取消任务，失败项是后续重试的依据）；自动轮转 `_prune_locked` 仍按全部终态从旧到新裁剪（上限 200，防持久化 JSON 无限膨胀，若失败/取消任务不参与轮转会永久堆积）。两者一个管「用户主动清理的意愿」，一个管「存储上限的兜底」，不共用口径。

验证：等价复现实测——4 个任务（done/failed/cancelled/running 各一）执行后删除数 1、剩余 `['c1','f1','r1']`；`py_compile` / `vue-tsc` / `read_lints` 全 0。

### 11.12 下载提交入口统一为共用 composable（2026-09-07）

**背景**：数据总览热门榜「下载」按钮此前直接 `submitDownload`——无防连点、无判重，与帖子浏览（11.8 末接入 D2）不对等；重复点击每次都创建任务。

**变更**：帖子浏览的 D2 判重提交逻辑（防连点 + check-dup 三分类 + 确认弹窗 + 提交）抽为共用 composable `composables/useDownloadSubmit.ts`，三处入口（下载中心页内提交 / 帖子浏览 / 数据总览）行为完全一致，消除第三份复制：

- `useDownloadSubmit()` 返回 `{ submitting, submitDownload }`；`submitting` 守卫拦截连点（帖子浏览批量按钮 `:loading` 继续绑定）；
- 通知钩子 `DownloadSubmitNotify`（success/error/warning/beforeDialog）：数据总览**真全屏时 ElMessage/ElMessageBox 挂在 body 上不可见**，须先 `exitFullscreen()` 再提示/弹窗（此前仅成功/失败提示做了处理，确认框路径此前不存在故无此问题）；不传钩子则默认 `ElMessage`（帖子浏览等常规页面零配置）；
- `PostsView` 删除本地实现改用 composable（`ElMessageBox`/`briefList` 导入随之移除）；`DashboardView.downloadUrl` 传入四个钩子接入。

验证：`vue-tsc --noEmit` / `read_lints` 全 0（三个改动文件）；行为与 11.8 中帖子浏览交互逐项一致（同一 composable）。

### 11.13 排队任务展示顺序与执行顺序对齐（2026-09-07）

**问题**：用户观察「最新提交的任务排在最前、当前任务完成后先下载最新的」。核实：**执行顺序没有插队**——`downloads_submit` 以默认 `priority=False` 入队 `(1, seq, tid)`，`PriorityQueue` 同优先级按 `seq` 升序出队，是严格 FIFO（除非显式点「优先执行」，其置顶语义为队列优先级 0）；**误导来自展示排序**——前端此前对排队中任务按创建时间倒序展示，与 FIFO 执行顺序正好相反。

**修复**：后端 `_public` 以 `ticket` 名义暴露队列令牌（原为 `_ticket` 内部字段；仅影响 API 输出，不进持久化文件，SSE 快照同构自动携带）；前端排序改为——排队中/进行中组内按「置顶标记优先 + `ticket` 升序」，与出队顺序完全一致；终态保持创建时间倒序。此后「列表中排队任务的上下位置」即「实际执行顺序」。

验证：`py_compile` / `vue-tsc --noEmit` / `npm run build` 全过（构建产物 21:xx 更新），`read_lints` 0 诊断。

**注意**：新增参数曾与 `_record_result` 内已有的局部变量 `detail`（结果行尾的统计文案）**撞名被覆盖**，导致只输出统计摘要一行——现已将二者分别命名为 `detail_log`（过程日志）与 `reason`（结果说明），避免同类混淆。
