# 定时抓取调度（页面可配置）调研与建议

> 项目：txxy 采集·管理·展示一体化工具（FastAPI + Vue3）
> 触发问题（用户）：本地启动服务后需要定时执行 `run_batch.py --restart`，**能否在页面上配置调度**？
> 状态：**已实施（2026-09-16）**，采用方案 A（应用内调度器 + 页面配置）；用户确认的四项决策见第 7 节，实施记录见第 8 节。
> 结论先行：**可行，且推荐做成「应用内调度器 + 页面配置」**；但落地前必须先解决两件事——① 与已有的两处 OS 级定时**二选一**（否则同一天会抓两次）；② 补齐 `start_run` 的防重窗口。

---

## 一、现状盘点（本项目已有的调度入口）

| 入口 | 机制 | 改时间的方式 | 存在的问题 |
|---|---|---|---|
| Windows 计划任务 `txxy_daily_batch` | 每天 01:00 以 SYSTEM 身份跑 `run_daily.bat`（内含 `run_batch.py --restart`），README §定时任务有 schtasks 命令 | `schtasks /Change`（需管理员） | 页面看不到、改不动；web 未运行时也照跑 |
| Docker `cron` 服务 | `profiles: ["cron"]`，每日 01:00 跑 `run_batch.py false`（`docker/txxy_cron`） | 改 `docker/txxy_cron` 后**必须 `--build` 重建镜像** | 页面看不到；与宿主机计划任务**必须二选一**（《Docker部署方案.md》13.2.3 已写明，否则双倍抓取） |
| 页面「启动抓取」按钮 | `POST /api/runs/start` → `runs.start_run(use_local_proxy, restart)` | — | 手动触发，无定时能力 |

既有的关键约束（新方案必须遵守）：

1. **全项目同时只允许一个抓取批次**：`runs.has_active_run()` 防重（并发抓取会互踩 CSV/SQLite 与运行记录）；
2. **唯一执行入口是 `runs.start_run()`**：已包含子进程拉起（`CREATE_NO_WINDOW`）、pid 落盘（`outputs/run_batch_web.pid`，web 重启后仍可强杀）、启动期输出留痕（`outputs/run_batch_web.log`）、`run_days` 记录由脚本自身写入；
3. `run_days` **每次运行一条、同日多次运行各自成条**（数据模型支持一天多时刻）；
4. 参数一律走 `settings.WHITELIST`（「页内设置 > 环境变量 > 默认值」三层），不新开配置源。

## 二、业界做法（三种调度归谁管）

| 形态 | 代表 | 谁保证执行 | 适合的语义 |
|---|---|---|---|
| **OS 层定时** | cron、systemd timer（`Persistent=`）、Windows 任务计划程序、K8s CronJob | 操作系统/编排器 | 「必须每次都跑」，与业务进程解耦；**改配置要碰系统**，应用看不到 |
| **应用内调度** | APScheduler（`BackgroundScheduler` + 持久化 JobStore）、Celery beat、RQ Scheduler、Django-Q | 应用进程 | 「应用在线时按计划跑」，配置与展示都在应用里；进程不在则不跑 |
| **外部编排 / SaaS** | GitHub Actions `schedule`、Vercel Cron、Airflow（`catchup`） | 平台 | 应用本身无状态；平台明确可能延迟/丢弃（GitHub 官方即声明高负载时会延后甚至跳过） |

业界的三个共识（对本项目直接适用）：

1. **「错过执行」必须显式定义策略，不能默默丢**：cron 的语义是「进程不在就不跑」；systemd timer 要 `Persistent=true` 才补跑；Airflow 用 `catchup` 开关 + `start_date` 限定补跑范围。本项目必须把「web 没开着 / 机器关机 / 上一批还在跑」三种情况的处理写成明确策略并在页面上显示原因。
2. **触发要幂等**：调度的判据是「(计划时刻, 日期) 是否已触发过」并持久化，而不是「现在几点」——否则重启/多线程/时钟回拨都可能重复触发（APScheduler 的 JobStore、Airflow 的 DagRun 唯一性都是这个思路）。
3. **「页面可配置」基本等于「应用内调度」**：要让页面展示「下次执行时间、上次结果、跳过原因」，调度状态就得在应用能读到的地方；把配置写进 OS 计划任务/容器 cron 会立刻产生**双向同步问题**（页面改了、系统没改；系统被手工删了、页面还显示已启用）。

## 三、方案对比与推荐

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 应用内调度器 + 页面配置**（推荐） | 零新依赖（单线程 tick 即可，本项目已有自研线程队列先例）；配置与页面同源、唯一事实源；改时间即时生效、无需重启/重建/管理员权限；Windows / Docker / 离线机行为一致；可展示下次执行与跳过原因 | web 进程不在跑则不执行；与已有 OS 级定时**必须二选一** | **推荐**。本项目定位是「本机自用、看板常驻」，进程在线即可用；离线镜像与容器同样适用 |
| B. 页面写 Windows 计划任务（`schtasks`） | OS 保证执行（web 不在也跑） | 需权限；平台绑定（Docker/Linux 无效）；页面与系统双向同步；与现有 `txxy_daily_batch` 重复 | 不建议作为主方案；可作为「保证 web 常驻」的辅助手段 |
| C. 维持现状（OS 定时 + 页面只读展示） | 改动最小 | 需求未满足（页面上仍配置不了） | 仅作为过渡 |

**落地形态（推荐 A + 一个显式的互斥提示）**：

- 页面启用「定时抓取」时，检测到 OS 计划任务 `txxy_daily_batch` 或容器 cron 服务存在时给出提示，并要求二选一；
- 在文档中同步写明：**同一时刻只应有一处调度在跑抓取**（沿用《Docker部署方案.md》既有口径）。

## 四、落地设计（页面 / 后端 / 存储）

### 4.1 后端：新增 `web/scheduler.py`（单线程 tick）

```
app.py startup 钩子 → scheduler.start()（守护线程，60s tick）
每个 tick：① 读配置（settings）→ ② 命中「(计划时刻, 今天)」且未被触发过？
          → ③ 幂等/重入检查 → ④ runs.start_run(use_local_proxy, restart) → ⑤ 记录触发结果
```

- **tick 而非 sleep 到点**：休眠唤醒、时钟跳变后仍能正确判定；tick 间隔 60s（最小粒度为分钟，与用户配置的 HH:MM 对齐）。
- **幂等键 = (日期, 计划时刻)**，落盘 `outputs/scrape_schedule_state.json`（复用 `atomicfile.write_json_atomic`，与下载任务/回收站索引同一套原子写）；同一分钟内重启 web 不会重复触发。
- **重入检查要做两道**：`runs.has_active_run()`（DB 里的 running 记录）+ `runs.active_pid()`（pid 文件）。**为什么必须加第二道**：`start_run` 拉起的子进程要到它自己建 `running` 记录（`run_batch.main` 里）之前有几秒空窗，调度若正好落在这个窗口，会同时跑两个批次——这属于本项目既有的防重缺口，实施调度前应一并补上（对手动「启动抓取」同样有益）。
- **失败不自动重试**：抓取内部已有请求级重试（退避递增），调度层再重试只会与源站限流叠加。失败仅记录 + 页面提示（可选：失败后 30 分钟重试一次，需用户决策）。
- **不改 web 的只读边界**：调度只调用 `start_run`（拉子进程），落库仍由 `run_batch`/`scraper` 自己完成，与「Web 进程严禁写库」的既有约定一致。

### 4.2 配置项（`settings.WHITELIST` 新增，遵循既有三层优先级）

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `scrape_schedule_enabled` | bool | `false` | 总开关（默认关闭，与 Docker cron「默认不启用」一致） |
| `scrape_schedule_times` | array/text | `["01:00"]` | 计划时刻列表（支持一天多次；`run_days` 同日多条已支持） |
| `scrape_schedule_weekdays` | array | 每天 | 仅在这些星期触发（可选，按需再加） |
| `scrape_schedule_restart` | bool | `true` | 对应 `--restart`（用户举例的就是全量重跑） |
| `scrape_schedule_use_proxy` | bool | 与手动弹窗默认一致 | 对应 `run_batch.py [true\|false]`（本地 1024 镜像 / 直连） |
| `scrape_schedule_missed` | enum | `skip` | 错过策略：`skip`（cron 口径，默认）/ `catchup_same_day`（systemd Persistent 口径，仅补当天） |

> 不建议用「cron 表达式」输入框：对非技术使用者易错且无预览（Windows 任务计划程序、Vercel Cron、Grafana 都用枚举式/预设）。用「时刻列表 + 星期选择」的显式控件，页面即时算出「下次执行时间」（与调度同源计算，避免两处口径不一致）。

### 4.3 页面（放「参数设置」页新增「定时抓取」分组）

- 开关 + 时刻列表 + `--restart` / 镜像开关 + 错过策略；
- **状态区**（只读，来自 `/api/config` 或新增 `/api/schedule`）：启用状态、下次执行时间、上次触发结果（启动成功 / 跳过原因 / 失败原因）、最近一次批次的链接（跳运行记录页）；
- 「立即运行一次」按钮（复用现有手动入口，便于验证配置）；
- 设置页已有的「生效范围」标注机制可复用（调度类参数为「保存即生效」）。

### 4.4 边界与风险

| 风险 | 处理 |
|---|---|
| 与 OS 计划任务 / 容器 cron 重复触发 | 页面提示 + 文档写明二选一（**必须做**，否则一天两次全量抓取） |
| web 未运行期间错过 | `skip` 默认（与 cron 一致）；要补跑则显式选 `catchup_same_day`（不补陈年批次） |
| 上一批仍在跑（常规情况：抓取 25–40 分钟） | 跳过本次并记录原因「上一批仍在运行」，页面可见；不排队堆积 |
| 一天多次 = 多次全量抓取 | 页面显示「一天 N 次」的显式提示（对源站压力与耗时都需用户知情） |
| 笔记本休眠/唤醒、时区 | 按本地时间；tick 中发现「已越过计划时刻但已超过容差」时按 `missed` 策略处理并记原因 |
| 容器/多实例 | 多实例会各自调度 → 限定单实例或在文档写明（本机自用场景暂不引入分布式锁） |

## 六、不推荐的做法（已评估排除）

1. **页面上直接改 `docker/txxy_cron` 或注册 `schtasks`**：双向同步必然漂移，且 Docker 改时间需重建镜像、Windows 需管理员权限，与本项目「单人自用、零配置负担」的定位冲突；
2. **引入 APScheduler / Celery**：本项目只有「每天固定时刻跑一个子进程」这一个调度需求，自研 60s tick + 幂等状态即可覆盖（与下载队列「不重复造轮子、也不过度设计」的既有取舍一致）；一旦出现「错峰、依赖关系、任务链」等需求再引入；
3. **页面调度与 OS 定时并行运行**：会产生同一时刻两个全量批次（源站双倍请求、CSV/进度文件互相覆盖），必须二选一。

### 8.2 实际行为（与调研结论一致）

- 计划时刻每天两次（08:00 / 20:00），保存后**立即生效**，无需重启；
- **幂等**：判据是「(日期, 计划时刻) 是否已处理」并落盘 `outputs/scrape_schedule_state.json`，重启、多 tick、时钟回拨都不会重复触发；
- **错过策略**：晚于计划时刻超过 10 分钟（容差）即视为「当时服务未运行」→ 记一次「未执行」到状态里（页面可见原因），**不补跑**；
- **重入保护**：`has_active_run()` 或 `active_pid()` 命中即跳过本次并记「上一批抓取仍在运行」；
- 启动失败（防重 / 进程拉不起来）把 `ValueError` 原文记入状态，页面「上次结果」显示「启动失败 + 原因」。

### 8.3 实测（2026-09-16）

- **判定逻辑（等价片段：直接驱动 `tick(注入 now)` + 打桩 `runs.start_run`，绝不真的抓站）14 项断言全通过**：到点触发一次 / 同一时刻不重复 / 重启后不重复 / 当天第二时刻触发 / 错过记「未执行」且不触发 / 上一批在跑则跳过（`active_pid` 与 `has_active_run` 两条判据各测一次）/ 启动失败记原因 / 关闭开关不触发也不消费时刻 / 时刻规格化 / 无时刻时下次执行为空 / 状态落盘结构。
- **真实服务端到端 10 项断言全通过**（独立 8089 实例 + 临时状态/设置/任务/履历文件，零抓取）：默认启用且时刻为 08:00/20:00、调度线程心跳在推进、启动前错过的 08:00 记「未执行（已过计划时刻 154 分钟（当时服务未运行））」且绝不触发、改时刻后状态立即变化、非法时刻被规格化、关闭开关后下次执行为空、**真实命中 `runs.active_pid()` 走 skipped 分支**（用「写一个活着的 python pid 到 pid 文件」构造，测完恢复原文件）、跳过的时刻计入今日已处理、恢复默认后回到 08:00/20:00。
- **浏览器实测 12 项断言全通过**（桌面 1440×1000 + 移动 390×844）：分组与状态区渲染、时刻列表增删后保存生效、保存后状态区同步刷新、移动端时刻控件未被挤出视口。「立即运行一次」只断言存在可用——点击会真的启动 25~40 分钟抓取批次，不在测试中触发（其调用的是「运行记录」页同一 `startRun` 接口，已有实测覆盖，此处如实交底）。
- `py_compile` / `npx vue-tsc --noEmit` / `read_lints` / `npm run build` 全部 0 问题。

### 8.4 实施中发现并修掉的两个问题

1. **`next_run_at` 口径错**：初版只找「已到点且未处理」的时刻，导致 08:05 时显示的下次执行直接跳到明天 08:00（漏了今天 20:00）；改口径时又发现另一种错——把「早已过容差、接下来只会被记为未执行」的历史时刻显示成「下次执行」（页面出现「下次执行 2026-09-16 00:00」这种过去的时刻）。最终口径：**下次执行 = 今天最早一个「还会真的跑起来」的时刻（未到点，或刚过点仍在容差内）；没有则明天第一个时刻**。
2. **`python web/app.py` 起不来**（8.1 中 `settings.py` 那条）：`settings.py` 顶层 `import download_files` 发生在 `app.py:main()` 的 sys.path 自举之前——这是上一轮复核时交底过的既有问题，本次因新增调度需要按此方式启动测试实例而顺手修掉。

### 8.5 运维提醒

### 8.6 上线当天暴露的两个问题与修复（2026-09-16，用户上报）

**用户上报**：① 点了「立即运行一次」，批次在跑，但卡片状态没变化；② 连点 2 次，出现了 2 个批次。

**取证结论（先看现场再动手）**：

- `run_days` 确实出现两条今日记录：**ID=135 与 ID=136**，`created_at` 同为 11:05:59、各自 ok=6 / fail=7；
- `outputs/20260916/` 下有**两个批次日志**（`run_batch_20260916_110551.log` / `..._110557.log`）与 26 个 scraper 日志（13 版块 × 2）；
- 两个批次**各起了一个 1024 镜像 web.exe，并各自「按端口定位强制结束占用进程」把对方刚起的镜像杀掉**——这正是 7 个版块全部「目标计算机积极拒绝」而失败的直接原因；
- 第二批次**没有留下 `===== Web 触发 ...` 头**（全文件只有 11:05:51 那一条），调度状态文件里也只有 08:00 的「未执行」记录（即**定时调度没有触发任何批次**），Windows 计划任务已删除、Docker 未运行。⇒ 第二批次的确切启动者无法从现场确证（页面并发触发的窗口、或页面之外的启动方式都符合证据），**但两个缺陷无论如何都要堵**。

**修复（两条，按业界做法）**：

1. **触发入口原子化**（`web/runs.py`）：`start_run` 的「检查 → 拉起进程 → 落 pid 文件」整体放进 `threading.Lock`。此前两次并发触发会**双双通过检查**（进程还没写 running 记录、pid 文件也还没落），各拉起一个批次。业界口径：**服务端必须保证幂等/互斥，不能只靠前端按钮的 loading 态**。
2. **执行侧 Job 级单实例锁**（`run_batch.py`）：启动 1024 镜像**之前**用 **OS 级文件锁**（Windows `msvcrt.locking` / POSIX `fcntl.flock`，非阻塞）抢占 `outputs/run_batch.lock`，抢不到即打印「已有另一个批次在跑，本次不启动」并退出。这样无论触发来自页面、控制台、计划任务还是容器 cron，都不可能同时跑两个批次。要点：
   - **用 OS 级锁而不是「pid 文件 + 存活检查」**：进程被强杀/崩溃时操作系统自动释放，不存在「残留锁把后续批次永久挡住」的问题，也不依赖 psutil；
   - **锁加在偏移 1024 处、持有者 pid 写在文件头**：Windows 的字节范围锁是**强制锁**，若锁住内容所在字节，排查时连读都读不了（实测 `PermissionError`）；
   - **写在拿到锁之后**：抢锁失败的一方不能改这个文件，否则会把持有者覆盖成自己（实测踩到，A3 用例暴露）。
3. **状态可见**（`web/scheduler.py` + 设置页）：`GET /api/schedule` 新增 `running`——`state="running"` 带批次 `#id` 与已运行分钟；`state="starting"` 表示进程已拉起、运行记录还没写（脚本启动期几秒空窗）。设置页「定时抓取」组新增**当前状态**行（含「查看进度」跳运行记录）、运行中**禁用「立即运行一次」**并给出原因悬浮（按钮可用性与后端守卫同源，避免点了才报错），并加 5 秒轮询（页面不可见时暂停）——批次一跑就是 25~40 分钟，状态必须自己刷新。

**实测（2026-09-16）**：

- 判定与互斥 **12 项断言全通过**：真实跨进程锁（父进程持锁 → 子进程 BLOCKED；释放后可获取；无持有者的残留锁文件不挡后续批次）、两线程并发触发**只拉起一个批次**、顺序再触发被拒、触发头与 pid 文件均在锁内落盘、**临界区并发深度恒为 1**（严格串行）、调度状态 running 三态。
- **真实服务 + 浏览器 9 项断言全通过**：空闲 → 写入一个活着的 pid 模拟「运行中」→ 接口 `state=starting` → **不刷新页面**卡片自动变为「批次正在启动（等待写入运行记录）…」+ 按钮禁用 + 悬浮可见原因 +「查看进度」入口 → 移走 pid 后卡片自动回到「空闲」且按钮恢复。
- 「批次 #id 运行中（已 N 分钟）」这一支（需要真实的 running 记录）是**进程内验证**（C1），没有为了测试往真实库里插记录——如实交底。
- 顺带修复：本次改动一度漏了 `web/runs.py` 的 `import threading`（模块级建锁会 NameError → 服务启动即失败），**是测试一跑就暴露的**（`py_compile` 与 IDE 诊断均未报）。
