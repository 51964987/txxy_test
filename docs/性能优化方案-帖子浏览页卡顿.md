# 帖子浏览页 SQL 性能排查与优化方案
> 注：本页为独立性能专项文档（帖子浏览页 /api/posts 分页与索引优化），不与「数据总览大屏」汇总文档合并。

## 1. 现状与数据规模

| 项目 | 数值 |
|---|---|
| 数据库文件 | `db/posts.db`，约 71.6 MB |
| 总记录数 | 122,003 条 |
| 前端页面 | `PostsView.vue` → `/api/posts` |
| 默认分页 | `page_size = 50` |
| 排序字段 | `date`、`created_at`、`likes`、`replies`（均支持正/倒序） |

## 2. 涉及的 SQL 语句

### 2.1 列表查询

```sql
SELECT title, fid, date, url, likes, author, replies, created_at, update_at, update_date
FROM posts
WHERE ...
ORDER BY <排序列>
LIMIT ? OFFSET ?;
```

前端支持以下排序：

| 排序名 | ORDER BY 片段 |
|---|---|
| 日期倒序 | `date DESC, created_at DESC` |
| 日期正序 | `date ASC, created_at ASC` |
| 入库时间倒序 | `created_at DESC` |
| 入库时间正序 | `created_at ASC` |
| 点赞数倒序 | `CAST(likes AS INTEGER) DESC, date DESC` |
| 回复数倒序 | `CAST(replies AS INTEGER) DESC, date DESC` |

### 2.2 总数统计

```sql
SELECT COUNT(*) FROM posts WHERE ...;
```

### 2.3 导出 CSV

```sql
SELECT ... FROM posts WHERE ... ORDER BY ...;
```

无分页，可能一次性返回全量数据。

## 3. 当前索引

```sql
CREATE INDEX idx_posts_author       ON posts(author) WHERE author IS NOT NULL AND author <> '';
CREATE INDEX idx_posts_created_at   ON posts(created_at);
CREATE INDEX idx_posts_date         ON posts(date);
CREATE INDEX idx_posts_fid          ON posts(fid);
CREATE INDEX idx_posts_fid_date     ON posts(fid, date);
CREATE INDEX idx_posts_likes_expr   ON posts(fid, CAST(likes AS INTEGER), date, created_at);
CREATE INDEX idx_posts_replies_expr ON posts(fid, CAST(replies AS INTEGER), date, created_at);
```

## 4. 实测结果（短连接、每场景 3 次取中位数）

### 4.1 分页查询

| 场景 | 执行计划 | 耗时 | 问题 |
|---|---|---|---|
| `date_desc` | `SCAN posts USING INDEX idx_posts_date` + `TEMP B-TREE` | 3.24 ms | 轻微 temp sort |
| `date_asc` | `SCAN posts USING INDEX idx_posts_date` + `TEMP B-TREE` | **170.87 ms** | 正序扫描+回表排序 |
| `created_at_desc` | `SCAN posts USING INDEX idx_posts_created_at` | 0.84 ms | 良好 |
| `created_at_asc` | `SCAN posts USING INDEX idx_posts_created_at` | 0.96 ms | 良好 |
| `likes_desc` 全表 | `SCAN posts` + `TEMP B-TREE FOR ORDER BY` | **98.64 ms** | 全表扫描排序 |
| `replies_desc` 全表 | `SCAN posts` + `TEMP B-TREE FOR ORDER BY` | **100.65 ms** | 全表扫描排序 |
| `likes_desc + fid=7` | `SEARCH posts USING INDEX idx_posts_likes_expr` | 1.81 ms | 良好 |
| `replies_desc + fid=28` | `SEARCH posts USING INDEX idx_posts_replies_expr` | 2.25 ms | 良好 |
| `fid IN (7,28)` | `SEARCH posts USING INDEX idx_posts_fid` + `TEMP B-TREE` | **31.03 ms** | 多值+排序回表 |
| `date 范围` | `SEARCH posts USING INDEX idx_posts_date` + `TEMP B-TREE` | 4.73 ms | 轻微 temp sort |

| `fid + date + q` | `SEARCH posts USING INDEX idx_posts_fid_date` + `TEMP B-TREE` | 19.01 ms | 有 fid+date 时 LIKE 仍要逐行匹配 |

### 4.3 导出 CSV（首 2000 条）

## 5. 根因分析

1. **`date_asc` / `date_desc` 的复合排序未完全走索引**
   - 现有 `idx_posts_date` 只有 `date` 一列。当 `ORDER BY date, created_at` 时，SQLite 按 date 索引扫描后仍需对 `created_at` 建临时 B-tree 排序（`USE TEMP B-TREE FOR RIGHT PART OF ORDER BY`）。
   - `date_desc` 数据最新，很快命中 LIMIT；`date_asc` 需要从头扫描并回表大量行，导致 170 ms。

2. **全局 `likes_desc` / `replies_desc` 缺少单列表达式索引**
   - 现有 `idx_posts_likes_expr` / `idx_posts_replies_expr` 的前缀是 `fid`，只适合“按版块查 top”。
   - 当用户不按版块、只按点赞/回复排序时，优化器无法使用这些索引，只能全表扫描 + 外部排序，耗时 ~100 ms。

3. **`title LIKE '%xxx%'` 前导通配符无法利用 B-tree 索引**
   - `title` 是 `TEXT PRIMARY KEY`，但前导 `%` 的 LIKE 只能全表/全索引扫描并逐行匹配，172 ms / 87 ms 是大表通病。
   - 这是整个帖子浏览页最严重的性能瓶颈。

4. **每次翻页执行两次查询（COUNT + SELECT）**
   - 虽然 COUNT 大部分场景可用覆盖索引，但遇到模糊搜索、深 OFFSET 时仍会被动放大。

5. **导出 CSV 无分页、返回字段冗余**
   - 列表接口和导出接口共用 `_SELECT_COLS`，列表页其实不需要 `update_at` / `update_date`。

## 6. 优化建议

### 6.1 索引层（低风险、立即见效）

#### 6.1.1 增加 `date + created_at` 复合索引

```sql
CREATE INDEX IF NOT EXISTS idx_posts_date_created
    ON posts(date DESC, created_at DESC);
```

- **效果**：`date_desc` / `date_asc` 的 `ORDER BY` 可完全由索引顺序满足，消除 temp B-tree；预计 `date_asc` 从 170 ms 降至 5 ms 以内。
- **注意**：SQLite 索引支持双向扫描，单列方向不影响 `date_asc` 使用。

#### 6.1.2 增加 `fid + date + created_at` 复合索引

```sql
CREATE INDEX IF NOT EXISTS idx_posts_fid_date_created
    ON posts(fid, date DESC, created_at DESC);
```

- **效果**：`fid IN (...) ORDER BY date DESC, created_at DESC` 可直接走索引顺序，预计从 31 ms 降至 3 ms 左右。

#### 6.1.3 增加全局 `likes / replies` 表达式索引

```sql
CREATE INDEX IF NOT EXISTS idx_posts_likes_num
    ON posts(CAST(likes AS INTEGER) DESC);

CREATE INDEX IF NOT EXISTS idx_posts_replies_num
    ON posts(CAST(replies AS INTEGER) DESC);
```

- **效果**：全局 `likes_desc` / `replies_desc` 从全表扫描排序变成索引扫描，预计从 100 ms 降至 5–10 ms。
- **注意**：`idx_posts_likes_expr(fid, CAST(likes AS INTEGER), ...)` 仍保留，用于“按版块 top”。

### 6.2 搜索层（中风险、收益最大）

#### 6.2.1 引入 FTS5 全文索引（推荐）

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS posts_fts USING fts5(
    title,
    content='posts',
    content_rowid='rowid'
);

-- 初始化同步已有数据
INSERT INTO posts_fts(rowid, title)
    SELECT rowid, title FROM posts;
```

抓取写入侧（`web/db.py` 或抓取脚本）在 `INSERT/UPDATE/DELETE posts` 时同步维护 `posts_fts`。

- **效果**：`title LIKE '%AI%'` 改为 `posts_fts MATCH 'AI'`，通过倒排索引定位，预计从 170 ms 降至 5–20 ms。
- **收益**：这是模糊搜索场景唯一可靠的根治方案。
- **风险**：需要同步维护 FTS 表；`title` 更新较少，维护成本低。

#### 6.2.2 折中方案：限制模糊搜索必须搭配其他条件

在 UI/API 层增加校验：当 `q` 非空时，必须同时提供 `fid` 或 `date_from/date_to`。

- **效果**：把全表 LIKE 变成“小范围过滤 + LIKE”，可借用 `idx_posts_fid_date` 等索引减少扫描行数。
- **收益**：改动最小，但不改变 LIKE 本质，深数据下仍会慢。

### 6.3 应用层

#### 6.3.1 拆分列表/导出字段

```python
_SELECT_LIST = "title, fid, date, url, likes, author, replies, created_at"
_SELECT_EXPORT = "title, fid, date, url, likes, author, replies, created_at, update_at, update_date"
```

- **效果**：列表查询减少两列回表，略微降低 I/O；`update_at` / `update_date` 只在导出时返回。

#### 6.3.2 COUNT 缓存/估算

- 对“默认首页”和“固定版块首页”等高频 COUNT，可在服务端缓存 30–60 秒。
- 对模糊搜索场景，可改为不显示精确总页数，使用“加载更多”/无限滚动，避免精确 COUNT。

#### 6.3.3 导出限制与后台化

- 对 `/posts/export` 增加 `limit` 上限（如 5000 条）和导出条件校验。
- 大导出改为后台任务 + 文件下载链接，避免阻塞 API 进程。

#### 6.3.4 深分页优化（keyset pagination）

当数据量持续增长时，用游标分页替代 `OFFSET`：

```sql
-- 替代 OFFSET 10000
SELECT ... FROM posts
WHERE date < ? OR (date = ? AND created_at < ?)
ORDER BY date DESC, created_at DESC
LIMIT 50;
```

- **效果**：避免深 OFFSET 时扫描并丢弃大量行。
- **成本**：前端需改为基于“上一页最后一条”的无限滚动，传统页码需要额外记录游标。

## 8. 推荐实施顺序

| 优先级 | 措施 | 风险 | 预期效果 |
|---|---|---|---|
| P0 | ✅ 已加 `idx_posts_date_created` | 极低 | `date_asc` 从 170 ms → 1.75 ms |
| P0 | ✅ 已加 `idx_posts_likes_num` / `idx_posts_replies_num` | 极低 | 全局 likes/replies 从 ~100 ms → < 3 ms |
| P1 | ✅ 已加 `idx_posts_fid_date_created` | 极低 | date 范围/q 组合查询大幅加速 |
| P1 | 拆分列表/导出字段 | 低 | 减少回表 I/O |
| P2 | 接入 FTS5 全文索引 | 中 | 模糊搜索 COUNT 从 94 ms → < 10 ms |
| P2 | COUNT 缓存 + 导出限制 | 低 | 降低高频 COUNT 与导出峰值 |
| P3 | keyset 分页 | 中 | 支撑未来百万级数据深分页 |
