# 帖子链接中继转发知识点（同源反向代理）

> 状态：**已实施（2026-09-17）**。起因是「手机打不开 `http://127.0.0.1:1024/htm_data/...`」，
> 结论是「本机回环服务要让别的设备用上，必须由本机进程做同源中继」，而不是把端口暴露出去。
>
> 代码落点：`web/mirror.py`（中继实现）、`web/frontend/src/utils/postUrl.ts`（前端拼装唯一实现）、
> `web/config.py`（`MIRROR_PREFIX` / `MIRROR_UPSTREAM` / `PUBLIC_DOMAIN`）、`mirror_service.py`（镜像端口守护，
> 看板启动器与抓取批次共用）。通用约束见 `CODEBUDDY.md` 第 26 条。

## 一、问题本质：三个地址不是一回事

| 地址                                     | 含义                             | 谁能访问                                   |
| ---------------------------------------- | -------------------------------- | ------------------------------------------ |
| `127.0.0.1`                            | **每台设备自己的回环地址** | 只有那台设备自己                           |
| `127.0.0.1:1024`（`web.exe` 的监听） | 服务**只绑在回环网卡**上   | 只有桌面机自己能连                         |
| `<桌面IP>:1024`                        | 同一个端口换了个网卡地址         | **连不上**（服务没在那个网卡上监听） |

两个最容易混的点：

1. **「我用 `127.0.0.1:1024` 去访问它」≠「它只绑回环」**：前者是客户端的访问方式，后者是服务端的绑定行为，要靠 `netstat` 才能定。
2. **手机上的 `127.0.0.1` 指的是手机自己**：所以「手机打开 `http://127.0.0.1:1024/...`」在任何配置下都不可能成功——不是配置漏了，是地址语义决定的。

判断命令与本项目实测结果：

```text
netstat -ano | findstr ":1024"
  TCP    127.0.0.1:1024    0.0.0.0:0    LISTENING    936     ← 只绑回环
（若显示 0.0.0.0:1024，才说明监听所有网卡、别的设备可直连）
```

`web.exe` 安装目录里只有 exe、没有任何可改监听地址的配置（实测确认），所以「让它绑 `0.0.0.0`」这条路走不通。

## 二、中继（反向代理）是什么

**一句话**：浏览器只访问「看板自己的源」，由看板进程替它去访问那个别人够不着的地址。

```text
                    ┌──────── 桌面机（本机）──────────────────┐
手机浏览器           │                                        │
  │  http://192.168.1.5:8088/mirror/htm_data/x.html          │
  └────────────────►│  看板进程（FastAPI）                    │
                    │    /mirror/{path} 路由                  │
                    │      │ 服务端转发（requests）           │
                    │      ▼                                 │
                    │   http://127.0.0.1:1024/htm_data/x.html ← web.exe
                    └────────────────────────────────────────┘
```

术语对照：这就是标准意义上的**反向代理**（nginx `proxy_pass`、CDN「回源」、Vite dev proxy 是同一件事）。
本项目称「同源中继」，因为入口与看板**同源**（同 host:port），所以前端不需要拼任何域名。

**最大收益**：链接从「写死一个域名/地址」变成**相对路径** `/mirror/htm_data/...`，于是本机、局域网 IP、
将来换域名/加反代，前端代码一行都不用改。

## 三、为什么不直接把 1024「暴露出去」

| 方案               | 做法                                           | 结论                                                                                                                                                        |
| ------------------ | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 改绑定             | 让`web.exe` 监听 `0.0.0.0`                 | 第三方 exe、无配置项，**改不动**                                                                                                                      |
| 端口转发           | `netsh interface portproxy` + 防火墙入站规则 | 要管理员权限、每台机器重做一遍、失败点散在环境里（绑定没成功 / 规则没生效 / IP 变了），现象只有「手机打不开」而查不到原因；还把无鉴权的 1024 直接开到局域网 |
| **自建中继** | 看板进程转发                                   | 纯代码、零环境配置、复用已放行的 8088、天然带降级钩子 →**采用**                                                                                      |

## 四、中继实现的 8 个要点

| # | 要点                                      | 细节与原因                                                                                                                                                                                                                                                                                                      |
| - | ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 | **上游地址写死**                    | 只能取自唯一配置源`txxy_env.LOCAL_PROXY`，**绝不接受调用方传入地址**，否则就是任意转发器（SSRF 入口）                                                                                                                                                                                                   |
| 2 | **降级策略**                        | 连不上 / 上游 5xx →`302` 到业务域名**同一路径（含查询串）**；**4xx 要透传**——那是镜像给出的真实答案，不代表「1024 访问不了」                                                                                                                                                                   |
| 3 | **HTML 要重写两类链接**             | ① 静态属性`href/src/action="/x"` → `/mirror/x`；② **页面 JS 运行时生成的**（实测相关帖 `a[href="/htm_data/..."]` 由脚本注入，服务端重写看不到）→ 用「点击瞬间兜底脚本」改写。只做 ① 会留下「看得见、点不通」的链接                                                                             |
| 4 | **`Location` 要重写**             | 镜像自己发的 3xx 指向`127.0.0.1:1024`，不改写浏览器会去打那个够不着的地址                                                                                                                                                                                                                                     |
| 5 | **透传二进制/大文件有三个坑**       | ①`requests.iter_content` 默认**解压**响应体，若同时透传 `Content-Encoding` / `Content-Length` 会让浏览器解析失败 → 必须走 `raw.read`（本项目 `_iter_raw`）；② `Content-Length` / `Content-Range` 必须准确（视频拖进度条靠它）；③ 逐跳头（`Connection` / `Transfer-Encoding`）不透传 |
| 6 | **HEAD 要兼容**                     | 上游不支持 HEAD（`web.exe` 实测回 404）时，改用上游 GET、按 HEAD 语义「只回头、不读体」                                                                                                                                                                                                                       |
| 7 | **路由必须在 SPA 兜底路由之前注册** | 否则`/mirror/...` 会被前端兜底路由当成页面路由，返回 `index.html`                                                                                                                                                                                                                                           |
| 8 | **限流要单独想**                    | 一次页面加载会并发十几次子资源请求，按 (IP, 路径) 计数的固定窗口限流必然误伤 → 中继不挂限流（只读、仅本机/局域网可达）                                                                                                                                                                                         |

补充：请求侧要透传 `Range`（视频拖动）、`Cookie`（Cookie 按 host 归属、与端口无关，所以桌面端在 1024 上的
登录态能带到看板源再转发给镜像）、`Referer`（同源来源，防防盗链）；`User-Agent` 则**统一用项目唯一 UA**，不透传浏览器 UA。

## 五、链接基址必须按「谁最终发这个请求」派生

这是本次最值钱的一条经验，四类消费方四种答案：

| 消费方             | 用哪种地址                                                  | 本项目落点                                                       |
| ------------------ | ----------------------------------------------------------- | ---------------------------------------------------------------- |
| 浏览器要打开       | **同源中继相对路径** `/mirror/...`                  | 帖子标题、榜单、资源页「原帖」                                   |
| 服务端自己发请求   | 本机回环`127.0.0.1:1024`                                  | 下载中心提交、抓取；接口下发（前端只从它取相对路径）             |
| 粘到别处 / 分享    | 同源**绝对**地址（`location.origin + /mirror/...`） | 帖子页「复制链接」                                               |
| 离开本机环境的产物 | **不带任何域名，只存相对路径**                        | CSV 导出（`config.to_storage_path`），与库内/采集端 CSV 同形态 |

反面教材就是改造前的状态：服务端把「展示域名」当成全局常量下发给所有客户端，于是手机必然拿到一个它永远连不上的地址。

## 六、镜像的生命周期归属（单一 owner）

镜像（`web.exe`）有两个潜在使用者：**抓取批次**（`run_batch.py`）与**看板启动器**（`start_web.py`）。
两边都启停它，就必须定好归属，否则会重演「一批抓取把另一批正在用的镜像关掉」的事故。

规则（实现见 `mirror_service.py`）：

1. **谁启动谁关闭**：端口已在监听 → 后来者 `ensure_web_service()` 返回 `None`，只消费、不接管、不关闭；
2. **退出前必须确认没有别的消费者**：看板退出时复用**批次单实例锁**（`run_batch.acquire_single_instance_lock`）判断——
   抢不到说明批次在跑，则**保留**镜像（并打印原因）；锁持有到关闭完成再释放，避免窗口期被新批次抢到；
3. **失败口径按角色分**：抓取端 fail-fast（没镜像抓不了站 → 终止本次批次）；看板端 warn-only
   （镜像只是「链接优先走本机」的加速项 → 起不来照常启动，链接自动降级到业务域名）；
4. **看板启动器默认托管镜像**，可用 `start_web.bat --no-mirror` 关闭；Docker / 离线环境
   `TXXY_LOCAL_PROXY` 为空 → 自动跳过（不会去找 `web.exe`）。

## 七、怎么验证一个中继「真的能用」

1. **可控上游**：临时写个 20 行 `http.server` 当上游，逐项断言——请求头转发、Range 返回 206/`Content-Range`、
   gzip 原样、多条 `Set-Cookie` 不合并、上游 302 的 Location 改写、5xx 降级、HTML 重写、4xx 透传。比对着真实站点测可靠得多。
2. **三条链路都要测**：上游活着 / 上游死（`TXXY_LOCAL_PROXY=http://127.0.0.1:1`）/ 本环境根本没配置镜像（置空）。
3. **与直连逐项比对**：把镜像直连页与中继页对比，断言「根相对属性全部指向中继」「页面不泄漏回环地址」。
4. **浏览器级真实点击**：桌面 + 移动双视口，**并且用局域网 IP 访问一次**——非 localhost 是非安全上下文，
   `navigator.clipboard` 直接不可用，只有这样才能测到真实的复制降级路径。
5. **判据要选可靠信号**：断言「新开页 URL 是 `/mirror/...` 且 HTTP 200」「浏览器全程没请求过 `127.0.0.1:1024`」，
   而不是看截图。

## 八、踩坑清单（都实际踩过或被实测抓住）

| 坑                                    | 现象                                                                                                                                                                                                                                                                                                | 正解                                                                                                                                                   |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `iter_content` 会解压               | 同时透传`Content-Encoding` / `Content-Length` 时浏览器解析失败                                                                                                                                                                                                                                  | 用`raw.read` 产出原始字节                                                                                                                            |
| 上游不支持 HEAD                       | 中继返回 404                                                                                                                                                                                                                                                                                        | 上游改用 GET，按 HEAD 语义只回头                                                                                                                       |
| 只重写静态链接                        | 页面里有「看得见、点不通」的链接（JS 运行时生成）                                                                                                                                                                                                                                                   | 追加点击瞬间兜底脚本                                                                                                                                   |
| SPA 兜底路由吃掉`/mirror`           | 打开链接变成看板首页                                                                                                                                                                                                                                                                                | 中继路由注册在兜底路由之前                                                                                                                             |
| **`atexit` 里 import 新模块** | `RuntimeError: can't register atexit after shutdown`；后果是「退出时镜像没关掉、web.exe 残留在 1024」                                                                                                                                                                                             | 依赖模块**启动期预加载**（`_preload_batch_lock()`），退出时只用已加载引用                                                                      |
| **改 `.bat` 三条硬约束**      | ① 行尾变 LF → cmd 成片解析失败（`'skip'/'t'/'arse' is not recognized`）；② 中文出现在 `set`/`if` 的引号里 → 引号被吞（`'ROR_DESC' is not recognized`，值也错）；③ 非 `echo` 行以全角标点结尾 → 吞掉 CR 把下一行并进本行命令（`'下第二个命令窗口或孤立进程。' is not recognized`） | 保持 CRLF；中文只放`echo` 行；非 echo 行用 ASCII 结尾。**必须在真实控制台验证**（隐藏窗口 + 重定向 stdout 下 `chcp` 效果受影响，会给假失败） |
| **启动器继承了外部 `PYTHONPATH`** | IDE / 编辑器工具注入的 `sitecustomize.py` 会拦截文件操作：某 IDE 的删除守卫在 `POST /api/resources/delete` 里抛 `SystemExit(1)`，**穿透 uvicorn 直接把看板进程带走**（用户看到 500 + 服务退出，日志里连 `Shutting down` 都没有） | `start_web.bat` 里 `set "PYTHONPATH="`；`start_web.py` 启动时检测外部 `sitecustomize` 并告警、同时把 `PYTHONPATH` 从环境摘掉供子进程使用。**AI 助手用自己 shell 拉起的服务一定带这个变量**，验证性重启也要显式清环境 |
| **看板日志写进了 `web/outputs/`** | `file_logger.LOG_ROOT` 是相对 `outputs`，而启动器在加载 `web/app.py` 前 `chdir(web/)` → 排查时在项目根 `outputs/` 找不到当次会话日志（本次多绕了一圈） | `LOG_ROOT` 改为基于 `file_logger.py` 自身位置的绝对路径（2026-09-17）；通用规则：按 CWD 解析的路径都要检查调用方会不会 chdir |

## 十、常见问答

**Q：手机链接打不开，怎么排查？**
① `GET /api/health` 看 `mirror_upstream` 是否为空（空 = 本环境没配镜像）；② `netstat -ano | findstr ":1024"`
看镜像是否在跑（没跑就让 `start_web.bat` 或 `python run_batch.py` 拉起，或手动启动 `web.exe`）；
③ 直接请求 `http://<看板IP>:8088/mirror/htm_data/...`：**返回 302 到业务域名 = 镜像没起来**（降级正常），
返回 200 = 中继与镜像都正常。

**Q：为什么链接里带 `/mirror`，而不是直接给 1024 的地址？**
因为相对路径与「谁在访问」无关：桌面、手机、局域网 IP、将来换域名都能用同一份链接。

**Q：中继会不会拖慢看板？**
帖子页只有 HTML 经看板转发（本机回环，几十 KB 级）；贴内图片在外部图床/CDN，由浏览器直连；
下载中心的大文件下载发生在**服务端**，不经过中继。

**Q：Docker 里这套还成立吗？**
成立：容器内没有 `web.exe`、`TXXY_LOCAL_PROXY` 为空 → 启动器跳过镜像管理，`/mirror` 路由整体 302 到业务域名，
行为与本地一致（只是不走镜像加速）。
