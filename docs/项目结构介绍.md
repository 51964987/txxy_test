# 项目结构介绍

当前项目是**标准的前后端分离结构**，但更准确地说它是一个「**前端 + 后端 API + 独立的 Python 采集工具集**」三位一体的单人自用工具。

## 整体架构

```
txxy_test/
├── 采集端（CLI 工具集，项目根目录）   ← 真正写库的一方
│   ├── scraper.py / run_batch.py / run_recorder.py
│   ├── download_files.py / extract_*.py / media_download.py
│   ├── txxy_env.py / http_headers.py / txt_export.py
│   └── init_db.py
└── web/                              ← 前后端都在这里
    ├── app.py / api.py / config.py / db.py ...   （后端）
    └── frontend/                     （前端 Vue3）
```

## 后端（Web 服务）

### 技术栈与入口

- **技术栈**：Python3 + FastAPI，启动入口 `web/app.py`（挂载 GZip、API 请求耗时监控、SPA 静态托管）。
- 启动：`python web/app.py`，默认 `http://127.0.0.1:8080`；若 `web/frontend/dist` 已构建则同时托管前端 SPA，否则仅提供 API（Swagger 调试页在 `/api/docs`）。
- **关键约束**：
  - 数据库 `db/posts.db` 是 **SQLite 只读**（`PRAGMA query_only=ON`），统计接口经 `web/db.py` 的 `cached()` 做 **5s TTL 内存缓存**。
  - 写入数据库**只由根目录的采集脚本负责**，Web 进程严禁写库；但 Web 会写文件系统状态（下载任务 JSON、回收站索引、榜单快照），用 `web/atomicfile.py` 做原子落盘。
  - 接口统一 `HTTPException(detail)` 返回错误，无 `{ok:false,msg}` 形态。
- 路由统一挂在 `/api` 前缀下（`app.include_router(api_router, prefix="/api")`），另有一个独立健康检查 `GET /api/health`（返回数据库路径、是否存在、运行环境、前端是否已构建）。

### HTTP 封装

- 统一走 `web/frontend/src/api/index.ts`（原生 fetch，10s 超时 + 同 key 去重取消 + 统一 `ApiError`），禁止裸 fetch。
- 提供 URL 构造助手：`sseUrl()`（SSE 地址）、`exportCsvUrl()`（CSV 导出）、`resourceFileUrl()` / `resourceVideoUrl()`（资源预览）。
- 状态管理跨页归并 `useAppStore`（全局刷新版本号/最后更新）+ `useDashboardStore`（自动刷新开关/实时时钟），不新建分散 store。
- 错误统一 `ElMessage.error` 提示，禁止裸抛或静默吞错。

## 采集流程串讲（数据是怎么进库的）

数据生产者是根目录的 CLI 工具集，与 Web 看板完全解耦，链路如下：

1. **调度层 `run_batch.py`**：遍历 `txxy_env.SECTIONS` 所有版块，用 `ThreadPoolExecutor`（`MAX_WORKERS=3`）为每个版块起一个 `scraper.py` 子进程，`STAGGER_DELAY=5` 秒错开启动防反爬；启动前先确保本机 1024 镜像端口就绪（端口守护：未监听则自动起 `web.exe`，跑完再关）。`USE_LOCAL_PROXY` 由 `txxy_env.use_local_proxy()` 推出（本地默认启用，置空=直连业务域名），命令行可临时覆盖。
2. **抓取层 `scraper.py`**：单版块多页抓取，请求头复用 `http_headers.build_headers`（全项目唯一 UA）；页间间隔**自适应**（顺利 1.0s，异常翻倍上限 10.0s）；单页失败重试 3 次，连续失败 3 页判定站点不可用而停抓——停抓时该版块/本次运行记为 `error`（非成功），避免「0 条却标绿」的假成功（手动 Ctrl+C 则记为 `cancelled`）。
3. **容错与续传**：进度文件 `outputs/<日期>/<fid>_progress_<日期>.txt` 按「版块+日期」固定文件名（断点续传按精确文件名读进度），CSV 同名 `append` 累积；同批次产物共享同一时间戳、落同一日期目录（跨午夜也不会错位）。
4. **入库**：抓取结果按 `SQLITE_BATCH_ROWS=500` 行批量写入 `db/posts.db`（posts 表 + `run_days` 运行记录）。
5. **展示**：Web API 只读读库，5s TTL 缓存，前端看板把上述数据呈现为榜单 / 趋势 / 明细。

> 关键边界：**Web 不写 SQLite**，但会写文件系统状态（下载任务 JSON、回收站索引、榜单 NEW 快照 `outputs/board_snapshot.json`）。这些「Web 自有状态」绝不写 posts.db，以免与抓取进程并发冲突；落盘统一走 `atomicfile.write_json_atomic` 保证原子性。

## 一个容易混淆的点

按项目规范里的定位，Web 看板只是「展示层」，不是项目全貌：

- **采集端**（根目录 `scraper.py` 等）才是数据的生产者，重「跑得通、能容错、可断点续传」，历史债也集中在这里。
- **管理端**（`web/download_tasks.py`、`web/resources.py` 回收站）负责下载队列持久化、回收站保留 N 天。
- **展示端**（API + 前端）做 BI 看板，口径自洽、5s 缓存、限流、下钻继承上下文，规范最严。

## 重要前提

- 当前是**单人自用、本机运行**：接口无鉴权，部分路径硬编码，依赖本机 1024 镜像（本地镜像站，只能替换 host 访问，无法改用业界通用的 `HTTPS_PROXY`）。
- **数据是核心资产，会跨环境搬迁**：支持离线（air-gapped）镜像交付，数据在本机 / Docker / 离线机之间流动。
  - 推论：域名不得写入数据库（入库只存相对路径 `/htm_data/...`）；dotenv 保持零依赖；域名按环境自适应。
  - 破坏这条不会立刻报错，但会让数据换个环境就打不开（历史上因此产生过十几万条带代理地址的脏数据）。
- 若要开放多人或迁到服务器，须先补鉴权并将路径配置化。
