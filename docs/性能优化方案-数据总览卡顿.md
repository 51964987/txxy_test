# 数据总览页面卡顿 · SQLite 查询性能优化方案

> 背景：进入数据总览（Dashboard）页面时卡顿数秒。经排查，根因在 `web/api.py` 统计接口的查询，非前端渲染。
> 本文件为排查结论 + 变更方案，方案待确认后实施。

## 一、现状排查结论

### 1.1 数据库与表结构

- 库：`db/posts.db`，WAL 模式，122,003 行，约 56MB（13748 页 × 4096B）。
- 表 `posts`（title 为 PRIMARY KEY），现有索引：

| 索引 | 定义 |
|---|---|
| `idx_posts_date` | `(date)` |
| `idx_posts_fid` | `(fid)` |
| `idx_posts_fid_date` | `(fid, date)` |

- `likes` / `replies` / `author` **无任何索引**；`likes` / `replies` 为 TEXT 文本数字（可能为空串）。

### 1.2 查询计划（EXPLAIN QUERY PLAN）与耗时

测量口径与生产一致：**每次查询新建连接**（`db.query()` 每请求短连接 → sqlite 页缓存冷启动），取实际单次耗时。

| # | 查询（`/stats/overview` 内，串行执行） | 查询计划 | 耗时 | 结论 |
|---|---|---|---|---|
| 1 | `COUNT(*) FROM posts` | SCAN 覆盖索引 `idx_posts_date` | 15ms | 正常 |
| 2-4 | `COUNT(*) ... date=?` / `date>=?`（今天/昨天/近7天） | SEARCH 覆盖索引 `idx_posts_date` | 45ms | 正常 |
| 5 | `MAX(created_at), MAX(date) FROM posts` | **SCAN posts（全表扫描）** | **103ms** | `created_at` 无索引，双 MAX 无法走索引 |
| 6 | `COUNT(DISTINCT author) ... author<>''` | **SCAN posts + USE TEMP B-TREE** | **168ms** | `author` 无索引，全表扫描 + 临时去重排序 |
| 7 | `COUNT(DISTINCT author) ... date=?` | SEARCH `idx_posts_date` | 10ms | 正常 |
| 8 | `_board_top("likes")` 窗口函数 | **CO-ROUTINE + SCAN 全表 + TEMP B-TREE 排序** | **~656ms** | 见 1.3 |
| 9 | `_board_top("replies")` 窗口函数 | 同上 | **~656ms** | 见 1.3 |
| - | **overview 合计（冷连接）** | | **~1.65s** | **卡顿主因** |

其它数据总览接口（均正常，非瓶颈）：

- `/stats/trend`（30天）：18ms，覆盖索引 `idx_posts_date`，无缓存。
- `/stats/fid_dist`：49ms，覆盖索引 `idx_posts_fid_date`，缓存 5s。
- `/stats/recent`（10 条）：1.2ms，`idx_posts_date` 倒序 + LIMIT 短路，无缓存。

### 1.3 根因分析

1. **`_board_top`（likes/replies 各一次，占 overview 总耗时约 79%）**
   ```sql
   SELECT fid, title, url, likes AS value FROM (
     SELECT fid, title, url, likes,
       ROW_NUMBER() OVER (PARTITION BY fid ORDER BY
         CAST(likes AS INTEGER) DESC, date DESC, created_at DESC) AS rn
     FROM posts WHERE likes IS NOT NULL AND likes <> ''
   ) WHERE rn = 1 ORDER BY CAST(value AS INTEGER) DESC, fid
   ```
   窗口函数排序键为**表达式** `CAST(likes AS INTEGER)`，任何现有索引都无法命中 → SQLite 必须把 12.2 万行整体物化进临时 B-tree 排序，且 likes/replies 各跑一遍。实测表达式索引对窗口查询**无效**（EXPLAIN 仍走 `idx_posts_fid` + 临时排序）。

2. **`COUNT(DISTINCT author)`（168ms）**：`author` 无索引 → 全表扫描 + 临时去重 B-tree。

3. **`MAX(created_at), MAX(date)`（103ms）**：`created_at` 无索引 → 全表扫描取最大值。

4. **N+1 / JOIN**：数据总览所有统计查询均无 JOIN、无 N+1（`_board_top` 每次请求仅 1 条 SQL）。已排除此类问题。

## 二、变更方案

### 方案 A：仅改写 `_board_top`（无 schema 变更，低风险）

把窗口函数查询改为**按版块循环 + `ORDER BY ... LIMIT 1`**（13 个版块 → 13 条小查询，各自命中 `idx_posts_fid`）：

```sql
-- 每个 fid 各执行一次
SELECT fid, title, url, likes AS value FROM posts
 WHERE fid = ? AND likes IS NOT NULL AND likes <> ''
 ORDER BY CAST(likes AS INTEGER) DESC, date DESC, created_at DESC
 LIMIT 1
```

- 实测：board_top 两项 1312ms → **528ms**；overview 1.65s → **0.88s**（约 1.9 倍提升）。
- 正确性已实测验证：结果与现状**逐行一致**（13 行，fid+title 全同）。

### 方案 B：方案 A + 新增索引（推荐）

在 `init_db.py` 的 `_DDL_POSTS` 中追加 4 个幂等索引（`CREATE INDEX IF NOT EXISTS`，重跑即迁移，不重建表）：

```sql
CREATE INDEX IF NOT EXISTS idx_posts_likes_expr
    ON posts(fid, CAST(likes AS INTEGER), date, created_at);
CREATE INDEX IF NOT EXISTS idx_posts_replies_expr
    ON posts(fid, CAST(replies AS INTEGER), date, created_at);
CREATE INDEX IF NOT EXISTS idx_posts_author
    ON posts(author) WHERE author IS NOT NULL AND author <> '';
CREATE INDEX IF NOT EXISTS idx_posts_created_at
    ON posts(created_at);
```

- 前两个为**表达式索引**（SQLite ≥ 3.9，Python 3.11 自带 ≥ 3.37，满足），使 per-fid 查询由"索引定位 fid + 临时排序"变为**直接按索引顺序取 LIMIT 1**（实测 EXPLAIN：`SEARCH posts USING INDEX idx_posts_likes_expr (fid=?)`）。
- 实测组合效果：

| 项 | 现状 | 方案 A | 方案 B |
|---|---|---|---|
| `_board_top` ×2 | 1312ms | 528ms | **82ms** |
| `COUNT(DISTINCT author)` | 168ms | 168ms | **26ms** |
| `MAX(...)` | 103ms | 103ms | **39ms** |
| **overview 合计** | **~1.65s** | ~0.88s | **~0.21s（约 8 倍）** |

### 方案 C：前端分区懒加载（推荐与 B 组合）

> 依据同类项目最佳实践评估（详见下方"同类项目参考"）：路由级懒加载与 ECharts 按需引入本项目已具备；当前主要缺口是**模块级懒加载、骨架屏、可见性懒加载与渲染顺序优化**。

#### C.1 现状问题

`DashboardView.vue` 的 `load()` 用 `Promise.all` 并行请求 4 个接口，并用**整页 `v-loading` 遮罩**等待全部返回后才渲染：

- 最慢接口（`/stats/overview`）决定整个页面的首帧时间（短板效应）；
- 页面内 6 大区块（KPI 卡、趋势图、分布图、点赞榜、回复榜、最近抓取）同生共死，无法渐进呈现；
- 热门榜 / 最近抓取常位于首屏之外，仍随首屏一起请求。

#### C.2 区块拆分与加载优先级

| 区块 | 数据源 | B 方案后耗时 | 优先级 | 加载方式 |
|---|---|---|---|---|
| KPI 指标卡（6 张） | `/stats/overview`（轻量字段） | ~100ms | P0 首屏 | 进入即加载 |
| 每日新增趋势图 | `/stats/trend` | 18ms | P0 首屏 | 进入即加载 |
| 版块分布图/排行榜 | `/stats/fid_dist` | 49ms | P0 首屏 | 进入即加载 |
| 点赞/回复热门榜 | `/stats/overview`（top_likes/top_replies） | ~120ms | P1 | 视口懒加载 |
| 最近抓取 Top10 | `/stats/recent` | 1.2ms | P1 | 视口懒加载 |

#### C.3 加载策略

1. **去掉整页 `v-loading`**，改为各区块独立骨架屏（`el-skeleton` / shimmer），数据到达即替换，不再整页白屏转圈；
2. **首屏 P0 区块各自独立请求、独立渲染**（`Promise.allSettled` 或直接拆分，互不阻塞）；
3. **P1 区块可见性懒加载**：用 `IntersectionObserver` 监听容器，进入视口（`rootMargin: 200px` 预取）才发起请求；不支持时回退为进入即加载；
4. **渲染顺序**：数据到达后在 `nextTick` + `requestAnimationFrame` 中初始化图表，避免阻塞首帧布局；保持趋势天数切换、分布图视图切换、跳转、自动刷新联动等交互不变；
5. **自动刷新联动**：配置开启时，仅刷新**已加载**的区块（懒加载区块未进入视口时不请求）。

#### C.4 收益（B + C 组合）

- 冷连接首屏（KPI + 图表）：由 ~1.65s 降至 **~0.27s（约 6 倍）**，首帧即出骨架屏与渐进内容；
- 热门榜 / 最近抓取滚动进入视口时即时加载，无感知延迟；
- 非视口内容不再浪费请求，页面滚动过程平滑。

#### C.5 风险与权衡

- **改动面**：`DashboardView.vue` 需按区块拆分（组件或模板分区 + 独立 loading 状态），需保持现有交互与自动刷新联动；
- **浏览器兼容**：`IntersectionObserver` 现代浏览器均支持，老环境回退直接加载；
- **错误处理**：区块独立失败提示（区块内错误态 + 统一 `ElMessage`），避免整页报错。

#### 同类项目参考（调研摘要）

- **Grafana / Superset Dashboard**：面板（Panel）独立请求、独立渲染，重面板不阻塞轻面板；Superset 优化实践核心即"调整请求顺序与渲染顺序"。
- **数据大屏 / Vue 后台看板**（vue-bigscreen-template、可视化大屏脚手架等）：普遍采用"分模块独立加载 + 骨架屏 + 首屏优先、重模块延迟加载"。
- **前端通用实践**：骨架屏（货拉拉案例）、`IntersectionObserver` 懒加载、异步组件 + Suspense，均作为首屏优化的标准手段。
- **本项目已具备**：路由级懒加载（`router` 已用 `() => import()`）、ECharts 按需引入（`echarts/core` tree-shaking）。

### 实施步骤

1. 修改 `web/api.py`：重写 `_board_top()` 为 per-fid 循环（保留现有返回结构，`fid` 列表来自 `SELECT DISTINCT fid FROM posts ORDER BY fid`，结果按 `CAST(value AS INTEGER) DESC, fid` 排序与现状一致）。
2. 修改 `init_db.py`：在 `_DDL_POSTS` 追加 4 个 `CREATE INDEX IF NOT EXISTS`。
3. 已有环境迁移：执行一次 `python -X utf8 init_db.py`（幂等，仅补索引，不重建表）。
4. 前端 `DashboardView.vue` 按方案 C 拆分区块：
   - 去掉整页 `v-loading`，KPI / 趋势图 / 分布图首屏独立加载 + 骨架屏；
   - 热门榜 / 最近抓取用 `IntersectionObserver` 视口懒加载（`rootMargin: 200px`，不兼容时回退直载）；
   - 保留趋势天数切换、分布视图切换、跳转、自动刷新联动（仅刷新已加载区块）。
5. 回归验证：
   - `_board_top` 新旧结果逐行比对一致（likes/replies 各 13 行）；
   - 冷连接下 overview 总耗时 ≤ 300ms；
   - 首屏（KPI + 图表）冷连接 ≤ 300ms，热门榜 / 最近抓取滚动可见后即时出现；
   - 页面进入无卡顿、无整页白屏；trend / fid_dist / recent 行为不变。

### 风险与权衡

- **写入开销**（方案 B）：新增索引会略微增加 scraper 的 `INSERT ... ON CONFLICT DO UPDATE` 维护成本（每行多维护 2 个表达式索引 + 1 个部分索引 + 1 个普通索引）。12.2 万行规模下可接受；若后续数据量激增，可将 likes/replies 表达式索引改为部分索引（`WHERE likes <> ''`）缩小体积。
- **依赖 SQLite 版本**：表达式索引需 ≥ 3.9.0，当前 Python 3.11 环境满足；Docker 镜像内 Python 版本需确认（≥ 3.9 即无风险）。
- **只读约定**：web 层保持"绝不写库"，索引统一由 `init_db.py`（初始化路径）创建，不在 web 启动时建。
- **缓存策略**：overview / fid_dist 维持 5s TTL（配合前端 5s 轮询实现抓取进度准实时刷新）；trend / recent 量级小（≤20ms）无需缓存。
- **前端改动面**（方案 C）：`DashboardView.vue` 需按区块拆分 loading 状态，保持既有交互；`IntersectionObserver` 老浏览器回退直载。

## 三、结论

- 卡顿根因：`/stats/overview` 冷连接下约 1.65s，其中 `_board_top` 两个窗口查询占 79%（1312ms），其次 `COUNT(DISTINCT author)` 168ms 与 `MAX()` 103ms 的全表扫描；前端整页 `v-loading` + `Promise.all` 让最慢接口决定首帧。
- 无 N+1、无未优化 JOIN。
- 推荐 **方案 B + 方案 C**：
  - 后端：改写 `_board_top` + 新增 4 个索引，overview 从 ~1.65s 降至 ~0.21s（约 8 倍）；
  - 前端：分区懒加载 + 骨架屏 + 视口懒加载，首屏即出骨架与渐进内容，热门榜 / 最近抓取滚动时即时加载；
  - 组合后冷连接首屏约 ~0.27s，改动集中、幂等、可回归。
